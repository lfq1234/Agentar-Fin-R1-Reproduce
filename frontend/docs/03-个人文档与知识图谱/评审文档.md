## 1. 评审结论

两份文档（需求 / 技术）覆盖完整：范围、10 项功能需求、数据模型、接口契约、验收标准、组件/Hook/API 扩展、实现步骤、风险与替代方案齐全，且已显式关联 01（技术栈/API 客户端/ErrorModal）与 02（个人文档入口 / `PersonalDocsPanel` 初版）。

相比 01 评审时"目标与现状混淆"的问题，03 在 §2.2 已明确"后端解析算法另议"、在 R1/R4 已标识后端未就绪与依赖冲突，意识到位。但存在 **4 项门禁项（P0×1 / P1×2 / P2×1）**，核心是"前端新增契约未与后端源码核对""`d3-force` 偏离 01 零依赖原则未决策""图谱渲染性能上限与声明不一致"，必须在进入实现前闭环，否则会出现 **联调 404 / 图谱卡死 / 依赖原则被悄悄突破**。

一致性核对见 §4：**文档内部（需求↔技术）基本一致**；但 **与后端源码的契约核对无法完成**（后端 03 模块接口为新增、本次未读到源码），标记为"待核对"。

| 编号 | 级别 | 问题 | 影响 | 建议改法 |

| G1 | P0 | **新增后端契约未与后端源码核对 / 未锁定实现顺序**。需求 §5.2 列出 `POST/GET/DELETE /api/v1/documents`、`GET /api/v1/documents/{id}/status`、`GET /api/v1/knowledge-graph` 共 5 个全新接口，并注明"需后端配套实现；如后端暂未实现，前端先做 Mock"。与 01 的 G1 同源问题：已识别但未上升为阻断首步，且后端 `03-传统后端基础层` 是否已实现这些路由、字段（尤其 `knowledge-graph` 返回结构是否与 `PersonalKnowledgeGraph` 吻合）未验证。 | 联调阶段 5 个接口可能全 404 或字段漂移；前端 Mock 跑通后切换真实接口时返工。 | 从"已知问题 R1"提升为**实现清单第 0 项**：① 先核对或约定 `backend/03` 是否落地上述路由，给出字段对齐表；② 若后端未就绪，明确 Mock→真实 切换开关（如 `VITE_USE_MOCK` 或 `client.ts` 内常量）与数据样例（建议项 S6）；③ 技术文档 §9 把"Mock 联调"前置为第 1 步并标注为阻断项。 |
| G2 | P1 | **`d3-force` 偏离 01「零额外依赖」原则未做决策**。01 技术栈明确"不引入额外状态/HTTP/UI 库"；03 技术 §1 / 风险 R4 承认冲突，仅以"~10KB gzip"辩解，未获得对该偏离的显式批准。 | 若团队坚持零依赖，实现中途被叫停返工；或原则被悄悄突破无人担责。 | 在 03 文档顶部（需求 §4 / 技术 §1）以**决策形式**明示二选一：a) 批准引入 `d3-force`（单一子包，仅力导向模拟，渲染自研 SVG）；或 b) 拒绝并自研简易力导向（工作量高、效果弱）。无论哪种，技术文档 §3 目录与 §9 步骤需与之匹配（b 则删除 `npm install d3-force`，改为 `utils/graph.ts` 内力计算）。 |

## 3. 建议项（非门禁，提升质量）

| 编号 | 建议 | 说明 |
| --- | --- | --- |
| S1 | 跨模块依赖 `ErrorModal` 显式化 | 需求 FR9 引用 02 的 `ErrorModal` 弹窗。需确认 02 是否真会产出该组件（02 文档需核对其定义）。建议在 03 文档标注"依赖 02 的 ErrorModal，若 02 未实现则 03 暂用原生 `alert`/简单 Banner 兜底"，消除隐性耦合。 |
| S2 | 轮询需补 cleanup | 需求 FR3 要求"间隔 2s、最多 60 次"；技术 §5.1 `pollStatus` 用 `setInterval` 但未提组件卸载清理。建议在技术 §5.1 补 `useEffect` 返回 `clearInterval`，并在 60 次或 `done/error` 后停止，避免内存泄漏/卸载后 setState 报错。 |
| S3 | 联动方式二选一 | 需求 FR7 给出两种联动（"带入对话"追加到输入框 / "基于此文档提问"新建会话）；技术 §8 仅描述单一 `onInjectContext` 回调。需锁定产品决策：默认哪种、是否两者都做，以及"当前会话"在 02 多会话模型下指 `activeSessionId`。 |
| S4 | 类型命名防冲突 | 技术 §3 在 `types/agent.ts` 新增 `PersonalDocument`/`GraphNode`/`GraphEdge`；需确认不与后端未来图接口、或其他模块类型重名（尤其 `GraphNode` 较通用）。建议加 `Personal` 前缀（如 `PersonalGraphNode`）或收敛到 `knowledge.ts` 独立文件。 |
| S5 | 接口前缀一致性复核 | 需求 §5.2 注"所有路径统一带 /api 前缀"，技术 §7 用 `${BASE}/documents`（BASE="/api/v1"）。与 01 G1 决策（前后端统一 `/api`）一致 ✅；但需确认后端 `03` 模块注册路由时也带 `/api` 前缀（否则代理 404）。建议在 G1 核对中一并验证 `include_router(prefix="/api")`。 |
| S6 | 给出 Mock 数据样例 | 需求 R1 / 技术 §9 第9步"Mock 联调"但未给样例结构。建议随文档附一份 `mock/graph.json`（含 nodes/edges 示例）与 `mock/documents.json`，前端直接 fetch 本地文件，联调切换零成本。 |
| S7 | 响应式/可访问性落到 CSS | 需求 FR8（≤820px 分屏）、非功能（WCAG 2.1 AA、aria-label）在技术上仅 §6 提了"颜色映射"。建议在技术 §6 补 `index.css` 断点（media query 820px）与按钮 `aria-label` 清单，验收可逐项勾选。 |
| S8 | 上限语义统一 | 非功能"超 500 节点提示文档过多"与 FR4"展示全量图"对超上限的处理（降采样 vs 提示）表述冲突。需明确：达到上限是"提示并截断前 N"还是"允许全量但提示卡顿风险"，与 G3 的渲染方案联动决策。 |
