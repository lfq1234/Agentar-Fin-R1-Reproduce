## 4. 技术文档评审

### 4.1 架构与组件（良好）
- 架构图（§2）、目录结构变更（§3）、组件 props（§5）、`useChat` 改造（§6）、`App.tsx` 布局（§7）、CSS（§8）层层细化，链路自洽。
- `deriveTitle` 与 `deleteSession` 切换逻辑（§6）与需求 §3 目标 3/目标 1 整体吻合。

### 4.2 必须修正的问题（见 M 类）
- **M2 标题截断**：需求 §3 目标 3 明确 `content.trim().slice(0, 20)`（无省略号）；技术 §6 实现为 `text.slice(0, 20) + "…"`（带省略号，且实际为 21 字符）。实现方会按技术文档写，但验收按需求描述则不符。须统一。
- **M3 移动端响应式缺口**：技术 §8 给出 `@media (max-width: 820px)` 的 `.sidebar { transform: translateX(-100%) }` 与 `.sidebar.open { transform: translateX(0) }`，但全文（§2 架构图、§5 组件、§7 App.tsx）**没有任何汉堡菜单按钮或 `sidebarOpen` 状态**来切换 `.open`。即窄屏下侧边栏永远隐藏、无法打开，响应式功能不完整。
- **M4 conversationId 复用**：需求 §4 写"每个会话发送消息时携带 `user_id` 与 `conversation_id`（若后端返回）"，技术 §6 仅说"更新当前会话的 `conversationId`"，**未明确已有 `conversationId` 时是否复用**。若不复用，用户在同一会话切走再切回、再次发送会令后端新建会话，丢失后端侧历史上下文（与"conversation_id 隔离/连续"目标相悖）。

### 4.3 可实施性遗漏（见 N 类）
- 技术 §3 目录结构表缺 `PersonalDocsPanel.tsx`（§5.5、§7 均引用）—— **N1**。
- 相对时间"刚刚/5 分钟前/昨天"（需求 §3 目标 1）在技术文档中**无实现说明**；且"不引入额外依赖"下需手写或确认 `Intl.RelativeTimeFormat`—— **N3**。
- `runAnalyze "不受会话切换影响，仍分析最近一条助手回复"`（技术 §6）措辞模糊，应明确为"分析**当前会话**最近一条助手回复"—— **N4**。
- 场景 `scene` 会话间隔离（需求 §3 目标 4）但技术未说明 `SceneSelect` 与 `currentSession.scene` 的双向绑定—— **N5**。

## 6. 问题分级清单与修复建议

### 6.1 重大级（Major，开工前必修）

**M1 · 刷新语义自相矛盾**
- 现象：需求 §2.1"当前激活会话在 URL 或本地状态中保持；刷新后默认回到最近会话"与技术 §1"刷新后数据丢失"、需求 §7 已知问题 1"刷新即丢失"直接冲突。
- 影响：实现者无法判定本期刷新行为，易写成"刷新回到新空白会话"或"尝试恢复"两种不同产物。
- 建议（二选一，推荐 A）：
  - **A（与已知问题/技术一致）**：将需求 §2.1 改为"本期会话仅存内存，**刷新即丢失、重置为单个空白会话**；URL/本地保持与刷新恢复为后续接入后端 `GET /api/v1/conversations` 时的能力（见 §7 已知问题 1）"。
  - B（若确实要做本地保持）：明确引入 `localStorage` 持久化（但违反"不引入本地持久化/本期最小改动"基调，不推荐）。

**M2 · 标题截断逻辑不一致**
- 现象：需求 `slice(0,20)` 无省略号；技术 `slice(0,20)+"…"`。
- 影响：验收描述与实现产物不符；且带省略号时显示宽度多 1 字符。
- 建议：统一为**带省略号**（更符合 UX），并同步修订需求 §2.1、§2.3、§3 目标 3，使其与技术 §6 一致：`text.length > 20 ? text.slice(0, 20) + "…" : text`。

**M3 · 移动端侧边栏无展开入口**
- 现象：技术 §8 CSS 有 `.sidebar.open` 展开态，但无组件/状态触发 `open`。
- 影响：窄屏（≤820px）侧边栏永久隐藏，用户无法访问历史会话/新对话。
- 建议：
  - 新增 `sidebarOpen` 状态（放 `App.tsx` 或 `useChat`），在 `Header` 或 `app-main` 左上角加**汉堡菜单按钮** `onToggleSidebar`。
  - 切换会话/打开个人文档时 `setSidebarOpen(false)`（移动端自动收起）。
  - 技术 §3 目录结构补 `HamburgerButton`（或并入 `Header`），§5、§7 补对应 props 与调用。

**M4 · `conversationId` 复用语义缺失**
- 现象：需求 §4 要求"发送时携带 `conversation_id`（若后端返回）"，技术 §6 仅"更新当前会话的 conversationId"，未说"已有则复用"。
- 影响：同一会话切走再回来、再次发送若不携带原 `conversationId`，后端会新建会话，历史上下文断裂——与"conversation_id 隔离且连续"目标相悖。
- 建议：技术 §6 `send` 明确规则——"若 `currentSession.conversationId != null`，发送请求体携带该值（复用后端会话）；后端返回新 `conversationId` 时更新；若 `null` 则不携带，由后端新建"。需求 §4 同步加一句"切换回已有会话后发送应复用其 `conversationId`"。

### 6.2 一般级（Minor，可随实现处理）

- **N1**：技术 §3 目录结构表补 `PersonalDocsPanel.tsx`；需求 §2.3 状态总览补一行 `⬜ 待建 | src/components/PersonalDocsPanel.tsx`。
- **N2**：需求 §3 目标 5 由"底部或顶部"改为"底部"，与技术 §5.1 对齐。
- **N3**：技术补充相对时间方案——推荐用原生 `Intl.RelativeTimeFormat`（无额外依赖），或手写 `formatRelativeTime(ts)`，并在 `SessionItem` props 说明中引用。
- **N4**：技术 §6 将 `runAnalyze` 描述改为"分析**当前会话**最近一条助手回复"，与需求 §3 目标 4 会话隔离一致。
- **N5**：技术补充 `SceneSelect` 与 `currentSession.scene` 双向绑定——切换会话时 Header 场景回显当前会话 scene；用户改场景时更新 `currentSession.scene`（§7 App.tsx 布局与 §6 useChat 补对应回调 `onSceneChange`）。
- **N6**：需求将"最近会话"统一术语为"`updatedAt` 最新的会话"，与技术 §6 一致。

### 6.3 建议级（Suggestion）

- **S1**：技术 §8 多处硬编码 light 主题色（`#eff6ff`、`#f3f4f6`）。dark 模式下会突兀；建议 hover/active 改用 CSS 变量或 `rgba(primary, .08)`，并尽快补 dark 变量（技术 §8 已自承仅 light）。
- **S2**：`crypto.randomUUID()`（技术 §6）需安全上下文（localhost 开发 OK，但 http 非本地部署不可用）。建议补降级生成（如 `${Date.now()}-${Math.random().toString(36).slice(2)}`）或注明仅 localhost 开发环境。
- **S3**：个人文档面板打开时，建议明确 `Header` 的"新对话/场景选择"是否禁用，避免用户在面板态误触发聊天态（技术 §7 仅互斥主区内容，未约束 Header）。
- **S4**：验收标准（需求 §6 / 技术 §10）偏手动 UI 验证；建议补充可单测项：`deriveTitle`、`deleteSession` 切换逻辑、`formatRelativeTime`。若本期不引入测试框架，可登记为后续项。
- **S5**：两份文档均标注"状态：草稿（待实现后转已落地）"，实现完成后别忘了回填状态并同步 `00-总文档` 的模块进度（属跨文档维护，本次评审不强制）。

## 8. 总体结论与放行建议

**结论：有条件通过（Conditional Pass）。**

两份文档质量整体良好——范围克制、最小改动原则清晰、组件与 Hook 设计自洽，具备直接进入实现的条件。但存在 **1 处需求自相矛盾（M1 刷新语义）** 与 **3 处需求↔技术冲突（M2 标题截断、M3 移动端入口、M4 conversationId 复用）**，会在开发期造成歧义或功能缺陷。

**放行动作**：
1. 需求方就 §7 待确认 3 项拍板（建议均采评审推荐值）。
2. 按 M1–M4 修订需求文档与技术文档，并顺带消化 N1–N6。
3. 修订后文档状态可从"草稿"推进，进入开发；S 类建议随实现酌情采纳。

修正 M1–M4 后，本模块可放行开发，预计无遗留阻塞风险。
