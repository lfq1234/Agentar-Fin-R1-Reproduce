## 1. 评审结论

两份文档（需求 / 技术）**结构完整、契约与后端源码逐字段核对一致**，是当前前端模块质量最高的产出，明显优于"先写文档后改代码"的常见返工。

但存在 **4 项门禁项（P0×1 / P1×3）**，均为"文档已识别但未闭环"或"目标设计与代码现状脱节"，必须在进入实现/联调前处理，否则会出现 **联调 100% 404** 或 **核心功能（会话连续性）开箱不可达**。

一致性核对结果见 §4，**接口契约 100% 与后端源码吻合**，无字段漂移。

## 2. 门禁项（必须闭环，否则不准进入实现）

| 编号 | 级别 | 问题 | 影响 | 建议改法 |
| --- | --- | --- | --- | --- |
| G1 | P0 | **路径前缀 `/api` ↔ `/v1` 错配未闭环**。真实代码 `src/App.tsx` 调 `/api/v1/chat`，`vite.config.ts` 代理 `/api → :8000`，而后端暴露 `/v1/chat`（无 `/api`）。三处不一致，经代理必然 404。文档已列入"已知问题 1"，但措辞为"实现时统一"，未上升为强制首步。 | 联调全链路不通，前端永远拿不到响应。 | 从"已知问题"提升为**实现清单第 0 项**，并给出具体 diff：① `App.tsx` 的 `fetch("/api/v1/chat")` → `fetch("/v1/chat")`；② `vite.config.ts` 的 `proxy: {"/api": ...}` → `"/v1"`；③ 同步 `README.md`。技术文档 §8 / 需求 §3 目标 7 已描述目标，补一句"此为阻断项，首步消除"。（注：v3 已决策反转——前后端统一 `/api` 前缀，后端 `include_router(prefix="/api")`，前端维持 `/api/v1/*` 不变；本建议的"去 /api"方案作废。） |
| G2 | P1 | **"会话连续性"被列为核心功能目标，却依赖默认关闭的配置 + 当前未传的字段**。目标 3（需求 §3）把续聊当功能性目标；但后端 `db.enabled` 默认 `false`（config.yaml 已确认），且 `chat_service` 仅当 `db is not None and req.user_id is not None` 才返回 `conversation_id`；而当前 `App.tsx` **完全不发送 `user_id`**。默认状态下该功能静默不可达，演示开箱看不到历史。 | 评审/演示误以为"核心功能缺工"；实际是配置+字段未就绪。 | 二选一并在文档明示：① 将目标 3 降级为"可选/进阶能力"，验收标注"仅当 `db.enabled=true` 且请求带 `user_id` 时生效"；② 或联调验收强制要求启用 db 并 `user_id=1`。**无论哪种，实现时 `useChat` hook 必须默认带 `user_id: 1`**，否则静默无续聊（建议在技术文档 §7 加粗强调）。 |
| G3 | P1 | **默认场景语义未锁定，且前端默认发送 Banking 会绕过后端路由**。后端 `run(scene=None)` 由 **Coordinator 经一次 LLM 调用判定场景**，解析失败才回退 `"Banking"`；而当前 `App.tsx` 与目标 hook 默认 `scene="Banking"` 且**总是发送 scene**，等于永远直连 Banking 专家、Coordinator 路由在 UI 上永不被触发。需求 §目标2 写"未选时由后端按默认（Banking 或 Coordinator 路由）处理"表述模糊，且未揭示此权衡。 | 演示无法体现"意图识别/路由"子能力；与"验证路由→RAG→专家"的目标自相矛盾。 | 在契约 §4 与需求 §目标2 明确二选一的产品决策：a) **默认自动路由**（前端不传 scene，让 Coordinator 判定，最贴合"验证路由"目标）；或 b) **默认 Banking**（前端始终发送，省一次路由调用）。当前代码倾向 b，但文档应写明并说明 Coordinator 路由需"不传 scene"才触发。 |
| G4 | P2 | **"目标设计"与"实现现状"边界不清，易被误读为部分已落地**。两份文档通篇是目标架构（`api/client.ts`、`hooks/useChat.ts`、8 个组件），但 `src/` 当前仅 `App.tsx`/`main.tsx`/`index.css`/`vite-env.d.ts`，**全部未实现**。需求文档顶部标了"草稿待评审"，但缺少一张"已实现 vs 待实现"的总览，读者易把目标当现状。 | 实现排期与验收口径混乱；评审难判断"完成"标准。 | 在需求文档 §2 与 技术文档 §3 顶部各加一张**实现状态总览表**：已实现（脚手架 main/App/index.css/vite/tsconfig/package）+ 待实现（client/hook/8 组件），并使"待实现"项与 §6/§10 验收清单一一对应。 |

| S5 | 生产代理给出示例 | 仅 dev 有 proxy。建议在 `Dockerfile`/docker-compose 中给出生产前端请求 `/api` 的指向（同网服务名或环境变量 `VITE_API_BASE`），避免生产跨域。 |
| S6 | 契约一致性 ✅（无需改） | `compliance_notes`/`risk_flags` 后端为必填 `List[str]`（default 空数组），前端"为空隐藏"逻辑正确；`AnalyzeResponse.expression` 必填（默认 `""`）、`intent` 可选（`None`），与 TS 类型吻合。一致性已验证，保留。 |
| S7 | 健康检查路径 ✅（无需改） | 需求 §4.1 与技术 §10 均写 `/api/health`，与后端 `GET /api/health` 经 proxy 一致，保留（G1 决策反转后统一 `/api` 前缀）。 |
