## 1. 背景与目标

### 架构定位（四层关系，权威定义）

本项目后端按职责切为四层，04 是其中 02 的进一步优化，而非独立并列模块：

- **01 模型接口**：只做模型服务——提供文本生成的统一调用（`get_model()` + api/local 双模式），并扩展提供嵌入模型服务（`get_embedder()` + `emb.mode`，供 04 的向量化调用）。
- **02 基础多智能体架构**：搭好多智能体骨架与编排（`app/agent.run()`、`prompts/*.txt`、`retrieval.py`、`tools.py`、9 角色拓扑 + AgentScope 桥接）。
- **03 传统后端基础层**：只做后端基础（DB / Services / Routers / Main），消费 02 的 `run()`，不重写提示词与检索。
- **04 = 02 的进一步优化**：在 02 已搭好的拓扑之上，把"内容层"填实——**交付 5 个领域专家 + 审核（合规）+ 风控 + 信息查询智能体**这 8 个具体角色能力（协调者 Coordinator 由 02 基础架构提供，04 仅小修其提示词）。04 不新建框架层，只充实 02 的提示词与 RAG/外联内容。

02 已经把 multi-agent 拓扑搭成"1 协调者 + 5 领域专家 + 3 支撑角色"的骨架，但**各角色内部"说什么、知识从哪来"还是空白**。04 的目标是把这块填实：

- **目标 1（专家提示词）**：为 5 个领域专家（Banking / Securities / Insurance / Trust / MutualFunds）设计专用 system prompt——明确角色定位、职责边界、不归我管的相邻领域、作答规范、风险提示义务。
- **目标 2（审核/风控提示词）**：为审核（合规）智能体与风控（风险）智能体设计专用提示词——定义各自的核查清单、输出格式、建议式结论（不阻断主链路）。
- **目标 3（RAG 本地文档）**：详细设计"本地文档解析→提取→切分→向量化→检索"的端到端管线，作为领域专家与审核/风控的本地知识来源（详细优先级最高）。该管线的检索能力由独立的**信息查询智能体**承载。
- **目标 4（信息查询智能体）**：将 RAG 设立为**独立的"信息查询智能体"**（区别于 5 领域专家与审核/风控）。它同时具备两种能力：① 本地文档检索（RAG）；② 联网新闻检索与总结。从外部获取最新市场/政策/产品动态，总结后喂给专家与审核/风控，补足本地知识时效缺口。

> **工具立场（评审 G2 闭环）**：04 **不重新定义工具契约、不新建工具名**。工具由 02 框架统一承载（02 已落地 `lookup_knowledge` / `retrieve_documents` / `check_compliance` / `assess_risk`），04 仅在 §4 就工具能力改进给出**建议**，不在本期定接口。

## 3. 角色与提示词设计要求

### 3.1 五大领域专家（作答主体）
每个专家提示词须包含以下固定模块，差异体现在"领域知识"与"边界"：

| 模块 | 内容 |
|---|---|
| 角色定位 | 你是「XX 领域」金融问答专家，服务对象为普通投资者/消费者 |
| 核心职责 | 该领域常见问题的专业、准确作答（列举 3–5 类典型问题） |
| 职责边界（不归我管） | 明确列出相邻领域由谁负责，避免路由重叠（如"买基金"归 MutualFunds，不归 Banking/Securities） |
| 作答规范 | 先结论后解释；用通俗语言；涉及金额/费率给计算口径；不承诺收益 |
| 风险提示义务 | 强制提示该领域最高频风险（如保险现金价值、信托门槛、基金不保本） |
| 工具使用指令 | 概念性描述"何时需要检索/计算/联网"，具体工具由 02 框架提供，04 不绑定工具名 |
| 引用要求 | 结论需标注来源类型（本地条例 / 新闻 / 通用知识），不杜撰出处 |

5 个专家的领域侧重点（详细）：
- **Banking（银行）**：存款、贷款（房贷/经营贷/消费贷/LPR）、银行理财净值化、银行卡费率、存款保险 50 万、现金管理；边界：理财 vs 公募基金、结构性存款 vs 保险。
- **Securities（证券）**：A 股交易规则（T+1、涨跌停、板块门槛）、可转债、两融、打新、退市/ST、交易税费、投资者适当性；边界：场内 vs 场外、证券账户买基金归 MutualFunds。
- **Insurance（保险）**：人寿/健康/意外/财产险，重疾 vs 医疗、年金/增额寿、车险、现金价值/犹豫期/退保、健康告知与理赔；边界：保障型 vs 理财型、保险 vs 信托传承。
- **Trust（信托）**：集合资金信托、家族信托（门槛通常 1000 万）、保险金信托、信托三分类、打破刚兑净值化；边界：信托 vs 基金/理财、服务属性强。
- **MutualFunds（公募基金）**：货币/债券/股票/混合、ETF/LOF、指数 vs 主动、申赎/管理/托管费、分红、定投、养老 FOF、个人养老金；边界：基金 vs 银行理财、场内基金归 Securities 交易规则部分。

### 3.2 审核（合规）智能体
- 定位：答案产出后的**合规把关者**，审"合不合规"。
- 核查清单（建议式，不阻断）：投资者适当性表述、是否出现"保本保收益/承诺收益"、风险提示是否到位、是否存在误导性表述、是否越界提供具体投资建议。
- 输出：合规提示列表 `compliance_notes`（每条含：问题点、对应法规/规范、修改建议），严重级别（提示 / 严重）。**对外仍为 `list[str]`**（与 02/03 契约一致，见评审 G5：02 内部以 Msg 结构化后拍平输出）。
- 工具：调用合规/监管类检索工具（由 02 框架提供，04 不重定义）。

### 3.3 风控（风险）智能体
- 定位：答案产出后的**风险把关者**，审"安不安全"。
- 核查清单（建议式，不阻断）：推荐产品风险等级与用户风险画像是否匹配、是否存在高危操作预警（如杠杆、集中持仓）、是否诱导非理性交易。
- 输出：风险标记列表 `risk_flags`（每条含：风险点、等级、处置建议）。**对外仍为 `list[str]`**（同上，评审 G5）。
- 工具：调用风险画像 / 产品风险评级类检索工具（由 02 框架提供，04 不重定义）。

### 3.4 信息查询智能体（独立角色：本地 RAG + 联网新闻）
- 定位：**独立的智能体**（区别于 5 领域专家与审核/风控），作为全链路的知识供给方，同时具备**本地文档检索（RAG）**与**联网新闻检索总结**双能力。
- 本地文档检索：从本地知识库（监管条文、产品库、内部资料）检索依据，喂给专家/审核/风控。
- 联网新闻：针对用户问题实时检索相关市场/政策/产品新闻，去重、时效过滤、可信度评估后总结，补足本地知识时效。
- 提示词重点：检索查询的构建方法、何时用本地 vs 联网、总结时标注来源与时间、无结果时如实声明。

## 4. 工具设计立场（04 不定义契约，仅提建议）

**立场**：工具接口由 02 框架统一承载（02 已落地 `lookup_knowledge` / `retrieve_documents` / `check_compliance` / `assess_risk`，经 `_ROLE_TOOLS` / `build_toolkit(role)` 注册给角色）。04 作为"内容层"设计文档，**不重新定义工具契约、不新建工具名**，避免与 02 既有实现打架（评审 G2 闭环）。

以下为 04 就工具能力给出的【改进建议】（非本期落地，供后续需求参考）：
- **检索统一化**：建议将本地检索统一收口到「信息查询智能体」（02 的 `rag` 角色），专家不再各自直挂检索工具，由该角色供给本地知识 + 联网新闻，降低重复与时效差。
- **计算/对比能力**：建议为专家补充利率/IRR/保费计算与多产品横向对比类计算工具，减少模型幻觉式计算。
- **合规/风控检索**：建议为审核、风控补充监管条文 / 合规规则 / 风险画像类检索工具，提升核查依据的可追溯性。
- **联网新闻**：建议信息查询智能体具备联网新闻检索与总结能力（02 当前 `retrieve_documents` 仅本地占位），补足本地知识时效缺口。

> 上述建议若落地，应在 02 的 `tools.py` / `build_toolkit` 中扩展，并由 02 评审/编码，04 仅描述期望能力。

## 5. RAG 本地文档管线（详细设计要求）

> 本节为 04 重点，需详细。定位：把本地金融文档（监管文件、产品说明书、内部资料）变成可检索的知识，供专家/审核/风控引用。实现落到 02 已落地的 `app/agent/retrieval.py`（扩展，不新建包，见评审 G1）。

### 5.1 文档接入
- 支持格式：PDF、DOCX、TXT、Markdown、HTML、CSV/Excel（产品表）。
- 来源分类：监管条文（银保监会/证监会/央行发文）、产品文档（理财/基金/保险条款）、内部知识库。
- 元数据：文档类型、发布机构、生效日期、适用领域标签（银行/证券/保险/信托/基金）、版本。

### 5.2 解析与结构化（重点）
- 文本提取：保留标题层级、段落、列表结构；PDF 优先提取文本层，扫描件走 OCR（排期）。
- 表格处理：金融产品表（费率、收益、风险等级）单独识别为结构化行，避免被切散。
- 结构保留：以标题为单位组织层级，便于"按章节检索"与"出处定位"。
- 字段提取：从文档抽取结构化元数据（产品名、风险等级、费率、生效日），用于过滤检索。

### 5.3 切分策略
- 默认按语义/标题切分，块大小与重叠可控；表格块整体保留。
- 长文档按小节聚合，短段落合并，避免碎片化与跨段割裂。

### 5.4 向量化
- **嵌入模型由 01 扩展提供**：01 新增 `get_embedder()` 与 `emb.mode` 配置（api/local 双模式），04 调用其完成向量化，不直接管理嵌入模型。详见技术文档 §12「01 待改清单」。
- 维度与语言：中文金融语料适配，支持领域微调（排期）。
- 混合检索：向量语义 + 关键词（BM25）混合，提升法条/产品名命中。

### 5.5 存储
- 本地向量库选型（设计）：轻量（SQLite + 向量扩展）或专用向量库二选一，支持按元数据过滤。

### 5.6 检索与重排
- 查询改写：结合用户问题与 `scene` 生成检索 query。
- 召回：top-k 候选，元数据过滤（领域/时间）。
- 重排：相关度重排，优先权威源（监管 > 产品 > 内部）。
- 可追溯：返回片段附出处（文档名 + 章节 + 生效日），供提示词引用。

### 5.7 合规与可追溯
- 检索结果不可篡改来源；回答标注"依据本地 XX 文档（生效日）"。
- 无命中时工具返回空，提示词强制"不编造、显式声明"。

## 6. 外联新闻管线（设计要求）

- 触发：信息查询智能体（或经协调者）判定需要"时效性信息"（政策新规、市场波动、产品停售）时，由该智能体调用联网新闻检索能力。
- 查询构建：由用户问题 + `scene` + 时间窗生成检索式。
- 检索与过滤：多源检索 → 去重 → 时间过滤（默认近 N 天/月）→ 可信源优先（官方/主流财经媒体）。
- 总结：聚合要点，标注来源与发布时间，剔除广告与低可信内容。
- 输出：外部信息摘要，作为专家补充依据；无结果时如实声明。
