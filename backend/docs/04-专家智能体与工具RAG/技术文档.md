## 1. 概述

### 架构定位（四层关系，权威定义）

本项目后端按职责切为四层，04 是其中 **02 的进一步优化**，不是独立并列模块：

- **01 模型接口**：只做模型服务——文本生成统一调用（`get_model()` + api/local 双模式）+ 扩展嵌入模型服务（`get_embedder()` + `emb.mode`，供 04 向量化调用）。
- **02 基础多智能体架构**：搭好多智能体骨架与编排（`app/agent.run()`、`prompts/*.txt`、`retrieval.py`、`tools.py`、9 角色拓扑 + AgentScope 桥接）。
- **03 传统后端基础层**：只做后端基础（DB / Services / Routers / Main），消费 02 的 `run()`，不重写提示词与检索。
- **04 = 02 的进一步优化**：在 02 已搭好的拓扑之上把"内容层"填实——**交付 5 个领域专家 + 审核（合规）+ 风控 + 信息查询智能体**这 8 个具体角色能力（协调者 Coordinator 由 02 基础架构提供，04 仅小修其提示词）。04 不新建框架层，只充实 02 的提示词与 RAG/外联内容。

04 是 02 的进一步优化，在 02 的拓扑骨架之上填充各角色的"内容层"：提示词、本地 RAG 与外联新闻。所有产物位于 `app/agent/`，不触及 03 的 `services/routes/db`。底层文本生成能力复用 01（`get_model()` + api/local 双模式），**嵌入模型由 01 扩展**（`get_embedder()` + `emb.mode`，见 §12）；工具由 02 框架统一承载，04 不重定义（见 §4）。

设计原则：
- **提示词即设计**：本文给出各角色提示词的结构模板与关键字段，编码阶段按模板落地到 02 已有的 `app/agent/prompts/*.txt`。
- **RAG 详尽**：本地文档解析→提取→切分→向量化→存储→检索→可追溯，逐环节给设计，实现落到 02 已有的 `app/agent/retrieval.py`（扩展，不新建包）。
- **工具不重定义**：04 不新建工具名、不定契约；工具能力改进仅以建议形式给出（§4）。

## 3. 提示词设计（结构模板）

### 3.1 专家提示词通用模板

每个专家提示词由以下段落组成（差异在【领域知识】与【职责边界】）：

```
【角色】
你是「{领域}」金融问答专家，面向普通投资者/消费者，用通俗、准确、合规的语言作答。

【核心职责】
负责 {领域} 相关问题，典型包括：{3–5 类典型问题}。

【职责边界（不归我管）】
以下由其他专家负责，识别到应礼貌转交或由协调者路由：
- {相邻领域 A} → 由 {XX} 专家负责
- {相邻领域 B} → 由 {YY} 专家负责

【作答规范】
1. 先给结论，再解释；复杂计算给口径。
2. 不承诺收益、不保证本金安全。
3. 涉及金额/费率/期限须注明假设与口径。
4. 无本地/新闻依据时，显式声明"无法确认/不编造"。

【风险提示义务】
强制提示本领域的{最高频风险 1–3 条}，例如：{风险提示}。

【工具使用】
- 需要权威依据 → 调用本地知识检索工具（由 02 框架提供）
- 需要时效信息（新规/市场） → 调用联网新闻检索工具（由 02 框架提供）
- 需要计算 → 调用计算工具（由 02 框架提供，04 不绑定具体名）
- 引用须标注来源类型：本地条例 / 新闻 / 通用知识

【引用要求】
每条关键结论标注来源；不得杜撰出处；无来源时声明"基于通用金融常识"。
```

### 3.2 各领域差异要点（设计要点，编码落地到各自 .txt）

- **Banking**：核心职责=存款/贷款(LPR/房贷/经营贷)/银行理财净值化/银行卡费率/存款保险50万。边界=银行理财 ≠ 公募基金（归 Funds）、结构性存款 ≠ 保险。风险=理财不刚兑、提前支取损失、LPR 浮动。
- **Securities**：核心职责=A股规则(T+1/涨跌停/板块门槛)/可转债/两融/打新/退市ST/税费/适当性。边界=证券账户买基金归 Funds，场内交易规则归 Securities。风险=涨跌停/退市/杠杆两融/适当性不匹配。
- **Insurance**：核心职责=寿/健/意/财险、重疾vs医疗、年金/增额寿、车险、现金价值/犹豫期/退保/健康告知理赔。边界=保障型≠理财型、保险传承≠信托。风险=现金价值损失、健康告知不实致拒赔、理财型流动性差。
- **Trust**：核心职责=集合资金信托/家族信托(门槛~1000万)/保险金信托/信托三分类/打破刚兑净值化。边界=信托≠基金理财、服务属性强。风险=高门槛、不刚兑、流动性差、识别"伪信托"。
- **MutualFunds**：核心职责=货币/债券/股票/混合、ETF/LOF、指数vs主动、申赎/管理/托管费、分红、定投、养老FOF/个人养老金。边界=基金≠银行理财、场内基金交易规则归 Securities。风险=不保本、净值波动、费率侵蚀、定投非稳赚。

### 3.3 审核（合规）提示词（review.txt）

```
【角色】你是金融合规审核员，对已生成的回答做合规核查，给出建议（不阻断）。
【核查清单】
1. 投资者适当性：是否对不适格人群做了不匹配建议。
2. 收益表述：是否出现"保本/保收益/承诺收益/稳赚"等违规表述。
3. 风险提示：是否缺失该领域强制风险提示。
4. 误导性：是否存在夸大、片面、歧义表述。
5. 越界：是否提供了本应由持牌顾问给出的具体投资建议。
【输出格式】逐条给出 compliance_notes（对外 list[str]；02 内部以 Msg 结构化后拍平）：
  - 级别：提示 | 严重
  - 问题点：{描述}
  - 依据：{法规/规范名}
  - 建议：{修改方向}
【工具】调用合规/监管类检索工具（由 02 框架提供，04 不重定义）
【原则】只审不改写；严重级问题须明确提示；无问题返回空列表。
```

### 3.4 风控（风险）提示词（risk.txt）

```
【角色】你是金融风控员，对已生成回答做风险核查，给出标记（不阻断）。
【核查清单】
1. 风险匹配：推荐产品风险等级与用户风险画像是否匹配。
2. 高危操作：是否诱导杠杆、集中持仓、频繁交易等非理性行为。
3. 流动性：是否提示了锁定期/赎回限制。
4. 集中度：是否提示单一产品/领域过度集中。
【输出格式】逐条给出 risk_flags（对外 list[str]；02 内部以 Msg 结构化后拍平）：
  - 等级：低 | 中 | 高
  - 风险点：{描述}
  - 处置建议：{提示用户注意 / 建议分散等}
【工具】调用风险画像 / 产品风险评级类检索工具（由 02 框架提供，04 不重定义）
【原则】只标记不拦截；高风险须明确预警；无问题返回空列表。
```

### 3.5 信息查询智能体提示词（rag.txt，独立角色）

```
【角色】你是一个**独立的信息查询智能体**，区别于领域专家与审核/风控；为它们提供本地知识依据与联网新闻总结。
【本地检索】调用本地知识检索工具：按查询+领域过滤，返回片段须带出处与生效日。
【联网新闻】调用联网新闻检索工具：构建查询(问题+scene+时间窗)，检索→去重→时效过滤→可信源优先→总结要点，标注来源与时间。
【何时用哪种】
- 法规/产品常识/内部资料 → 本地
- 新规/市场动态/产品停售/近期事件 → 联网
【总结要求】聚合不罗列；标注来源与发布时间；剔除广告与低可信；无结果如实声明。
【原则】不编造出处；本地无命中可转联网；联网无果如实声明。
```

## 5. RAG 本地文档管线（详细设计）

> 本节为 04 重点，逐环节给设计。实现落到 02 已落地的 `app/agent/retrieval.py`（扩展，不新建包，见评审 G1）。定位：把本地金融文档转为可检索、可追溯的知识。

### 5.1 文档接入（扩展 retrieval.py 的 ingest 设计）
- **格式支持**：PDF（文本层优先）、DOCX、TXT、Markdown、HTML、CSV/XLSX（产品表）。
- **来源分类**：监管条文（央行/证监会/银保监会发文）、产品文档（理财/基金/保险条款）、内部知识库。
- **元数据 schema**：`doc_id`, `title`, `doc_type`, `agency`, `effective_date`, `domain_tags[]`, `version`, `source_path`。
- **接入方式**：目录扫描 / 上传触发；增量更新靠 `doc_id` + `version` 去重。

### 5.2 解析与结构化（扩展 retrieval.py 的 parse 设计，重点）
- **文本提取**：PDF 优先提取文本层；扫描件 OCR 排期。保留标题层级（H1–H4）、段落、列表。
- **表格处理（关键）**：金融产品表（费率、收益、风险等级、门槛）用表格识别单独抽出，转为结构化行（避免被文本切分打散），每行带表名与页码。
- **结构保留**：以标题为骨架组织层级树，支持"按章节检索"与"出处定位到章节"。
- **字段提取**：从文档抽取结构化元数据——产品名、风险等级（R1–R5）、费率、收益区间、生效日——写入 `domain_tags` 与可过滤字段，供检索过滤。
- **清洗**：去页眉页脚、去重空白、统一全角半角、归一化日期。

### 5.3 切分策略（chunking 设计）
- **默认**：按标题/语义边界切分，块大小（如 300–800 字）与重叠（10–15%）可配。
- **表格块**：整表作为一个 chunk，附加列头，避免跨块断裂。
- **长文档**：按小节聚合，短段合并；保留块内"父标题"上下文，提升检索召回的相关度。
- **领域适配**：监管条文按"条/款"切，产品文档按"条款章节"切。

### 5.4 向量化（embed 设计，嵌入由 01 扩展提供）
- **嵌入模型（由 01 扩展提供）**：01 新增 `get_embedder()` 与 `emb.mode` 配置（api/local 双模式，复用 01 的双模式切换）；本地轻量嵌入（如 bge-small-zh）或 API 嵌入二选一，04 调用 `get_embedder()` 完成向量化，不直接管理嵌入模型。详见 §12「01 待改清单」。
- **语言与维度**：中文金融语料优先；维度固定（如 768/1024）。
- **混合检索**：向量语义召回 + 关键词 BM25 召回，加权融合，提升法条编号、产品名等精确命中。
- **领域微调**：嵌入模型领域微调排期（可选）。

### 5.5 存储（store 设计）
- **选型（设计二选一）**：轻量方案 = SQLite + 向量扩展（如 sqlite-vec）；或专用向量库（如 Chroma/FAISS）。
- **表/集合**：`documents`（元数据）、`chunks`（文本+向量+父标题+领域标签）、`embeddings`（向量列）。
- **过滤索引**：按 `domain_tags`、`effective_date`、`doc_type` 建索引，支撑元数据过滤检索。

### 5.6 检索与重排（search 设计）
- **查询改写**：结合用户问题 + `scene` + 时间窗，生成 1–3 个检索 query（含同义/上下位）。
- **召回**：向量 top-k + BM25 top-k，融合去重，得候选集。
- **过滤**：按 `domain` / `effective_date`（优先现行有效）过滤。
- **重排**：相关度重排，权威源加权（监管 > 产品 > 内部）；可选 cross-encoder 重排（排期）。
- **输出**：`passages[]` 含 `text, source, chapter, effective_date, score`，供提示词引用。

### 5.7 合规与可追溯（贯穿）
- 检索结果带不可篡改出处；回答须标注"依据本地《XX》（生效日）"。
- 无命中返回空，提示词强制"不编造、显式声明"。
- 全链路保留 `doc_id → chunk → 出处` 映射，支撑后续 `agent_trace` 审计。

## 6. 外联新闻管线（news 设计）

- **触发条件**：信息查询智能体判定需时效信息（新规、市场波动、产品停售、近期事件）时调用联网新闻检索能力。
- **查询构建**：由"用户问题 + scene + 时间窗（默认近 N 天/月）"生成检索式，必要时多轮改写。
- **检索与过滤**：多源检索 → 去重 → 时间过滤 → 可信源优先（官方发布/主流财经媒体，降权自媒体与广告）。
- **总结**：聚合要点（非罗列），标注来源与发布时间；剔除低可信与广告内容。
- **输出**：新闻摘要（summary, source, published_at, url, credibility），作为专家补充依据。
- **无结果**：如实声明"未检索到相关近期信息"，不编造。

## 12. 01 待修改清单（嵌入模型，04 对 01 的硬依赖，已闭环为"01 扩展"）

> 评审 G4 闭环：用户确认**嵌入模型由 01 扩展，04 调用**。04 §5.4 的向量化依赖 01 提供 embedding 能力，当前 01 仅有文本生成模型（`get_model()` + `generate()`），无 embedding 接口、无 `emb.mode` 配置。本节是 04 对上游 01 的**明确修改要求**，须在 04 进入编码（RAG 向量化）前由 01 完成。

### 12.1 01 新增嵌入接口

- 01 新增 `get_embedder()`（或 `get_model(role="embed")`），返回具备 `embed(texts: list[str]) -> list[list[float]]` 能力的嵌入对象，与 `get_model()` 平级。
- 复用 01 的 api/local 双模式：本地轻量嵌入（如 bge-small-zh，进程内）或 API 嵌入（如 OpenAI embedding）二选一。

### 12.2 config 新增 `emb` 段

在 `config/config.yaml` 的 `model` 之外新增顶层 `emb` 段（或在 `model` 下加 `embed` 子段），形态参考 `model`：

```yaml
emb:
  mode: api                  # api | local
  api:
    model_type: openai_embedding
    model_name: text-embedding-3-small
    api_key: ${OPENAI_API_KEY}
    base_url: https://api.openai.com/v1
  local:
    model_type: openai_embedding
    model_name: bge-small-zh
    api_key: EMPTY
    base_url: http://localhost:8001/v1
```

### 12.3 01 待改小结

1. 01 新增 `get_embedder()`（api/local 双模式）与 `emb` 配置段。
2. 01 提供嵌入对象的 `embed()` 方法，供 04 的 `retrieval.py` 调用完成向量化。
3. 上述完成后，04 的 RAG 向量化（`retrieval.embed`）即可接线 01，无需 04 自管嵌入模型。
