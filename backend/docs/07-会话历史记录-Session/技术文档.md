## 1. 概述与架构定位

### 1.1 在本项目中的层位
07 位于**03 后端基础层之上、与 06 知识库并列**的「可追溯 / 可复盘」横切层：

```
用户请求
  │
  ▼
03 路由/服务（chat_service.async chat）
  │   ├─ 聊天记录（用户/助手消息 + 多专家执行轨迹）全部自包含于 03 `conversations.data`（JSON 单字段）  ← 03 既有表，07 收口进同一行
  │   └─ 旁路 hook（无侵入包裹 chat_service.chat）──► 07 store 把 trace 挂到该轮助手消息  ← 07 不再独立建表
  ▼
02 run() 多 Agent 流水线（Coordinator→RAG→专家→审核→风控）
  │   └─ RAG 检索 ──► 06 DuckDB 向量检索（同主库）        ← 06 既有（07 可选语义检索复用）
  ▼
AgentResult（reply + compliance_notes + risk_flags + 结构化字段）
  │   └─ get_session_for_review ──► raf 总结智能体（复盘）  ← 07 与 raf 协作（类比 06 喂 raf）
```

- **03 管「单表会话记录」**：`conversations` 一行 = 一次会话；`data`(JSON) 字段自包含用户/助手消息 + 多专家轨迹（`trace`）。user/assistant 两条消息由 `chat_service._persist` 追加进 `data`；07 的 trace 由 hook 挂到对应助手消息。
- **07 管「全链路轨迹 + 历史检索/复盘」**：作为 03 主库之上的常规 service 层（落库 / 查询 / 检索 / 导出）读写同一 `conversations.data`，view 层（`SessionDetail` / `TurnDetail` / `SearchHit` 等聚合视图）组织结果呈现给 API / 前端，**不另开库、不分叉、不再独立建表**。
- **06 向量检索已不再用于 07**：`history.semantic_search` 当前未启用，`semantic_search` 直接返回 `[]`；语义检索的原 `history_embeddings` 表已废弃（不再写入，避免跨库分叉）。

### 1.2 为什么这样定位（相对 03 主消息流、06 向量库）
| 方案 | 取舍 | 结论 |
|---|---|---|
| 在 03 内直接加细粒度 trace 表 | 03 已稳定，混入 trace 会膨胀其职责（DB 层 ≠ 可追溯层） | 07 独立层，复用 03 表，不污染 03 |
| 复用 06 DuckDB 存历史 | 06 是向量检索库，非结构化历史审计库；强行塞进 06 会混淆职责 | 07 的轨迹表建在主库，语义检索才委托 06 |
| 独立服务（如 Elasticsearch）或另开 DB 分叉 | 引入进程外依赖 / 与主库分叉，违背「统一主库、常规分层」原则 | 07 表与主库同实例，走 service 层，不另开库 |

07 与 03/06 同属「嵌入式单文件、进程内」范式，部署形态一致，迁移与运维成本低。

## 3. Schema 设计与写入策略

### 3.1 表结构（SQLite）
**单表收口（2026-08-07 落地）**：会话记录全部收口为 03 的 `conversations` 单表，**一次会话一行**；聊天正文与多专家执行轨迹自包含于 `data`(JSON) 字段，不再拆分 `messages` / `session_*` / `history_embeddings` 等表。详见 `app/db/schema/sqlite/main.sql` 的 `conversations` DDL。要点：

- `conversations.data`：`{"messages":[{role,content,scene,created_at,("trace":{...})}]}`；助手消息带 `trace`（run_id/turn_id/created_at/model/status/duration_ms/total_tokens/final_result/events 事件树）。
- 旧表（`messages` / `session_meta` / `session_traces` / `trace_events` / `history_embeddings`）已删除，**代码中已无这些表的读写**；单表收口后无需聚合迁移（`_migrate_legacy` 已移除）。
- `user_id` / `scene` / `title` / `created_at` / `updated_at` 仍为 `conversations` 列（会话头），便于索引与权限过滤。

### 3.2 写入策略（控存储）
- **主消息流**：直接写入 `conversations.data` 的 `messages` 数组（07 不另建消息表）。
- **中间步骤**：存**摘要**（`summary_in` / `summary_out`）+ 必要结构化字段（`meta_json`），不存全文，降低敏感面与体积。
- **RAG 命中**：仅存溯源引用 + 分数（复用 06 `Passage` 字段：`doc_id/title/agency/domain/chapter/effective_date/version/score`），不重复存原文块。
- **错误**：存 `exc_type` / `message` / `traceback_summary`（前 N 行），不全量栈。

### 3.3 维度与一致性
- `history_embeddings.dim` 已废弃：`semantic_search` 当前返回 `[]`，不再写入向量（避免跨库分叉）。
- `init_history_db()` 幂等：执行 `app/db/schema/sqlite/main.sql` 确保 `conversations` 表存在（无 07 独立建表、无旧表聚合迁移）；与 03 `init_db()` 同时由 lifespan 调用，`history.enabled` 门控。

## 4. 轨迹采集集成点（hook 无侵入）

### 4.1 采集目标
把「每次和 AI 聊了什么」从 03 的「两条主消息」扩展为「一次完整、可回放的交互记录」。采集点：

1. **run() 入口/出口**：生成 `run_id`、记录 `scene` / `model` / `duration_ms` / `total_tokens` / `final_result`。
2. **02 流水线 step 钩子（演进）**：02 在 Coordinator→RAG→专家→审核→风控每个关键节点 emit 一个 step 事件（含 agent 名、输入/输出摘要、token、耗时）；07 `collect.py` 把它们转成 `trace` 事件（挂到该轮助手消息的 `data.messages[].trace`）。
3. **tool 调用**：`lookup_knowledge` / `retrieve_documents` 的调用与结果（命中数、命中文档）作为 `tool_call` / `rag_hit` 事件。
4. **错误**：任一节点抛 `ModelInvokeError` 或其他异常，记 `error` 事件，`status=error`。

### 4.2 集成方式（无侵入、旁路、降级）
- **装饰器/上下文管理器**：`app/db/history/hooks.py` 的 `install_history_tracing()` 把 `chat_service.chat` 替换为 `traced_chat`（无侵入包裹）。伪代码（精简）：

```python
# app/db/history/hooks.py
def traced_chat(req, db, **kwargs):  # install_history_tracing() 包裹 chat_service.chat
                  get_conv=lambda kw: kw.get("conversation_id")):
    def deco(fn):
        @wraps(fn)
        async def wrapper(*a, **kw):
            if not _store or not _store.enabled:
                return await fn(*a, **kw)          # 总开关关 -> 完全旁路
            run_id = uuid4().hex
            t0 = time.monotonic()
            try:
                result = await fn(*a, **kw)
                status, err = "ok", None
            except Exception as e:
                status, err = "error", e
                raise                                # 主链路异常照常抛出
            finally:
                # 旁路异步写入，不阻塞返回
                _write_trace_async(run_id, get_user(kw), get_conv(kw),
                                   result, err, t0)
            return result
        return wrapper
    return deco
```

- **旁路异步写入**：`_write_trace_async` 把 trace 构造与 DB 写入提交到线程/任务，主协程立即 `return result`；写入失败按 `fail_mode` 处理（`silent` 丢弃 / `local` 落兜底文件）。
- **降级契约**：`history.enabled=false` 或 DB 不可用时，`get_history_store()` 返回 `NoopHistoryStore`，所有方法为空操作，主链路 `reply` 不受影响（与 03 `db.enabled` 短路一致）。
- **与 03 协同**：03 `chat_service._persist` 先把 user/assistant 两条消息追加进 `conversations.data`；07 hook 在外层异步把 `trace` 挂到该轮助手消息（按回复内容精确匹配，否则取最后一个无 trace 的助手消息），二者同落 `conversations.data`，**绝不重复建表**。

### 4.3 演进路径（与 02 协作门禁）
- **首版（02 未暴露 step 钩子）**：`trace` 仅含「头 + user/assistant 主消息事件」，`record_traces` 退化为记录主消息级事件；满足「记录每次聊了什么」的基本可追溯。
- **增强版（02 扩展 step 钩子后）**：02 在每个 agent 节点 emit step，`collect.py` 补全 `tool_call` / `rag_hit` / `review` / `risk` / `error` 细粒度事件，达成完整回放。
- **现已落地（v2 已实现）**：02 的 `run()` 通过 `AgentResult.agent_trace`（路由 / RAG / 专家意见 / 合成 / 回写）emit 步骤；07 `hooks.traced_chat` 将其转为 `TraceEvent` 并经由 `collect.build_events(extra_events=...)` 构造为 `trace` dict，挂到同一 `conversation_id` 助手消息的 `data.messages[].trace`。实测细粒度事件可达 `expert_opinion`（各专家意见）/ `synthesize`（圆桌合成）/ `revise`（回写环改写）等，完整回放「专家聊天记录」已具备（评审 B1 闭环）。
- 该门禁在需求文档 §9.1 记录；07 接口预留 `events: list[TraceEvent]` 入参，02 就绪即填。

## 5. 历史检索

### 5.1 关键词检索（keyword_search）
- 在 `conversations.data.messages[].content` 与 `trace.events[].summary_in/out` / `meta_json` 上做匹配（单表 JSON 内检索）。
- 实现：`sqlite` 原生 `LIKE` 或启用 SQLite FTS5（`CREATE VIRTUAL TABLE ... USING fts5`）做 BM25；带 `user_id` / `scene` / `start` / `end` 过滤。
- 返回 `SearchHit`：`conversation_id` / `turn_id` / `event_id` / `snippet` / `score` / `created_at`。

### 5.2 可选语义检索（semantic_search，复用 06）
- 开关 `history.semantic_search=true` 时启用。
- **当前未启用**：`history.semantic_search=false`，`semantic_search()` 直接返回 `[]`（占位，避免跨库分叉）。若未来启用，将按 §5.2 原方案经 06 向量检索，但写入目标待定（不引入独立 `history_embeddings` 分叉表）。
- 不引入独立向量服务，复用 06 现有能力（与 06 §1.2 选型一致）。

### 5.3 检索结果去隐私
- 检索返回片段前先走 `redact.py` 脱敏；非本人（且非管理员）查询返回空（权限边界）。

## 6. 回放与导出

### 6.1 回放（get_session / get_turn）
- `get_session`：读 `conversations.data.messages`（按时间序）+ 各助手消息的 `trace` 树，组装 `SessionDetail`（可前端树状展示每次对话的完整链路）。
- `get_turn`：取单轮（一次 user→assistant）助手消息的 `trace.events` 子树，呈现「输入 → Coordinator 路由 → RAG 检索 → 专家作答 → 审核 → 风控 → 最终回复」。

### 6.2 导出（export_session）
- `fmt="md"`：渲染为复盘文档——会话元信息（场景/时间/模型/token）+ 主消息流 + 每轮 trace（agent 步骤、tool、RAG 命中溯源、审核/风控、耗时）。
- `fmt="json"`：原始结构化（便于二次处理/审计）。

### 6.3 复盘上下文（get_session_for_review，供 raf）
- 把一次会话组织成带溯源的结构化上下文（类比 06 `format_passages`）：聚合「用户诉求 + 各 agent 结论 + RAG 依据 + 审核/风控」，输出文本交给 **raf 总结智能体**生成复盘摘要/改进建议。
- 07 与 raf 职责边界：07 只「记录 + 组织成结构化上下文」；「总结成复盘」是 raf 的 LLM 职责（与 06 §FR9 一致）。

## 7. 留存与清理

- `retention_days`（默认 180）：`purge_before(before_date)` 按 `updated_at` 清理更早的 `conversations` 整行（含其 `data` 内全部消息与轨迹）。
- `delete_session`：删单会话 `conversations` 整行（含消息与轨迹）；权限校验（仅本人/管理员）。单表收口后「删会话即删全部」，无 `cascade` 概念。
- 清理为低频运维操作，建议脚本/定时任务触发，不在请求链路同步执行。

---

## 8. 隐私与安全

- **脱敏（redact.py）**：`pii_redact=true` 时，落库前对手机号/身份证/银行卡/邮箱等做掩码（`138****1234`）；正则集可配，白名单避免误伤（如合规条款编号）。
- **访问控制**：所有查询以 `user_id` 归属隔离；`allow_admin_all=true` 允许运维跨用户审计（仅管理员角色）。
- **防篡改（单表内不可变）**：`conversations.data` 内消息/轨迹仅追加，应用层禁 UPDATE 单条消息 / DELETE 单条事件；整体清理仅经 `delete_session` / `purge_before`（整行删）。
- **最小化**：中间步骤存摘要、RAG 命中仅存溯源，降低敏感面。
- **合规**：`retention_days=0` 表示永久留存（金融场景可能要求）；默认值待法务确认（需求 §9.6）。

## 9. 与多智能体集成（raf 复盘）

- **采集集成**：`install_history_tracing()` 的 `traced_chat` 包裹 03 `chat_service.chat`，无侵入记录全链路（§4）。
- **复盘集成**：`get_session_for_review` 产出结构化上下文 → raf 总结智能体生成复盘（类比 06 把 `Passage` 喂 raf）。07 与 raf 分工明确（§6.3）。
- **RAG 命中溯源一致性**：07 的 `rag_hit` 事件复用 06 `Passage` 溯源字段（`doc_id/title/agency/domain/chapter/effective_date/version/score`），保证 raf 引用与 06 一致。
- **降级契约**：07 不可用时主链路正常（fail_mode），raf 复盘缺失该会话历史时如实声明「无历史依据」。

## 13. 风险与权衡

| 风险 | 权衡 / 缓解 |
|---|---|
| 02 未暴露 step 钩子，细粒度 trace 暂不可得 | 首版记「头+主消息」，预留 events 入参；02 扩展后增强（§4.3） |
| 旁路异步写入可能丢失（进程崩溃） | `fail_mode=local` 落兜底文件；会话级可追溯非强一致，可接受最终一致 |
