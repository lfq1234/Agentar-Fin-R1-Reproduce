## 0. 总体评价

07 模块定位在「03 后端基础层之上、与 06 知识库并列」的可追溯横切层，目标是把「一次 AI 交互」从 03 的「两条主消息」扩展为「全链路可回放、可审计、可复盘」的记录。整体评价：

- **优点**：范围边界（In/Out Scope）定义清楚；「复用不重写」原则尊重了 03 已稳定的契约；hook/装饰器无侵入 + `NoopHistoryStore` 降级保证了主链路零阻塞；append-only 轨迹满足审计防篡改；隐私（脱敏/权限/最小化）内建；嵌入式 SQLite 与 06 范式一致；测试策略（mock `run()`、无真实 key 可跑）务实。
- **风险**：本模块的**核心价值主张（细粒度 trace 回放）在 v1 实际无法达成**——因为它硬依赖 02 暴露 step 钩子，而 02 当前没有。这是最大的时序/范围风险。此外，权限模型、时间类型、turn 模型、建表时机、写入并发等存在若干会直接影响正确性与安全性的设计空档。

## 1. 🔴 必须修改项（编码前阻断，Blocker）

### B1 · 02 step 钩子缺失导致 v1 核心价值落空（最高优先级）
- **问题**：需求 §9.1 / 技术 §4.3 已承认「02 未暴露 step 钩子，首版仅记头+主消息」。但验收标准 §8 仍写「`trace_events` 含各 agent 步骤 / tool / RAG 命中 / 审核 / 风控 / 错误」作为通过条件。二者矛盾：**按当前依赖，v1 验收不可能通过**。
- **要求**：
  1. 把验收标准拆成两档：**v1（02 无 step 钩子）= 仅 `session_traces` 头 + user/assistant 主消息事件**，明确写进验收；**v2（02 扩展 step 钩子后）= 完整细粒度事件**。
  2. 在 02 的评审/排期中给「step 钩子暴露」立项并排期，作为 07 完整能力的**硬前置**。否则 07 不应以「全链路回放」对外承诺。

### B2 · 权限/归属校验未覆盖全部接口（安全缺口）
- **问题**：`HistoryStore` 协议里只有 `get_session` 带可选 `requester_id`，而 `list_sessions`、`get_turn`、`keyword_search`、`semantic_search`、`export_session`、`delete_session`、`purge_before` 都**不接收 requester 身份**。实现层若只在 `get_session` 内判断，其他接口形同无鉴权；REST 层一旦直接透传 `user_id` 入参，任何用户可查/删他人会话（即便 `allow_admin_all=false`）。
- **要求**：
  1. 所有读/删方法签名统一加 `requester_id: str`，由 store 内部做「`requester_id == user_id` 或 管理员」的集中仲裁（管理员态由 `allow_admin_all` + 角色判定，角色来源需明确，见 B3）。
  2. `purge_before` 设为**仅管理员**，拒绝普通用户调用。

### B3 · 管理员角色来源未定义
- **问题**：`allow_admin_all` 依赖「管理员角色」，但全文未说明角色从哪来（03 的 `users` 表有角色字段吗？JWT/会话里带吗？）。没有来源，「管理员跨用户审计」是空话。
- **要求**：明确管理员身份的获取路径（沿用 03 的 user 角色字段或请求上下文），并在 `requester_id` 仲裁中落地。

### B4 · 时间字段用 VARCHAR，范围查询/排序脆弱
- **问题**：`created_at` / `first_at` / `last_at` 全为 `VARCHAR(ISO)`。`purge_before(before_date)`、`keyword_search(start/end)`、`list_sessions(order="last_at desc")` 都依赖字符串比较。只有严格统一的 **UTC、零填充、含时区** ISO-8601 才安全；一旦混入本地时区或非对齐格式，范围删除会漏删/错删，`last_at desc` 排序会错。
- **要求**：统一改为 `INTEGER`（epoch 毫秒）存储，或在写入侧强制 UTC ISO-8601（`Z` 后缀）并在所有比较前规范化；索引 `idx_traces_time` 建立在确定可比的类型上。

### B5 · `turn_id` 语义与生成机制缺失
- **问题**：`trace_events.turn_id` 指「一次 user→assistant 交互」，但无 `turns` 表，也未说明 `turn_id` 如何产生、如何与 03 `messages` 的行 id 映射。`get_turn(conversation_id, turn_id)` 的对象身份不明确，回放单轮无从实现。
- **要求**：定义 turn 模型——建议以「一对 (user_message_id, assistant_message_id)」或 03 `messages` 的轮次序号派生 `turn_id`，并在 `collect.py` 写入 trace 时显式绑定；或在 07 侧维护 `turns` 表。

### B6 · 建表时机与迁移策略不明确（运行时炸库风险）
- **问题**：`build_on_startup` 默认 `false`，而 `init_history_db()` 仅在 `enabled && build_on_startup` 时建表。若 `enabled=true` 但 `build_on_startup=false` 且无人跑迁移，首次 `record_run` 会因缺表报错——这与「07 失败不阻塞主链路」的降级契约冲突。
- **要求**：
  1. 提供显式迁移入口（`init_history_db()` 幂等建表，纳入部署/启动脚本），不依赖 `build_on_startup` 开关；
  2. 或把 `build_on_startup` 默认改为 `true`（与 03 `init_db()` 同模式）；
  3. 明确 07 与 03 schema 的版本管理关系。

## 2. 🟡 建议优化项（强烈建议，不阻塞但影响质量/安全）

### S1 · 写入并发：SQLite 单写者需串行化
- 技术 §13 / §4 说「旁路异步写入」「独立连接/事务」，但 asyncio 下多线程/协程并发写同一 SQLite 易触发 `database is locked`。建议用 `asyncio.Lock` 串行化写事务，或写队列（单 consumer 协程）兜底。

### S2 · 脱敏覆盖范围需覆盖全部写路径
- 需求 §8 脱敏描述偏「用户消息/输出」，但 `final_result` JSON、`trace_events.summary_in/out`、`meta_json`（tool 结果、RAG 命中内容）也可能含 PII（用户原话会被摘要进 summary_in）。要求 `redact.py` 在**所有落库字段写入前**统一过一遍，而非仅主消息。

### S3 · `trace_events` 的树序与 `parent_event_id` 一致性
- 事件跨异步多 agent 流水 emit，且写入是旁路异步。需保证事件间父子链接与顺序在异步环境下不串（建议每个事件带 `seq` 单调序号 + `run_id` 内有序；启用 SQLite FK 或至少在应用层校验 `parent_event_id` 存在）。

### S4 · `fail_mode=local` 兜底文件需定义闭环
- 进程崩溃时异步写可能丢；`local` 落兜底文件，但**文件路径、格式、留存、重放/回填路径**均未定义，否则只是把丢失变成「死文件」。要求定义重放器或明确标注为 best-effort 不保证。

### S5 · 语义检索存储位置（已固化，不再二选一）
- 原技术 §5.2 写「写入 07 `history_embeddings` **或** 经 DuckDB ATTACH 入 06 库」二选一，已**固化为一种**：07 语义检索的向量落在**主库内的 `history_embeddings` 表**（与 03 同实例），向量检索通过 DuckDB `ATTACH` 主库复用 06 的余弦机制；**不把历史塞进 06 知识库、也不另开 DB**。`history_embeddings` 已增加 `embedder_version` 字段以支撑 embedder 切换时的重建/版本策略。

### S6 · 与 03 预留 `agent_traces` 的命名决策（已决策）
- 03 `schema.sql` 曾预留 `agent_traces` 但未落地。为遵循「统一主库、不并行分叉」原则，**决策：07 采用 `session_traces` + `trace_events` 命名，并从 03 `schema.sql` 正式删除未使用的 `agent_traces` 预留**，使主库内只有一套轨迹命名，消除运维混淆。

### S7 · `session_meta` 聚合字段的同步责任方
- `msg_count` / `total_tokens` / `first_at` / `last_at` 是派生量，文档未说明由谁、何时更新（每次 `record_run` 经 `upsert_session_meta`？）。需定义更新触发点，否则列表展示的统计会陈旧。

### S8 · `silent` 模式失败不可见
- `fail_mode=silent` 下写入失败完全静默，不利于排障。建议至少打 `warning` 日志 + 可选失败计数器，不影响主链路但可观测。

### S9 · `record_traces=false` 时 `get_session(with_trace=True)` 行为
- 关细粒度后 `trace_events` 为空，`get_session` 应明确定义返回「仅主消息流 + 空 trace 树」而非报错；验收需覆盖此分支。

### S10 · 权限测试缺口
- 测试策略覆盖采集/查询/检索/导出/留存/降级，但**缺「非本人访问被拒」「管理员越权」「purge 仅管理员」**等安全用例。建议补 `test_history_auth.py`。

## 4. 验收标准补充建议

在需求 §8 基础上，建议增补：

- [ ] **v1/v2 双档验收**：v1 明确仅头+主消息事件即通过；v2（02 step 钩子就绪后）才要求完整 `trace_events` 树。
- [ ] **权限**：非本人访问 `list_sessions`/`get_turn`/`keyword_search`/`export_session` 均返回空/拒；`purge_before` 非管理员调用被拒。
- [ ] **时间**：`purge_before` 在跨时区/本地时区混用场景下仍精确（epoch ms 或 UTC ISO 归一化后验证）。
- [ ] **turn**：`get_turn` 能按定义的 `turn_id` 取出单轮完整子树（需先落地 B5）。
- [ ] **建表**：`enabled=true`、`build_on_startup=false` 且未跑迁移时，首写不应炸库（由 B6 迁移入口兜底）。
- [ ] **脱敏覆盖**：构造含 PII 的 tool 结果 / RAG 内容，验证 `final_result`/`meta_json` 落库也被掩码（S2）。
