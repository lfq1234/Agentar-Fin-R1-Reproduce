# 07 · 会话历史记录（Session History & Trace）模块（需求文档）

> 版本：v1（2026-08-05 初版）
> 状态：草稿（本轮产出需求/技术文档，尚未落地代码）
> 文档性质：**需求文档**，定义会话历史记录模块的功能边界、数据模型、接口契约与验收基线。
> 关联：
> - `00-总文档`（架构总览）
> - `02-多智能体基础框架`（`run()` 流水线 + 9 角色，07 需要无侵入地记录其每一步）
> - `03-传统后端基础层`（已建 `users` / `conversations` / `messages` 主消息流落库 + `schema.sql` 预留 `agent_traces`；07 在其上补全细粒度轨迹与历史检索）
> - `06-知识库-DuckDB`（可选语义检索复用其向量检索能力，把历史消息纳入可语义搜索的范围）

## 1. 背景与目标

后端前六个模块已落地：01 模型接口、02 多智能体流水线、03 后端基础层（含主消息流落库）、04 专家 RAG、05 联调、06 DuckDB 知识库。其中 03 已实现「用户消息 ↔ 助手消息」的主消息流落库（`chat_service` 在 `db.enabled` 时把 user/assistant 消息写入 `conversations` / `messages` 表），但其 `schema.sql` 预留的 `agent_traces` 表**尚未落地**，且存在三个未闭合的缺口：

1. **细粒度执行轨迹缺失**：每次 `run()` 内部是一条多 Agent 流水线（Coordinator 意图路由 → 信息查询智能体 RAG 检索 → 领域专家作答 → 审核 → 风控 → 汇总）。目前只落了最终的 user/assistant 两条消息，**中间每一步的输入/输出、tool 调用、RAG 命中、token 消耗、耗时、错误**全部丢失，无法事后「回放一次完整对话到底发生了什么」。
2. **历史不可检索、不可复盘**：03 只能按 `conversation_id` 顺序取出主消息，无法按关键词/语义搜索历史、无法导出成复盘材料、无法把某次对话交给总结智能体（raf）做复盘。
3. **多轮上下文信息薄弱**：仅凭 `conversation_id` 取消息，缺少结构化的会话元信息（场景、主题、状态、累计 token、起止时间），「断点续聊」和「会话级别管理」缺乏支撑。

**本模块（07 · 会话历史记录）的目标**：在 **03 主消息流之上**建立一层**可追溯、可检索、可复盘的会话历史记录**，把「每次和 AI 聊了什么」从「两条主消息」扩展为「一次完整、可回放、可审计的交互记录」，并支撑历史查询、语义/关键词检索、导出复盘、以及对 raf 总结智能体的复盘素材供给。

设计原则：

- **复用不重写**：主消息流（User / Conversation / Message）完全复用 03 的 SQLModel 与落库逻辑，07 **不重建**主消息流，只读取与扩展；07 新增的细粒度轨迹落在 03 `schema.sql` 已预留的 `agent_traces` 命名空间内（具体为 `session_traces` + `trace_events` 两张表）。
- **统一主库、常规分层（service + view）**：历史数据（主消息流 + 细粒度轨迹）统一落在 **03 主库同一实例**，07 不再另开数据库；07 以 **service 层**（落库 / 查询 / 检索 / 导出）与 **view 层**（会话级聚合视图 `SessionDetail` / `TurnDetail` / `SearchHit`）组织，是常规后端分层而非独立分叉。主库本身仍是进程内 SQLite（或统一 MySQL），不引入独立服务；语义检索（可选）复用 06 的 DuckDB，不新增向量服务。
- **可追溯优先（Trace-first）**：每一次 AI 交互都应留下「全链路可回放」的记录，包括中间 agent 步骤、tool 调用、RAG 命中溯源、token/耗时、错误。
- **旁路无侵入、不阻塞主链路**：轨迹采集以 hook/装饰器包裹 `run()`，异步、旁路写入；即使 07 自身写入失败，主服务（02/03）仍须正常返回 `reply`（降级而非中断）。
- **隐私与安全内建**：历史含用户输入等敏感内容，必须有脱敏、权限、留存与防篡改（append-only）机制。

## 2. 范围

### 2.1 包含（In Scope）

- **细粒度执行轨迹采集（agent_traces 落地）**：每次 `run()` 产生一条 `session_trace`（关联 `conversation_id` / `user_id` / `run_id` / `scene` / 耗时 / 总 token / 模型 / 最终 `AgentResult`），其下挂若干 `trace_event`（每个 agent 步骤 / tool 调用 / RAG 命中 / 审核 / 风控 / 错误一条），形成可回放的树。
- **会话元信息扩展**：在 03 `conversations` 之上补充会话级视图/扩展字段（场景、主题标题、状态、累计 token、消息数、起止时间），便于会话级管理，不破坏 03 既有表契约。
- **历史查询与回放**：`list_sessions`（按用户/过滤条件列出会话）、`get_session`（取主消息流 + 完整 trace 树）、`get_turn`（取单轮完整输入/输出/工具/RAG/审核风控）。
- **历史检索**：`keyword_search`（按关键词在消息/事件中 BM25 或 SQL 匹配，带时间/用户/场景过滤）；**可选** `semantic_search` 复用 06 的向量检索机制（把历史消息向量化写入主库 `history_embeddings` 表）做语义召回，与 06 同主库。
- **导出与复盘**：`export_session`（导出 md / json 复盘文档，含完整 trace）；`get_session_for_review`（结构化上下文供给 raf 总结智能体，类比 06 把 `Passage` 喂给 raf）。
- **留存与清理**：`retention` 策略（按天/条数），`delete_session` / `purge_before(date)`，清理可配置为仅清轨迹或联动清主消息。
- **隐私与安全**：敏感字段脱敏（PII 掩码）、访问控制（仅本人/管理员）、审计日志 append-only（防篡改）。
- **与多智能体集成**：以 hook 方式接入 02 `run()`（及 03 `chat_service`），无侵入采集；降级契约保证不影响主链路。
- **配置与生命周期**：`config.history` 段，`history.enabled` 总开关，`build_on_startup` 可选建表。

### 2.2 排除（Out of Scope）

- **主消息流重写**（user/assistant 落库）——属 03，07 仅读取与扩展。
- **多租户 / 跨用户全局检索**——隐私限制，本期仅本人/管理员访问本人会话。
- **前端 / UI 页面**——与 05 一致，07 不含浏览器/页面代码；仅提供模块级接口与可选 REST 契约。
- **实时流式 trace（SSE）**——本期为请求级旁路写入，流式逐 token trace 排期。
- **嵌入模型训练 / 领域微调**——属 01/04 后续；07 语义检索复用 06 的 `get_embedder()`。
- **会话级权限体系（鉴权/登录）**——属 03 后续；07 仅做 `user_id` 级别的归属隔离与简单管理员开关。
- **跨会话「记忆/画像」聚合**——本期不把多会话聚合为用户画像，仅做单会话复盘与检索。

## 3. 功能需求

### FR1 · 会话概念与主消息流（复用 03）
- 「会话（Session）」= 03 的 `Conversation`：`conversation_id` 为唯一键；07 不新建会话表，直接复用 03 的 `conversations` / `messages`。
- 主消息流（user → assistant）已由 03 `chat_service` 在 `db.enabled` 时落库；07 仅**读取**用于回放/检索/导出，不在 07 内重复写主消息。
- 若 `db.enabled=false`（03 短路不落库），07 仍可记录**内存态**轨迹（进程内、随进程生命周期），但 `list_sessions` / `get_session` 仅能访问本次进程内的会话；该降级行为须与 03 的 `db.enabled` 门控一致。

### FR2 · 会话元信息扩展（会话级视图）
- 在 03 `conversations` 基础上，07 提供会话级聚合视图/扩展字段（不破坏 03 表结构，优先以查询视图或 07 侧 `session_meta` 扩展表实现，而非 ALTER 03 表）：
  - `scene`：会话场景（Banking/Securities/Insurance/Trust/MutualFunds），以首次消息为准（与 03 §3 `scene` 归属规则一致）。
  - `title`：会话主题标题（可由首条 user 消息截断生成，或 raf 后续补生成）。
  - `status`：active / archived / deleted。
  - `msg_count`、`total_tokens`、`first_at`、`last_at`：聚合统计，便于列表展示与留存策略。
- `upsert_session_meta(conversation_id, **fields)`：幂等写入/更新会话元信息。

### FR3 · 细粒度执行轨迹采集（agent_traces 落地）
- 每次 `run()`（经 03 `chat_service` 或直接调用）触发一条 `session_trace`：
  - 字段：`run_id`（07 生成，UUID）、`conversation_id`、`user_id`、`scene`、`created_at`、`duration_ms`、`total_tokens`、`model`（实际调用的 `model_name`）、`final_result_json`（序列化 `AgentResult`：reply + compliance_notes + risk_flags + 结构化字段）、`status`（ok / error）。
- 其下 `trace_event` 树（parent_event_id 形成层级）：
  - **agent 步骤事件**：`agent`（Coordinator / rag / 各专家 / review / risk）、`type`、`summary_in`（输入摘要）、`summary_out`（输出摘要）、`tokens`、`duration_ms`。
  - **tool 调用事件**：`type=tool_call`（`tool` 名如 `lookup_knowledge` / `retrieve_documents`、参数摘要、结果摘要、是否命中）。
  - **RAG 命中事件**：`type=rag_hit`（`query`、命中的 `Passage` 溯源：`doc_id`/`title`/`agency`/`domain`/`chapter`/`effective_date`/`version`/`score`——复用 06 `Passage` 溯源字段），供 raf 引用与审计。
  - **审核/风控事件**：`type=review` / `risk`，记录 `compliance_notes` / `risk_flags` 摘要。
  - **错误事件**：`type=error`（`exc_type`、`message`、`traceback_summary`）。
- 采集方式：以 hook/上下文管理器包裹 `run()`（见技术文档 §4），在 02 流水线每个关键节点 emit event；允许「摘要而非全文」以控制存储（原文可仅保留 user/assistant 主消息，中间步骤存摘要 + 必要结构化字段）。

### FR4 · 历史查询与回放
- `list_sessions(user_id, *, scene=None, status="active", limit=50, offset=0, order="last_at desc") -> list[SessionMeta]`：列出某用户的会话列表（元信息）。
- `get_session(conversation_id, *, with_trace=True) -> SessionDetail`：返回主消息流（按时间序） + 完整 `trace` 树（可回放一次对话的全部链路）。
- `get_turn(conversation_id, turn_id) -> TurnDetail`：返回单轮（一次 user→assistant 交互）的完整内容：用户输入、各 agent 步骤、tool 调用、RAG 命中、审核/风控结论、最终 assistant 回复。
- 权限：非本人（且非管理员）访问须返回 `403`/空（隐私边界）。

### FR5 · 历史检索
- `keyword_search(query, *, user_id, scene=None, start=None, end=None, limit=20) -> list[SearchHit]`：在 `messages` 与 `trace_events`（summary_in/out）上做 BM25 或 `LIKE`/`fts` 匹配；返回命中的 会话 / 轮次 / 事件 引用与片段，带时间/场景过滤。
- **可选语义检索** `semantic_search(query, *, user_id, top_k=5) -> list[SearchHit]`：复用 06 的向量检索机制（DuckDB 余弦）——把历史消息（user + assistant 摘要）向量化后写入主库 `history_embeddings` 表（与 06 同主库），经 `list_cosine_distance` 召回；命中返回会话/轮次引用。受 `history.semantic_search` 开关控制（默认关），开启时依赖 06 的 `get_embedder()` 与维度一致性（与 06 §3.4 同约束）。

### FR6 · 导出与复盘
- `export_session(conversation_id, fmt="md") -> str`：导出复盘文档（md / json），含主消息流 + 完整 trace（agent 步骤、tool、RAG 命中溯源、审核/风控、token/耗时）。
- `get_session_for_review(conversation_id) -> str`：生成结构化复盘上下文（类比 06 `format_passages`），供 **raf 总结智能体**消费——把一次会话的「用户诉求 + 各 agent 结论 + RAG 依据 + 审核/风控」聚合成带溯源的上下文，由 raf 生成复盘摘要/改进建议。07 与 raf 职责边界：07 只负责「记录 + 组织成结构化上下文」，「总结成复盘」是 raf 的 LLM 职责。

### FR7 · 留存与清理
- `retention_days`（默认 180）：超过保留期的会话/轨迹进入清理范围。
- `delete_session(conversation_id) -> int`：删除某会话的轨迹（及可选联动删除 03 主消息，受 `purge_cascade` 控制）。
- `purge_before(before_date, *, cascade=False) -> int`：清理 `before_date` 之前的轨迹；`cascade=True` 时联动清 03 主消息（谨慎，默认 false）。
- 清理为低频运维操作，建议由 `build.py` 类脚本或定时任务触发，不在请求链路内同步执行。

### FR8 · 隐私与安全
- **脱敏（PII redact）**：`pii_redact=true` 时，落库前对用户消息/输出中的疑似敏感字段（手机号、身份证、银行卡、邮箱等）做掩码（`138****1234`）；规则可配，默认正则集；脱敏仅作用于落库副本，不影响实时 `reply`。
- **访问控制**：所有查询接口以 `user_id` 归属隔离；管理员开关 `allow_admin_all` 允许跨用户审计（仅运维角色）。
- **防篡改（append-only）**：`trace_event` 一旦写入不可 UPDATE/DELETE（仅 `delete_session`/`purge_before` 整体清理）；写操作记 `created_at`，不更新，保证审计链完整。
- **最小化**：中间步骤存摘要而非全文，降低敏感面；RAG 命中仅存溯源引用与分数，不重复存原文块。

## 4. 非功能需求

- **依赖**：复用 03 的 SQLModel / 异步引擎，**历史表与 03 同库同实例**（07 的 `session_meta` / `session_traces` / `trace_events` 直接建在主库，跨表关联即可）；语义检索可选复用 06 的 `duckdb`，不新增独立服务。
- **性能**：轨迹采集在 `run()` 返回后**旁路异步**写入（线程/任务），不阻塞主链路返回 `reply`；`list_sessions` / 检索走索引（`conversation_id` / `user_id` / `created_at`）。
- **可观测与降级**：07 写入失败（DB 不可用 / 磁盘满）**不得**导致 02/03 主服务报错；主链路返回 `reply`，07 静默失败或落本地兜底文件（受 `history.fail_mode=silent|local` 控制）。
- **兼容性**：新增表命名空间 `agent_traces` / `trace_events` 与 03 `schema.sql` 预留对齐；复用 03 `Conversation` / `Message` 契约，不 ALTER 03 表（会话元信息优先用 07 侧扩展表而非改 03）。
- **并发安全**：SQLite 单写者，07 写走独立连接/事务；读多写少天然契合。
- **可测试**：单测用 mock `run()` 注入（构造带多 agent 步骤的假 `AgentResult`），验证 trace 采集、查询、检索、导出、留存与降级；无真实模型/key 可跑。

## 5. 数据模型（SQLite schema）

> 复用 03 的 `users` / `conversations` / `messages`；07 新增 `session_meta`（扩展元信息，可选）、`session_traces`、`trace_events`。以下为 07 新增部分；完整 DDL 以 `app/services/history/schema.sql` 与 SQLModel 模型（`app/services/history/models.py`）为准，并与 03 `schema.sql` 字段比对一致。

```sql
-- 07 新增：会话元信息扩展（不破坏 03 conversations，独立表，conversation_id 为外键语义）
CREATE TABLE IF NOT EXISTS session_meta (
    conversation_id VARCHAR PRIMARY KEY,   -- 关联 03 conversations.id
    scene           VARCHAR,               -- 场景（首次消息为准）
    title           VARCHAR,               -- 主题标题（首条 user 截断或 raf 补）
    status          VARCHAR DEFAULT 'active',  -- active | archived | deleted
    msg_count       INTEGER DEFAULT 0,
    total_tokens    INTEGER DEFAULT 0,
    first_at        VARCHAR,               -- ISO
    last_at         VARCHAR,               -- ISO
    created_at      VARCHAR
);

-- 07 新增：一次 run() 的执行轨迹头（落地 03 预留的 agent_traces 命名空间）
CREATE TABLE IF NOT EXISTS session_traces (
    run_id          VARCHAR PRIMARY KEY,    -- 07 生成 UUID
    conversation_id VARCHAR,               -- 关联 03 conversations.id
    user_id         VARCHAR,               -- 关联 03 users.id
    scene           VARCHAR,
    created_at      VARCHAR,               -- ISO，精确毫秒
    duration_ms     INTEGER,
    total_tokens    INTEGER,
    model           VARCHAR,               -- 实际 model_name
    status          VARCHAR,               -- ok | error
    final_result    TEXT                   -- JSON 序列化 AgentResult（reply+compliance_notes+risk_flags+结构化）
);
CREATE INDEX IF NOT EXISTS idx_traces_conv ON session_traces(conversation_id);
CREATE INDEX IF NOT EXISTS idx_traces_user ON session_traces(user_id);
CREATE INDEX IF NOT EXISTS idx_traces_time ON session_traces(created_at);

-- 07 新增：轨迹事件树（每个 agent 步骤 / tool / RAG 命中 / 审核 / 风控 / 错误 一条）
CREATE TABLE IF NOT EXISTS trace_events (
    id              BIGINT,                -- 自增（或 UUID）
    run_id          VARCHAR,               -- 关联 session_traces.run_id
    parent_event_id BIGINT,                -- 层级（一轮下的多步骤；NULL=根）
    turn_id         VARCHAR,               -- 关联一次 user->assistant 交互
    agent           VARCHAR,               -- Coordinator/rag/专家/review/risk
    type            VARCHAR,               -- user|assistant|tool_call|tool_result|rag_hit|review|risk|error
    summary_in      TEXT,                  -- 输入摘要（控存储）
    summary_out     TEXT,                  -- 输出摘要
    meta_json       TEXT,                  -- 结构化扩展：tool 名/参数、RAG 命中溯源(Passage 字段)、错误类型等
    tokens          INTEGER,
    duration_ms     INTEGER,
    created_at      VARCHAR                -- ISO
);
CREATE INDEX IF NOT EXISTS idx_events_run ON trace_events(run_id);
CREATE INDEX IF NOT EXISTS idx_events_turn ON trace_events(turn_id);
CREATE INDEX IF NOT EXISTS idx_events_type ON trace_events(type);

-- 可选语义检索：历史消息向量列（开启 history.semantic_search 时启用，复用 06 维度约定）
CREATE TABLE IF NOT EXISTS history_embeddings (
    message_id      VARCHAR PRIMARY KEY,    -- 关联 03 messages.id
    conversation_id VARCHAR,
    embedding       TEXT,                   -- JSON 数组（经 DuckDB ATTACH 做余弦，同 06 范式）
    dim             INTEGER
);
```

> 说明：`trace_events` 为 append-only，应用层不提供 UPDATE/单条 DELETE，仅 `delete_session` / `purge_before` 整清理；`meta_json` 存 RAG 命中溯源时复用 06 `Passage` 的 `doc_id/title/agency/domain/chapter/effective_date/version/score` 字段，保证 raf 引用一致。

## 6. 接口 / API 契约

### 6.1 历史存储与查询（`app/services/history/store.py`）
统一契约（SQLite 实现；语义检索可选委托 06）：
```python
class HistoryStore(Protocol):
    def record_run(self, *, conversation_id: str, user_id: str,
                   scene: str | None, run_id: str,
```

```yaml
  retention_days: 180           # 留存期；purge_before 清理更早的轨迹
  purge_cascade: false          # delete_session/purge_before 是否联动清 03 主消息（谨慎）
```

## 9. 已知问题 / 待办

1. **02 中间 step 钩子未暴露**：首版 07 可能只能记「头 + 主消息」，细粒度 `trace_events` 依赖 02 在流水线关键节点 emit 事件（需 02 评审后扩展）——属 07 与 02 的协作门禁。
2. **与 03 `agent_traces` 预留对齐**：03 `schema.sql` 已预留 `agent_traces`，07 以 `session_traces` + `trace_events` 落地，需确认命名与 03 评审一致，避免重复表。
3. **语义检索维度一致性**：开启 `semantic_search` 复用 06 `get_embedder()`，需遵循 06 §3.4 维度一致约束，跨 embedder 切换需重建 `history_embeddings`。
4. **脱敏规则待定**：PII 正则集与掩码策略需安全/合规确认；误伤（如把合规条款编号当敏感）需可调白名单。
5. **总文档 §7 拓扑仍待校正**：`00-总文档` 未含 06/07 层，待 02/03/06/07 评审通过后统一回正（沿用 04 §11、06 §9 约定）。
6. **留存与合规**：`retention_days` 默认值需法务/合规确认；金融场景可能要求更长留存或不可删除，需可配为 `0`（永久）。
