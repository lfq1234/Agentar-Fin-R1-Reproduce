## 1. 背景与目标

前端 03 模块「个人文档与知识图谱」已实现 UI（双标签面板：文档管理 + 知识图谱），并通过 `VITE_USE_MOCK` 本地 Mock 跑通。其 5 个接口当前指向后端但后端尚未实现。本模块（**08**）即为前端 03 提供后端支撑：

- **个人文档**：上传、解析、分块、查看列表、查看处理状态、删除（级联）。
- **知识图谱**：从个人文档抽取实体/关系，供前端 G6 辐射布局可视化。

设计原则（来自项目长期约定与 06 已落地范式）：

- **复用 06 的存储范式**：结构化业务数据落 **SQLite**，向量检索走 **DuckDB**（`ATTACH` 主库，`list_cosine_distance` 算余弦）。
- **不另开独立 SQLite 文件**：所有表（文档元数据、分块、向量、图谱）统一建在 **03 主库 `agentar.db`**（与 `users` / `conversations` / `messages` / 07 会话历史同实例），不新建 `*.db` 分叉库（与 06 当前默认 `kb/knowledge.db` 的「独立文件」实现形成对照，08 显式选择主库方案）。
- **嵌入统一走 01 `get_embedder()`**，切分复用 `06`/`04` 的 `chunking._split_into_chunks`，不重复造轮子。

## 2. 范围

### 2.1 包含

- 文件上传（multipart，`files[]` + `user_id`）。
- 文本 / Markdown 解析（`.txt` / `.md`）。
- 文本分块（复用共享切分，默认 `max_chars=600`、`overlap=80`）。
- 分块向量化（01 `get_embedder()`）并落 DuckDB 向量表。
- 文档处理状态机（`pending` → `parsing` → `done` / `error`）与状态轮询。
- 文档列表、删除（级联删分块 + 向量 + 图谱）。
- 知识图谱抽取（文档节点 + 实体节点 + 关系边）与查询。

### 2.2 排除（本期不做，留扩展点）

- **二进制解析**：PDF / DOCX / XLSX 本期不支持，上传即标记 `status=error` 并给出明确错误文案（扩展点：后续接入 `pdfplumber` / `python-docx` 等）。
- **鉴权**：仅以 `user_id` 作作用域隔离，不接登录/权限体系（沿用 03「不接鉴权」约定）。
- **图谱抽取降级**：LLM 不可用时不阻塞上传，退化为启发式（正则/共现）抽取，保证 `status=done` 且图谱非空或空均可。
- **后台异步任务框架**：MVP 同步处理（小文件）；大文件/多文件后台化留作后续（状态轮询机制已为此预留）。
- **将个人文档喂入 06 通用知识库做 RAG 召回**：本期个人文档图谱与向量独立，不与 06 `chunks` 耦合；后续可选择性同步。

## 3. 功能需求

> 所有接口统一 `prefix="/api"`（FastAPI 注册方式同 `chat.py` / `history.py`），故完整路径形如 `/api/v1/documents`。`user_id` 由前端以字符串 `"1"` 传递（FormData / query），后端按 `int` 接收并强制作用域。

### FR1 · 上传文档
- **接口**：`POST /api/v1/documents`（multipart）
- **入参**：`files: UploadFile[]`（字段名 `files`）、`user_id: int`（默认 1）
- **行为**：
  1. 为每个文件先写 `personal_documents` 一行，`status=pending`。
  2. 解析文本 → 分块 → 逐块嵌入（批量 `get_embedder().embed`）→ 写 `personal_doc_chunks` + `personal_doc_chunk_embeddings`（DuckDB）。
  3. 抽取知识图谱 → 写 `personal_graph_nodes` / `personal_graph_edges`。
  4. 置 `status=done`，生成 `summary`（可选，来自图谱或首段摘要）。
  5. 解析/嵌入失败时置 `status=error` 并写 `error` 文案（不影响其他文件）。
- **响应**：`{ "documents": PersonalDocument[] }`（见 §5.1）。

### FR2 · 文档列表
- **接口**：`GET /api/v1/documents?user_id=1`
- **响应**：`{ "documents": PersonalDocument[] }`，按 `uploaded_at` 倒序。

### FR3 · 删除文档
- **接口**：`DELETE /api/v1/documents/{id}?user_id=1`
- **行为**：级联删除该文档的 `personal_doc_chunks`、`personal_doc_chunk_embeddings`、`personal_graph_nodes`、`personal_graph_edges`，再删 `personal_documents`（或靠外键 `ON DELETE CASCADE`）。
- **响应**：`204 No Content`。

### FR4 · 文档状态
- **接口**：`GET /api/v1/documents/{id}/status`
- **响应**：`PersonalDocument`（单条，同 §5.1）。

### FR5 · 知识图谱
- **接口**：`GET /api/v1/knowledge-graph?user_id=1`
- **响应**：`{ "nodes": GraphNode[], "edges": GraphEdge[] }`（见 §5.2）。仅返回该 `user_id` 作用域内的节点/边。

## 4. 数据模型（落 03 主库 `agentar.db`）

### 4.1 SQLite（结构化业务数据，DDL 收口 `app/db/schema/sqlite/main.sql`）

```sql
-- 八、personal_documents（个人文档元数据）
CREATE TABLE IF NOT EXISTS personal_documents (
    id          TEXT PRIMARY KEY,        -- UUID
    user_id     INTEGER NOT NULL,
    filename    TEXT NOT NULL,
    size        INTEGER NOT NULL,        -- bytes
    status      TEXT NOT NULL,           -- pending | parsing | done | error
    error       TEXT,                    -- status=error 时填充
    uploaded_at TEXT NOT NULL,           -- ISO 8601
    summary     TEXT,                    -- 可选：首段/图谱摘要，供前端「基于此文档提问」
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS ix_pdoc_user ON personal_documents(user_id);

-- 九、personal_doc_chunks（分块文本，结构化业务数据）
CREATE TABLE IF NOT EXISTS personal_doc_chunks (
    id        TEXT PRIMARY KEY,          -- UUID
    doc_id    TEXT NOT NULL,
    user_id   INTEGER NOT NULL,
    idx       INTEGER NOT NULL,          -- 块顺序
    text      TEXT NOT NULL,
    chapter   TEXT,                      -- 切分得到的父标题/章节
    FOREIGN KEY (doc_id) REFERENCES personal_documents(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS ix_pchunk_doc ON personal_doc_chunks(doc_id);

-- 十、personal_graph_nodes（知识图谱节点）
CREATE TABLE IF NOT EXISTS personal_graph_nodes (
    id              TEXT PRIMARY KEY,    -- UUID
    doc_id          TEXT NOT NULL,
    user_id         INTEGER NOT NULL,
    label           TEXT NOT NULL,
    type            TEXT NOT NULL,       -- Org | Product | Clause | Metric | Person | Concept | Document
    source_doc_id   TEXT NOT NULL,
    properties_json TEXT                -- JSON：{k: string|number}
);
CREATE INDEX IF NOT EXISTS ix_pgn_doc ON personal_graph_nodes(doc_id);

-- 十一、personal_graph_edges（知识图谱边）
CREATE TABLE IF NOT EXISTS personal_graph_edges (
    id              TEXT PRIMARY KEY,
    doc_id          TEXT NOT NULL,
    user_id         INTEGER NOT NULL,
    source          TEXT NOT NULL,       -- node id
    target          TEXT NOT NULL,       -- node id
    label           TEXT NOT NULL,
    source_doc_id   TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS ix_pge_doc ON personal_graph_edges(doc_id);
```

### 4.2 DuckDB 向量表（DDL 收口 `app/db/schema/duckdb/personal_docs.sql`）

> 由 DuckDB 在 `ATTACH 'agentar.db' AS main (TYPE sqlite, READ_WRITE)` 时建表，与 06 `knowledge.sql` 同范式。**因表建在 SQLite 主库（SQLite 无数组类型），`embedding` 以 `TEXT`（JSON 数组）存储**，检索时由 DuckDB 在 SQL 端 `embedding::FLOAT[]` 转型；这与 06 `chunks.embedding` 的「TEXT(JSON) + 转型」完全一致的存储风格，避免 schema 范式漂移。检索用 `1 - list_cosine_distance(embedding::FLOAT[], ?::FLOAT[])`。

```sql
CREATE TABLE IF NOT EXISTS personal_doc_chunk_embeddings (
    chunk_id   TEXT PRIMARY KEY,         -- 关联 personal_doc_chunks.id
    doc_id     TEXT NOT NULL,
    user_id    INTEGER NOT NULL,
    embedding  TEXT NOT NULL,           -- JSON 数组（FLOAT 列表），DuckDB 检索时 ::FLOAT[] 转型；与 SQLite 主库兼容
    dim        INTEGER
);
CREATE INDEX IF NOT EXISTS idx_pemb_doc ON personal_doc_chunk_embeddings(doc_id);
```

## 5. 接口契约（与前端 03 严格对齐）

> 前端 03 类型使用 **camelCase**（`uploadedAt` / `sourceDocId` 等），因此后端 08 响应**必须返回 camelCase JSON**（建议 Pydantic `alias_generator=to_camel` + `populate_by_name=True`，序列化按 alias 输出）。下方为精确 JSON 形状。

### 5.1 PersonalDocument
```json
{
  "id": "uuid",
  "filename": "基金合同.md",
  "size": 12345,
  "status": "done",
  "error": null,
  "uploadedAt": "2026-08-06T00:00:00Z",
  "summary": "（可选）文档摘要"
}
```
- `status` 枚举：`pending` | `parsing` | `done` | `error`（与前端 `DocStatus` 一致）。

### 5.2 知识图谱
```json
{
  "nodes": [
    { "id": "n1", "label": "某基金", "type": "Product", "sourceDocId": "doc-uuid", "properties": { "风险等级": "R3" } }
  ],
  "edges": [
    { "id": "e1", "source": "n1", "target": "n2", "label": "关联条款", "sourceDocId": "doc-uuid" }
  ]
}
```
- `type` 自由字符串，建议取值：`Document`（文档根节点）/ `Org` / `Product` / `Clause` / `Metric` / `Person` / `Concept`。
- `properties` 为 `Record<string, string|number>`，允许 `null`/缺省。

## 6. 配置

在 `config/config.yaml` 顶层新增 `personal_docs` 段（同步 `config.example.yaml`），由 `app/config.py` 解析：

```yaml
personal_docs:
  enabled: true
  chunk:
    max_chars: 600      # 透传给 _split_into_chunks
    overlap: 80
  graph:
    enabled: true
    model: auto         # auto=走 01 get_model() 抽取；none=仅启发式
  embed_dim: 0          # 0=自适应（首个向量定维）；非 0 时强制校验维度
```

- 主库路径复用 `db.sqlite_path`（默认 `./agentar.db`），08 不再单独配置路径（**不另开文件**）。
- `db.enabled=false` 时主库不可用，08 的持久化类应短路并返回明确错误（沿用 `connection.py` 的 enabled 门控）。

## 7. 验收标准

- **AC1（前端联调）**：前端 03 关闭 `VITE_USE_MOCK` 后，上传 `.md` 文件 → 列表出现 `status=done` 文档 → 「知识图谱」标签可见节点与边 → 删除后列表与图谱同步消失。
- **AC2（数据落主库）**：上传后 `agentar.db` 的 `personal_documents` / `personal_doc_chunks` / `personal_doc_chunk_embeddings` / `personal_graph_*` 均有对应行；删除后级联清空。
- **AC3（向量检索生效）**：DuckDB 端 `list_cosine_distance` 可对该用户分块做相似度排序（单元/接口验证）。
- **AC4（无 torch 单测）**：注入 mock embedder，单测可跑通 `ingest` / `list` / `delete` / `get_graph` / 向量检索，不依赖 GPU/模型。
- **AC5（降级）**：LLM 不可用（或 `graph.model=none`）时上传仍 `done`，图谱由启发式产出或不产出，不报错/不幻觉。
- **AC6（二进制）**：上传 `.pdf`/`.docx` 返回 `status=error` 且 `error` 文案明确（非 500 崩溃）。

## 8. 风险与依赖

- **依赖**：`01 get_embedder()`（嵌入）、`04/06 chunking._split_into_chunks`（切分）、`06` DuckDB ATTACH + `list_cosine_distance` 机制（向量检索）、`03` 主库 `agentar.db`（`connection.py`）。
- **维度一致性**：跨 embedder 切换需 rebuild（同 06 §3.4）；`embed_dim` 非 0 时强制校验。
- **DuckDB 单写者**：进程内单连接串行写；多 worker uvicorn 共享同一主库文件需协调（本期单进程，风险低）。08 与 06 若同时写主库，建议错峰或统一经同一 DuckDB 连接管理。
- **同步处理超时**：MVP 同步解析/嵌入，超大文件可能超时；后续后台任务化（状态轮询已预留）。
- **图谱抽取质量**：依赖 LLM 提示词与金融实体定义；本期以「文档根节点 + 实体节点 + 共现/抽取边」为 MVP，质量随模型增强。
- **层位一致**：06 已实现「独立 kb 文件」版，08 显式改为「主库」版——二者共用 DuckDB 机制但存储目标不同，文档须明确区分，避免 reader 误以为 08 复用 `kb/knowledge.db`。
