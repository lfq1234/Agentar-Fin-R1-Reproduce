## 1. 评审目标与一句话范围

本评审在 08 需求 / 技术文档之上，重点回答一个问题：**如何把 04（专家智能体 + 工具 RAG）与 06（DuckDB 向量知识库）整合成「给智能体用的 RAG 检索」，用 DuckDB 做向量库，并经前端 03 暴露给用户。**

一句话目标：

> 前端 03 上传的**个人文档** → 切分 / 嵌入 → 落 **DuckDB 向量表**（主库）→ 智能体（04）经 06 检索增强作答（带引用）→ 前端 03 展示答案与出处。

由此，本评审**推翻 08 需求文档 §2.2「个人文档不与 06 chunks 耦合」的排除项**——个人文档在本期即作为用户作用域内的 RAG 语料，由 06 的 DuckDB 检索机制统一服务（见 §4 B2 / S4）。

## 2. 现状盘点（已落地 / 缺口）

### 2.1 06 DuckDB 知识库（已落地，链路已通）
- 包结构齐备：`store.py`（DuckDB 后端，双路召回 + 融合重排）、`sqlite_store.py`（SQLite 回落）、`chunking.py`（Passage / 切分 / BM25 / 归一化）、`build.py`、`__init__.py`（`get_knowledge_store()` 工厂按 `kb.engine` 分发）。
- `app/agent/tools.py` 已将 `lookup_knowledge` / `retrieve_documents` 切到 `get_knowledge_store().retrieve()`（文件头「06 演进」注释明确）。
- `app/agent/system.py` 的 `run()` 第 2 步：`agents["rag"]` → `retrieve_documents` → 06 的「召回 + 重排」→ 专家消费上下文。**智能体 → 06 DuckDB KB 的 RAG 链路已接通**。
- `backend/kb/` 已有 `sample_faq.md` / `sample_regulations.md` 与 `knowledge.db`；`python -m app.db.knowledge.build` 可构建（06 FR1）。

### 2.2 关键偏差（实现与 06 需求文档 / 08 主库原则不一致，须在 08 收口）
- **偏差 1（存储落点）**：06 需求 FR4 写「统一主库、不再有独立知识库文件」，但实现默认 `kb.path=./kb/knowledge.db`（独立文件），`store.py` 以 `ATTACH '{kb.path}'` 挂载。**与 08 §1「不另开独立 SQLite 文件、统一落 `agentar.db`」直接冲突**，也造成两套 DuckDB ATTACH 并存。
- **偏差 2（向量列类型）**：06 需求 §5 用 `embedding FLOAT[]` + `domain_tags VARCHAR[]`；实现为 `embedding TEXT(JSON)` + `domain TEXT`（逗号分隔），并在 SQL 端 `embedding::FLOAT[]` 转型。实现侧恰好与 08 §4.2「TEXT(JSON)+转型」同范式——**是 06 需求文档过时，而非实现错**，评审建议以实现为准并回正需求文档。
- **偏差 3（用户作用域）**：`get_knowledge_store().retrieve()` 为**全局库**，无 `user_id` 过滤；而 08 个人文档必须按 `user_id` 隔离检索。06 当前契约**不含 user scope**，是本期必须满足的硬缺口。

## 3. 目标架构与数据流

```
┌─────────────┐   上传 .md/.txt    ┌──────────────────────────────┐
│  前端 03     │ ─────────────────▶ │ 08 服务层 (app/services/...)  │
│ 个人文档与   │                    │ 解析→切分(_split_into_chunks) │
│ 知识图谱 UI  │                    │ →嵌入(01 get_embedder)        │
└──────┬──────┘                    │ →写主库 personal_documents/   │
       │                           │   chunks + DuckDB 向量表       │
       │  问答(可选 use_personal)   │ + 知识图谱抽取                 │
       │ ────────────────────────▶ │                               │
       │                           └───────────────┬──────────────┘
       │                                            │ DuckDB ATTACH agentar.db
       │                                            │ (list_cosine_distance 向量检索)
       │                                            ▼
       │   ┌──────────────────────────────────────────────────┐
       │   │ 06 知识库（DuckDB）: 个人向量 + (可选)通用 kb chunks  │
       │   │ get_knowledge_store().retrieve(query, user_id)      │
       │   └───────────────────────┬──────────────────────────┘
       │                            │ 用户作用域 Passage(带出处)
       │                            ▼
       │   ┌──────────────────────────────────────────────────┐
       │   │ 04 run(): rag 检索 → 专家作答(引用) → 审核 → 风控    │
       │   └───────────────────────┬──────────────────────────┘
       │                            │ AgentResult.reply(+引用)
       └────────────────────────────┘
```

- **DuckDB 的唯一职责**：`ATTACH 'agentar.db' AS main (TYPE sqlite, READ_WRITE)`，**一个 ATTACH 服务全部向量检索**（个人向量 + 通用 KB），`1 - list_cosine_distance(embedding::FLOAT[], ?::FLOAT[])` 做余弦近邻，元数据（含 `user_id`）预过滤后缩小候选集。
- **检索结果即 RAG 上下文**：06 返回带 `source` / `chapter` / `effective_date` 的 `Passage` 列表，由 rag 智能体总结为上下文注入专家，专家作答并标注出处（与 04 §5.7 一致）。

## 4. 关键设计决策（评审结论）

### B · 阻塞项（不解决则无法正确落地）
- **B1（存储落点必须收口为统一主库）**：06 通用 KB 须由独立 `kb/knowledge.db` 改为落 `agentar.db`（复用 03 `connection.py` 的 `sqlite_path`），与 08 个人向量同库；单一 DuckDB ATTACH 服务全量检索。实现点：`store.py` 的 `sqlite_path` 改为主库路径，废弃 `config.kb.path` 的独立文件语义；既有 `kb/knowledge.db` 数据迁移 / 重建（`build.py` 幂等可重跑）。此项是 08 §8 已标注风险「06 已实现独立文件版，08 改主库版」的正式收口。
- **B2（用户作用域检索必须落地）**：06 `get_knowledge_store().retrieve()` 增加 `user_id`（或 `corpus` 维度）参数；08 个人文档检索走 `personal_doc_chunk_embeddings WHERE user_id=?`。否则「个人文档 RAG」会跨用户串库，违反 08「以 `user_id` 作作用域隔离」约定。

### I · 重要项（影响正确性 / 一致性）
- **I1（向量列类型定稿）**：以「`TEXT(JSON)` + DuckDB `::FLOAT[]` 转型」为准（实现侧与 08 §4.2 同范式），**回正 06 需求文档 §5**（改为 `TEXT` + `domain TEXT`），消除 reader 对 `FLOAT[]` / `VARCHAR[]` 的误解。
- **I2（维度一致性）**：个人库与通用库共用同一 embedder；08 配置 `embed_dim` 并复用 06 的维度校验（首个 ingest 定维 / 不一致报错）；跨 embedder 切换需 rebuild（同 06 §3.4）。
- **I3（RAG 触发形态）**：前端 03 用哪种方式触发「基于我的文档」问答？两种可选：
  - (a) 主路径：扩展 `/v1/chat`，请求带 `user_id` + `use_personal_docs` 标志，`run()` 第 2 步改用**用户作用域**检索；
  - (b) 辅助：新增 `POST /api/v1/rag/retrieve` 供前端先取片段再自行组装（调试 / 引用展示用）。
  - **推荐 (a) 为主、保留 (b)**。两者都复用 06 `retrieve()`，仅检索作用域不同。
- **I4（KB 基线语料）**：智能体通用问答仍需 06 通用 KB（sample 法规 / FAQ）；建议 `build_on_startup: true` 或部署期 `build.py`，保证有库可检、避免空库降级（06 FR9 降级契约）。
- **I5（并发写）**：06 与 08 同写主库，DuckDB 单写者；MVP 单进程风险低，统一经 03 `connection` 的同一 DuckDB 连接或错峰写入（08 §8 已标注）。

### S · 建议项
- **S1**：前端 03 增加「基于我的文档提问」入口 + **引用卡**（来源文档 / 章节 / 生效日），复用 `Passage.source` / `chapter` / `effective_date`。
- **S2**：个人文档删除级联清向量 + 图谱（08 §3 已规划，`ON DELETE CASCADE`）。
- **S3**：检索结果可追溯——返回 `Passage` 出处供专家引用，与 04 §5.7 一致，不编造。
- **S4**：本期即采纳「个人文档同步进 RAG 语料」方向，**推翻 08 需求 §2.2 的排除项**（原「后续可选择性同步」提前到本期）。

## 5. 接口契约（新增 / 修订）

> 沿用 08 §3 的 `/api` prefix 与 camelCase 响应约定。

- **`POST /api/v1/documents`**（已有契约）：ingest 时**同步**写主库 `personal_documents` / `personal_doc_chunks` + DuckDB `personal_doc_chunk_embeddings` + 图谱；`status` 状态机不变。
- **（新增）`POST /api/v1/rag/retrieve`**
  - 入参：`{ query: str, user_id: int, top_k?: int = 5, domain?: str }`
  - 响应：`{ passages: Passage[] }`，`Passage = { content, source, score, chapter, effective_date, title, agency, docType, domain, version, docId }`（调试 / 引用展示用，user-scoped）。
- **`POST /api/v1/chat`**（扩展）：请求增 `user_id?: int`、`use_personal_docs?: bool`；`use_personal_docs=true` 时 `run()` 第 2 步以该 `user_id` 作用域检索（I3-a）。
- **`get_knowledge_store().retrieve(query, user_id=None, top_k=3, domain=None)`**：通用库 `user_id=None`（全局）；个人库按 `user_id` 走 `personal_doc_chunk_embeddings`（B2）。工厂仍按 `kb.engine` 分发 DuckDB / SQLite 双实现。

## 6. 验收标准（建议）
- **AC-R1（向量落主库）**：上传 `.md` 后 `agentar.db` 的 `personal_doc_chunk_embeddings` 有向量；DuckDB `list_cosine_distance` 可对**该用户**分块排序。
- **AC-R2（RAG 命中 + 引用）**：`/v1/chat`（`use_personal_docs=true`）命中用户文档片段，`reply` 含来源引用；无文档时降级声明「未检索到本地依据」。
- **AC-R3（不串户）**：用户 A 检索不到用户 B 的个人文档（B2）。
- **AC-R4（统一主库）**：06 通用 KB 与 08 个人向量同落 `agentar.db`，单一 DuckDB ATTACH（B1）。
- **AC-R5（无 torch 单测）**：注入 mock embedder，单测覆盖 08 ingest / list / delete / get_graph / 用户作用域 retrieve，不依赖 GPU / 模型。
- **AC-R6（降级）**：LLM 不可用 / `graph.model=none` 时上传仍 `done`；检索空时如实声明。
