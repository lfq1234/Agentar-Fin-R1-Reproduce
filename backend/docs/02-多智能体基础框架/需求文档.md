## 1. 背景与诉求

后端确定用 **AgentScope** 做金融推理 multi-agent。上游 **01-模型接口** 已把 API / 本地两种模型统一成 `get_model()` 一个入口，并提供了统一调用方法 `generate()` 与配置导出 `build_agentscope_config()`。现有 `app/agent/runner.py` 是 stub，没有任何真正的 AgentScope 运行时。

本次只搭建 **multi-agent 基础框架本身**——它是后端 `app/agent/` 模块的地基，**独立于** `services/`（服务层）、`routes/`（接口层）、`db/`（数据层）。本框架只负责"把多智能体立起来、能端到端跑通一条对话"，由后续的**独立需求**（如服务层接入、HTTP 路由等）来消费/包装它。

> ⚠️ **AgentScope 版本冲突（评审发现，已升级为门禁）**：02 与 01 原有文档基于 AgentScope「v1」API（`agentscope.init(model_configs=...)`、`DialogAgent(model_config_name=)`、`generate_args`）编写；但当前 `pyproject` / 实际安装为 **AgentScope 2.0.5**，其 API 完全不同（`agentscope.init`、`DialogAgent`、`msghub` 在 2.x 中均不存在；模型配置键为 `type` / `credential` / `model` / `parameters`）。**本项目须先锁定目标 AgentScope 版本**（见 §6），01 的 `build_agentscope_config()` 与 02 的 agent 构建均须对齐该版本。本框架采用 §2 目标1 的「方案 X」，使 02 运行时只依赖 01 的 `generate()`，从而**不**直接依赖 AgentScope 的模型初始化 API，降低版本不确定性影响。

> 范围校正（v2）：在 v1 的"1 协调者 + 5 领域专家"基础上，扩展 **3 个贯穿所有领域的支撑智能体**——RAG（知识检索）、审核（合规）、风控（风险），形成完整流水线。

## 2. 目标与范围

- 目标 1：**02 的所有模型调用必须经由 01 的统一入口 `get_model()` 与统一调用方法 `generate()`**（评审门禁 G1，方案 X）——AgentScope 在本框架中**仅做多智能体编排/流水线**，模型执行不得绕过 01。具体落地：02 定义一个自定义模型包装器（如 `AgentarModel`），其模型调用委托给 `get_model().generate(prompt)`；所有 `DialogAgent`（或等价 agent）通过 `model=包装器` 注入，禁止 `DialogAgent` 自行直连模型。
- 目标 2：定义 **1 个 Coordinator**（协调 / 路由 / 意图识别）+ **5 个领域专家** `DialogAgent`（Banking / Securities / Insurance / Trust / MutualFunds）。
- 目标 3：定义 **3 个支撑智能体**（贯穿所有领域，非业务专家）：
  - **RAG（知识检索）**：从知识库 / 监管条文 / 产品库中检索依据，给领域专家"喂料"；**本期为接口占位**（检索后端留 stub，真实向量库为后续需求）。
  - **审核（合规）**：对领域专家答案做合规审查（适当性、禁止承诺收益、风险提示到位、表述无误导），**建议式**（不阻断，附合规提示）。
  - **风控（风险）**：对答案做风险审查（风险等级匹配、高危操作预警），**建议式**（不阻断，附风险警示）。
- 目标 4：流水线编排——协调者按 `scene` 路由后，统一走 `RAG 检索 → 领域专家 → 审核 → 风控 → 汇总`，全程由协调者驱动。
- 目标 5：提供统一运行入口 `run()`，返回 `AgentResult`（含 `reply` + `compliance_notes` + `risk_flags` + 结构化字段）；结构化分析（`intent/slots/tool_plan/expression`）本期作为框架能力，**不**对外暴露 HTTP。
- 目标 6：基础 prompts——Coordinator + 5 专家 + RAG + 审核 + 风控 共 **9 个** system prompt 文件（**简版 / 占位**，后续细化）。

**不在本次范围（均为后续独立需求，已"捏出来"排期）**：
- `services/` 服务层：把本框架接入 FastAPI、提供 `run_agent` 服务入口（→ 后续需求"后端服务接入"）。
- `routes/` 接口层：`/v1/chat`、`/v1/analyze` 的 HTTP 暴露。
- `db/` 持久化、`agent_trace` 轨迹可视化、SSE 流式、真实金融工具注册表。
- **RAG 真实检索后端**（向量库 / 知识库接入）：本期仅接口占位，留 stub。

## 3. 多 Agent 拓扑

```
用户消息
   │
   ▼
Coordinator（意图识别 + 场景路由 + 流水线驱动）
   │  scene = Banking/Securities/Insurance/Trust/MutualFunds（未给定则先判定）
   ▼
RAG 知识检索（02 占位：retrieve() 返回 stub 上下文）
   │  检索上下文 → 注入领域专家
   ▼
领域专家 DialogAgent（按 scene，消费检索上下文作答）
   │  答案 draft —— 模型调用经 01 的 get_model().generate()（方案 X）
   ▼
审核（合规审查，建议式）→ 产出 compliance_notes
   │
   ▼
风控（风险审查，建议式）→ 产出 risk_flags
   │
   ▼
汇总 → AgentResult(reply + compliance_notes + risk_flags + 结构化字段)
```

- **领域专家**负责"作答"；**RAG / 审核 / 风控**是通用支撑，不绑定具体业务领域。
- **审核 / 风控为建议式**：不拦截、不打回，专家答案正常返回，审查结论仅作为 `compliance_notes` / `risk_flags` 附在结果里。
- **RAG 为接口占位**：02 中 `retrieve()` 返回空 / 占位上下文；真实检索后端（向量库等）由后续需求接入，本框架流水线结构保持不变。
- **统一模型入口（评审 G1）**：上述任一处对 LLM 的调用，都必须经由 01 的 `get_model().generate()`，禁止任何 agent 直接构造 OpenAI/本地客户端。

## 4. 功能 / 非功能要求

- 功能点（**全部位于 `app/agent/` 内**）：
  - 运行时初始化：经 `get_model()` 取得 01 统一模型对象；封装为 AgentScope 自定义模型包装器（模型调用委托给 `get_model().generate()`），再初始化 AgentScope 运行时。**02 不直接消费 `build_agentscope_config()` 来做模型初始化**（其形态对齐见 §6），但允许读取该配置作为包装器的辅助参数来源。
  - 智能体定义：Coordinator + 5 领域专家 + RAG + 审核 + 风控（共 **9 个角色**；RAG 的检索后端为 stub）。
  - 流水线编排：`run(message, scene=None, structured=False) -> AgentResult`，封装初始化 / 构建 / 路由 / RAG / 审核 / 风控 / 汇总。
  - 基础 prompts：`agent/prompts/` 下 9 个 `.txt`（Coordinator / 5 专家 / rag / review / risk）。
  - 结构化分析：以 prompt 引导 LLM 输出 JSON，解析填充四个字段（框架级，不做严格 schema 校验）。
- 非功能约束：
  - **统一模型调用（评审 G1，硬约束）**：02 不得自行直连模型；所有 LLM 调用经 01 的 `get_model().generate()`。`model.mode` 在 `api` / `local` 间切换对框架透明（靠 01 内部切换），框架代码无需改动。
  - 错误契约（评审 N2）：02 捕获来自 `app.model` 的 `ModelInvokeError`（key 缺失 / 网络错误 / 超时），转化为框架级错误，**不得静默吞掉**。
  - AgentScope 版本对齐（评审 G2/G3 升级）：agent 构建与运行时须对齐 §6 锁定的 AgentScope 版本。
  - 可测性：无真实模型 / key 时，单测用 fake 模型或 `skip` 真实调用；RAG 检索后端因本就是 stub，可直接 mock。

## 6. 01 待修改清单（02 编码前置硬依赖）

> 本节是 02 对上游 01 的**明确修改要求**，必须在 02 进入编码前由 01 完成（评审门禁 G2/G3 + 01 评审问题7）。01 当前代码 `app/model/{api/openai_api.py, local/vllm_local.py}` 的 `build_agentscope_config()` 仍输出**顶层 `temperature` / `stream`** 形态，不满足 AgentScope 配置契约。

### 6.1 锁定 AgentScope 版本（根因）

- 01 与 02 须在 `pyproject.toml` 显式锁定目标 AgentScope 版本（如 `agentscope==<目标版本>`），并写入 02 的测试依赖。
- 当前实际安装为 **2.0.5**，但 02/01 文档原假设为「v1」。**二者 API 不兼容**，必须二选一先拍板：
  - 若沿用文档原意的「v1」线（含 `agentscope.init` / `DialogAgent` / `generate_args`）：则 `pyproject` 须 pin 到对应旧版（如 `agentscope==0.1.x` 或 `1.x`），01 按 §6.2 的 **v1 形态** 改 `build_agentscope_config()`。
  - 若改用最新 **2.0.5**：则 02 的 agent 构建须改用 2.x API（无 `DialogAgent` / `msghub`），01 按 §6.2 的 **2.x 形态** 改 `build_agentscope_config()`；且 02 文档 §7/§10 的 agent 类名须整体替换为 2.x 对应类（编码期核对）。
- **无论选哪个版本**，02 的「方案 X」（模型调用走 `get_model().generate()`）均成立——它只依赖 01 的 `generate()`，不依赖 AgentScope 的模型初始化 API，因此版本不确定性不影响「02 必须调用 01」这一硬要求。

### 6.2 `build_agentscope_config()` 必须产出对齐版本的正确形态

**v1 目标形态（若锁定 v1 线）**——将 `temperature` / `stream` 移入 `generate_args`：

```python
def build_agentscope_config(self) -> dict:
    return {
        "model_type": "openai_chat",
        "config_name": self.cfg.model_name,
        "model_name": self.cfg.model_name,
        "api_key": self.cfg.api_key,
        "base_url": self.cfg.base_url,
        "generate_args": {
            "temperature": self.cfg.temperature,
            "stream": self.cfg.stream,
        },
    }
```

**2.x 目标形态（若锁定 2.0.5，已实测 `OpenAIChatModel` 接受的键）**——`type` / `credential` / `model` / `parameters`：

```python
def build_agentscope_config(self) -> dict:
    return {
        "type": "openai_chat",
        "credential": {
            "api_key": self.cfg.api_key,
            "base_url": self.cfg.base_url,
        },
        "model": self.cfg.model_name,
        "parameters": {
            "temperature": self.cfg.temperature,
        },
        "stream": self.cfg.stream,
    }
```

### 6.3 字段名与 `base_url` 键（评审 G3 + 01 评审问题7）

- `config_name` / `model_name` 是否都为必需、`base_url` 在配置里是顶层键还是 `credential`/`client_kwargs` 子键，**取决于锁定的版本**（见 §6.1）。01 须在锁版后，以该版本 `OpenAIChatModel`/`OpenAIChatWrapper` 实际接受的签名为准回填，闭环 01 评审问题7。
- 本地 vLLM 的 `base_url`（如 `http://localhost:8000/v1`）须与所选版本一致地透传（v1 顶层 `base_url`；2.x 置于 `credential.base_url`）。
