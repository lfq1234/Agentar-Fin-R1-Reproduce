## 2. 问题清单

### 问题1 〔门禁·中〕顶层 `timeout`/`max_retries` 成为死配置（技术文档内部不一致）
- **位置**：技术文档 §3.4（工厂）与 §3.5（YAML）不一致。
- **现象**：§3.5 把 `timeout: 120`、`max_retries: 2` 放在顶层 `model` 下（与 `api`/`local` 平级）；但 §3.4 工厂 `cls(ModelConfig(**section))` 传入的是 `model.api` / `model.local` 子段，这两段里**没有** `timeout`/`max_retries`。`ModelConfig`（§3.2）虽有这两个字段（带默认值），但工厂从不把顶层值传进去。
- **影响**：配置了超时/重试却永远不生效；后续线上排查超时问题会误以为配置生效。
- **建议**：二选一——
  - 将 `timeout`/`max_retries` 直接写进 `api`/`local` 各自子段；或
  - 工厂里做 merge：子段优先、顶层兜底（`{**顶层, **子段}`）。
  - 同时在验收标准中增加"超时/重试配置确实传入 `ModelConfig`"的检查。

### 问题2 〔低〕单测文件命名仅在技术文档指定，需求未对齐
- **位置**：需求文档 §4（未显式命名单测文件）/ 技术文档 §4 步骤7、§5（`tests/test_model.py`）。
- **现象**：需求文档 §4 只写"单测覆盖：get_model()…"，未给出文件名；技术文档指定 `tests/test_model.py`。两份文档对"建哪个测试文件"口径不一致。
- **建议**：需求文档 §4 补一句单测文件名为 `tests/test_model.py`，与技术文档对齐；若后续另有聚合测试，应显式说明，避免实现者猜测。

### 问题3 〔门禁·中〕核心方法 `generate()` 的实现策略仍未决策
- **位置**：技术文档 §6 风险（"本期 `generate()` 可作为兜底直连，主链路由 `services/` 经 AgentScope 调用（待 §02 服务层确认）"）。
- **现象**：本模块最关键的产出方法没有落地方案；需求文档 §4 验收标准也未规定 `generate()` 的行为。
- **影响**：编码时可能卡在"到底直连还是走 AgentScope"；验收无法闭环。
- **建议**：评审结论明确二选一——
  - **(a)** 本期 `generate()` 直接用 OpenAI SDK 直连（`api` 用真实 key，`local` 指向 vLLM 的 `/v1`）；`build_agentscope_config()` 仅作为给后续 AgentScope 的"配置导出"，不影响 `generate()` 行为；或
  - **(b)** `generate()` 本期返回 stub / 抛 `NotImplementedError`，真正生成等服务层接入 AgentScope 后补。
  - 并在需求文档 §4 增加一条对应验收项。

### 问题4 〔门禁·中〕异常类型 `ModelInvokeError` 只在需求提了，技术文档未设计
- **位置**：需求文档 §3 非功能约束（"调用失败应抛出可识别的异常，如 `ModelInvokeError`"）vs 技术文档 §3.2/§3.3（无异常类定义）。
- **现象**：技术文档未定义该异常类的位置（如 `app/model/exceptions.py` 或 `base.py`），`generate()` 在 key 缺失 / 网络失败 / 超时时的抛出行为也未规定；验收标准未覆盖异常。
- **建议**：技术文档补 `ModelInvokeError` 的定义位置与触发场景；验收标准增加"两模式在 key 缺失/网络失败时能抛出可识别异常"的检查。

### 问题5 〔低〕工厂对非法 `mode` 值静默回退
- **位置**：技术文档 §3.4 工厂（`mode != "local"` 一律走 api 的 else 分支）。
- **现象**：`mode` 写成 `local2`、`Api`（大小写）、拼写错时会静默回退到 api，难以排查。
- **建议**：非法 mode 显式抛 `ValueError` / 配置校验错误；在配置加载处即校验 `mode ∈ {api, local}`。

### 问题6 〔低〕两份文档均未声明本期新增依赖
- **位置**：需求文档 §3 / 技术文档（均无"依赖变更"小节）。
- **现象**：技术文档通篇未说明本期新增依赖（如 `generate()` 直连需 `openai` SDK，`build_agentscope_config` 导出需 `agentscope`）。两份文档都缺，属于共同遗漏而非冲突。
- **建议**：技术文档增加"依赖变更"小节，明确本期新增 `openai`（若走直连）和 `agentscope`（若需要）；并提示 `agentscope` 版本须编码前 `pip show` 核实（目前仅在 §6 风险提及，建议前移）。

### 问题7 〔门禁·中〕`build_agentscope_config` 字段名悬而未决，验收无法判定
- **位置**：技术文档 §3.3（输出字典含 `config_name` + `model_name`）与 §6 风险（`config_name` vs `model_name` 随版本变化）。
- **现象**：§3.3 自承"当前字段为设计预期，可能需微调"，而验收标准 §5 要求"返回合法 `openai_chat` 配置字典"——字段名不确定时该验收项无法判定通过。
- **建议**：评审结论要求——编码前用 `pip show agentscope` + 官方 tutorial 锁定 `openai_chat` 字段名，将确认结果回填到技术文档 §3.3，删除"可能需微调"的悬空表述，使验收标准可判定。

### 问题8 〔门禁·中〕需求文档内部表述矛盾："共用同一 wrapper 类型" vs "物理分离"
- **位置**：需求文档 §3 功能点（"`ApiModel` 与 `LocalModel` 共用同一 wrapper 类型"）vs 需求文档 §2 目标2（"`model/api/` 与 `model/local/` 两个文件夹物理分离，互不耦合"）。
- **现象**："共用同一 wrapper 类型"易被实现者理解为"只写一个具体类（如 `OpenAIChatModel`）"，与"物理分离、互不耦合"的目标相冲突。技术文档已折中处理为两个子类各在不同文件夹、逻辑相同仅 endpoint 不同，是合理的，但需求文档措辞会误导。
- **建议**：需求文档 §3 澄清表述——"两者共享同一抽象接口 `ModelInterface` 与同一份 `build_agentscope_config` 字段模板，但具体实现物理分离（各自文件夹、各自类）"，消除与目标2的张力。

## 3. 评审结论与门禁

**结论：有条件通过。**

进入编码前必须修复（门禁项）：**问题1、问题3、问题4、问题7、问题8**。
建议一并修复（非阻塞）：问题2、问题5、问题6。

理由：
- 问题1（死配置）与问题7（字段名悬空）属于"验收无法闭环"，不改则编码完也无法判定通过；
- 问题3（`generate()` 无落地方案）是本模块核心方法的实现阻塞点，必须二选一拍板；
- 问题4（需求声明了异常但技术未设计）与问题8（需求内部自相矛盾）属于"方向/契约性"问题，不改会误导实现或导致返工。
