## 4. 数据模型设计

### 4.1 持久化实体（`app/db/models.py`）

定义三个核心实体，承载会话与消息的落库：

- **User（用户）**：最小字段集——`id`（主键自增）、`username`（唯一、非空）、`email`、`created_at`、`updated_at`。03 不接鉴权，仅用于标识对话归属。
- **Conversation（会话）**：`id`、`user_id`（关联 User，级联删除）、`scene`（领域场景：Banking/Securities/Insurance/Trust/MutualFunds，可为空）、`title`、`created_at`、`updated_at`。用于聚合一次或多轮对话。
- **Message（消息）**：`id`、`conversation_id`（关联 Conversation，级联删除）、`role`（user/assistant/system）、`content`、`scene`（可空）、`created_at`。存储每轮用户与助手消息，支撑历史回溯。

> 字段类型、约束细节以 `app/db/schema.sql` 设计文档与编码期 ORM 定义为准。

### 4.2 接口契约（`app/routes/schemas.py`）

请求/响应以 Pydantic 模型约定，关键字段如下（具体字段在实现期定稿）：

- **ChatRequest**：`message`（必填）、`scene`（可选）、`user_id`（可选，临时方案，待鉴权后改 token 解析）、`conversation_id`（可选，续聊）。
- **ChatResponse**：`reply`、`conversation_id`（可为空）、`compliance_notes`（合规建议列表）、`risk_flags`（风险标记列表）。
- **AnalyzeRequest**：`message`、`scene`（可选）。
- **AnalyzeResponse**：`intent`、`slots`（字典）、`tool_plan`（列表）、`expression`。

## 5. DB 层设计（`app/db/`）

### 5.1 `session.py` 职责

- **引擎与会话**：根据 `config.db` 构建 SQLAlchemy 引擎与会话工厂（支持 `sqlite` 与 `postgresql` 两种 `db.type`）。
- **`init_db()`**：在 `db.enabled=true` 时初始化表结构（开发期以 ORM `create_all` 为主；生产以 `schema.sql` 落地版为准）。
- **`get_db` 依赖**：FastAPI 依赖项，每次请求提供一个会话并在结束时关闭。
- **`enabled` 门控**：`db.enabled=false` 时，引擎/会话不构建，`get_db` 产出 `None`；服务层据此短路落库逻辑，系统仍可在无数据库状态下启动并响应。
- **双轨建表一致性**：ORM 模型与 `schema.sql` 字段以 ORM 定义为单一事实来源，二者必须保持一致。

### 5.2 `schema.sql` 设计文档

作为"数据库新建设计文档"，描述核心表结构与字段规划（见同仓库 `app/db/schema.sql`），不含可执行 DDL；具体建表语句在编码阶段生成。

## 6. Services 层设计（`app/services/`）

服务层是 02 框架与 HTTP 之间的业务编排层。

### 6.1 `chat_service.py`

- 职责：`chat(message, scene, user_id, conversation_id)` 调用 02 的 `app/agent.run(structured=False)` 得到 `AgentResult`，取得 `reply` 与建议式 `compliance_notes` / `risk_flags`。
- 落库：当数据库可用且提供了 `user_id` 时，取得或创建会话，写入用户消息与助手消息，返回 `conversation_id`。
- 短路：数据库不可用时跳过落库，仍返回 `reply`。

### 6.2 `analyze_service.py`

- 职责：`analyze(message, scene)` 调用 `app/agent.run(structured=True)`，返回结构化四字段（`intent` / `slots` / `tool_plan` / `expression`）。

## 7. Routers 层设计（`app/routes/`）

- **`chat.py`**：传统 REST 风格，全部为 `async def` + `Depends(get_db)`。提供三个端点：
  - `GET /health`：健康检查，返回状态。
  - `POST /v1/chat`：聊天，调用 `chat_service.chat`。
  - `POST /v1/analyze`：结构化分析，调用 `analyze_service.analyze`。
- **`__init__.py`**：聚合 `APIRouter`，便于 `main.py` 统一挂载；后续多路由在此扩展。

## 8. Main 设计（`app/main.py`）

- **启动方式**：传统 FastAPI 应用，`lifespan` 启动钩子内完成"加载配置 +（启用时）`init_db()`"。
- **CORS**：从 `config.server.cors` 读取 origins / methods / headers 并注册。
- **路由挂载**：`include_router(api_router)` 挂载接口层。
- 不引入额外启动复杂度（如异步任务队列），保持"传统后端"定位。

## 9. 实现要点与步骤（设计层，编码期落地）

1. **`app/db/models.py`**：定义 `Base` + `User` / `Conversation` / `Message` 实体。
2. **`app/db/session.py`**：按 `config.db` 构建引擎/会话；实现 `init_db()`、`get_db`；`enabled=false` 短路。
3. **`app/db/schema.sql`**：按设计文档落地最终建表语句（或保持设计为 ORM 生成）。
4. **`app/routes/schemas.py`**：定义请求/响应 Pydantic 模型（§4.2）。
5. **`app/services/chat_service.py` + `analyze_service.py`**：调用 `app/agent.run()` 并实现落库逻辑。
6. **`app/routes/chat.py` + `__init__.py`**：实现 `/health`、`/v1/chat`、`/v1/analyze`。
7. **`app/main.py`**：实现 `lifespan` + CORS + `include_router`。
8. **单测**（`tests/`）：`/health` 断言；`db.enabled=false` 且无模型 key 时 `/v1/chat` 跳过真实调用。

## 11. 风险与待定

- **02 框架接口形态**：本设计按 02 规划调用 `app.agent.run(message, scene, structured)`，最终以 02 编码后的实际签名/返回结构（`AgentResult`）为准；若 02 改签名，03 同步调整。
- **DB 建表双轨**：开发期 ORM `create_all` 与生产 `schema.sql` 字段需保持一致（以 ORM 模型为单一事实来源）。
- **`user_id` 来源**：03 不接鉴权，`user_id` 由请求体携带（临时方案）；接鉴权后改为从 token 解析。
- **`agent_trace` 落库**：`schema.sql` 已预留设计，但 02 当前 `AgentResult` 不含 trace，03 不写；待 02 扩展 trace 后再接。
- **`model.mode=local` 依赖 vLLM**：同 01/02，开发期先 `api` 模式跑通。
