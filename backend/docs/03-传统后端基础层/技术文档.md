## 4. 数据模型设计

### 4.1 持久化实体（`app/db/models/`，SQLModel）

采用 **SQLModel**：在同一套类型上同时得到 SQLAlchemy ORM 表模型与 Pydantic 校验能力；表模型以 `table=True` 声明。模型与数据库连接（§5.1）同处 `app/db/models/` 文件夹，遵循"一个模型一个文件"的约定（与 01 的 `model/` 拆分风格一致）。

> **请求/响应契约同处 `app/db/models/`**：以**非 `table=True` 的 SQLModel** 承载 API 请求/响应（底层即 Pydantic，可直接作 FastAPI 请求体/响应体校验），与表模型同文件。共享字段抽为 `ConversationBase` / `MessageBase`，表模型与契约模型均继承之，字段只写一次（参考 tiangolo/full-stack-fastapi-template 的 Base 继承范式）。不再保留独立的 `app/schemas/`。

三个核心实体（字段以 `app/db/schema.sql` 实际 DDL 为准，二者一致）：

- **User（用户）**：`id`（主键自增）、`username`（唯一、非空）、`email`（可空）、`created_at`、`updated_at`。03 不接鉴权，仅用于标识对话归属；**`user_id` 入参即视为合法，未知 `user_id` 由服务层自动 upsert 创建（见 §6.1）**。
- **Conversation（会话）**：`id`、`user_id`（关联 User，级联删除）、`scene`（领域场景，可空）、`title`、`created_at`、`updated_at`。聚合一次或多轮对话；**会话级 `scene` 以首次创建请求为准**。
- **Message（消息）**：`id`、`conversation_id`（关联 Conversation，级联删除）、`role`（user/assistant/system）、`content`、`scene`（可空）、`created_at`。**消息级 `scene` 默认继承所属会话的 `scene`，仅当请求显式传 `scene` 时才覆盖该条消息**（见 §6.1）。

- **时间字段默认**：`created_at` 默认当前时间（`datetime.utcnow` 或等价），`updated_at` 在更新时刷新；SQLite/PostgreSQL 双轨下统一在应用侧写入 UTC，避免 `CURRENT_TIMESTAMP` 时区差异。

### 4.2 接口校验模型（非表 SQLModel，与表模型同文件）

请求/响应契约承载在 `app/db/models/` 的**非表 SQLModel** 上（底层即 Pydantic，可直接作 FastAPI 请求体/响应体校验），与表模型同文件、无需独立 `app/schemas/`。关键契约：

- **`ConversationBase`（共享字段）**：`scene`（可选，会话级场景）。
- **ChatRequest**（继承 `ConversationBase`）：`message`（必填）、`scene`（可选）、`user_id`（可选，临时方案，待鉴权后改 token 解析）、`conversation_id`（可选，续聊）。
- **ChatResponse**（继承 `ConversationBase`）：`reply`、`conversation_id`（可为空）、`compliance_notes`（合规建议列表）、`risk_flags`（风险标记列表）；`scene` 回显会话级场景。
- **`MessageBase`（共享字段）**：`scene`（可选）。
- **AnalyzeRequest**（继承 `MessageBase`）：`message`、`scene`（可选）。
- **AnalyzeResponse**（继承 `MessageBase`）：`intent`、`slots`（字典）、`tool_plan`（列表）、`expression`；`scene` 回显被分析请求的场景。

> 设计要点：持久化表模型与 API 契约统一用 SQLModel，共享字段由 `ConversationBase` / `MessageBase` 承载，避免字段重复声明。
> 来源契约（已锁定）：`app/agent.run()` 返回 `AgentResult`（`app/agent/system.py`，评审问题4 已锁定终审签名/字段），字段 `reply` / `compliance_notes` / `risk_flags` / `intent` / `slots` / `tool_plan` / `expression` 与上方 `ChatResponse` / `AnalyzeResponse` 一一对应；03 仅依赖该已文档化契约，不做未声明字段假设。

## 5. DB 层设计（`app/db/`）

### 5.1 `app/db/models/connection.py` 职责（与模型同文件夹，异步）

- **异步引擎与会话**：基于 SQLAlchemy 异步扩展（`sqlalchemy.ext.asyncio`），按 `config.db` 构建 `AsyncEngine` 与 `async_sessionmaker`（`AsyncSession`，`expire_on_commit=False`）。`db.type=sqlite` 自动使用 `sqlite+aiosqlite://` 驱动；`db.type=postgresql` 自动规整为 `postgresql+asyncpg://` 驱动（见 §11 依赖清单）。SQLite 下监听底层 `sync_engine` 的 `connect` 事件注册 `PRAGMA foreign_keys=ON` 以满足级联删除。
- **`init_db()`（异步）**：`db.enabled=true` 时 `await` 在引擎上 `run_sync(SQLModel.metadata.create_all)` 初始化表结构（开发/测试期以 ORM 建表为主；**生产环境以 `app/db/schema.sql` 的可执行 DDL 为准**，部署时执行该脚本建表，见 §5.2）。
- **`get_db` 依赖（异步生成器）**：`AsyncGenerator[AsyncSession | None, None]`；每次请求 `async with` 一个 `AsyncSession` 并在结束时关闭；`db.enabled=false` 时产出 `None`。
- **`enabled` 门控**：`db.enabled=false` 时引擎/会话不构建，`get_db` 产出 `None`；服务层据此短路落库，系统仍可在无数据库状态下启动并响应。
- **双轨建表一致性**：SQLModel 模型（§4.1）与 `schema.sql`（§5.2）字段以 SQLModel 模型为单一事实来源，二者必须保持一致（验收 §10 含一致性核查）。

### 5.2 `app/db/schema.sql`（单独文件，可执行 DDL）

作为**可执行的生产建表脚本**（含 users / conversations / messages 三表的 `CREATE TABLE` + 索引 + agent_traces 预留 + SQLite/PostgreSQL 适配说明），**单独存放于 `db/` 根，不纳入 `models/` 文件夹**。开发/测试期可用 ORM `create_all` 代建；SQLModel 模型（§4.1）为单一事实来源，`schema.sql` 必须与其字段保持一致。文件顶部注释给出 PostgreSQL 适配差异（如 `BIGSERIAL`、TIMESTAMPTZ、JSONB）。

## 6. Services 层设计（`app/services/`）

服务层是 02 框架与 HTTP 之间的业务编排层，全部为 `async`，调用 02 的 `async run()` 时必须 `await`。

### 6.1 `chat_service.py`

- 职责：`async chat(req, db)` **`await`** 02 的 `app/agent.run(structured=False)` 得到 `AgentResult`，取得 `reply` 与建议式 `compliance_notes` / `risk_flags`。
- 落库：当数据库可用**且**提供了 `user_id` 时——
  - (a) **upsert `User`**：未知 `user_id` 自动创建 `User` 行（不抛错，username 取 `user_{id}`）；
  - (b) **取得或创建会话**：`conversation_id` 提供则加载现有会话（不存在则新建），否则新建会话，`scene` 以本次/首次请求为准；
  - (c) **写入两条 `Message`**：`role=user` 的用户消息与 `role=assistant` 的回复；消息级 `scene` 默认继承会话 `scene`，仅显式传参时覆盖；返回 `conversation_id`。
- 短路：数据库不可用**或** `user_id` 为空时跳过落库，仍返回 `reply`（`conversation_id` 为 `None`）。

### 6.2 `analyze_service.py`

- 职责：`async analyze(req)` **`await`** `app/agent.run(structured=True)`，返回结构化四字段（`intent` / `slots` / `tool_plan` / `expression`）；`analyze` 不落库。

## 7. Routers 层设计（`app/routes/`）

- **`chat.py`**：传统 REST 风格，全部为 `async def` + `Depends(get_db)`；路由函数声明 `db: AsyncSession | None`（由 `get_db` 在 `db.enabled=false` 时返回 `None`），服务层据此短路落库。提供三个端点：
  - `GET /health`：健康检查，返回状态。
  - `POST /v1/chat`：聊天，调用 `chat_service.chat`（传入 `db`）。
  - `POST /v1/analyze`：结构化分析，调用 `analyze_service.analyze`。
- **校验来源**：请求/响应使用 `app/db/models/` 下的**非表 SQLModel** 模型——`ChatRequest` / `ChatResponse` 在 `conversation.py`，`AnalyzeRequest` / `AnalyzeResponse` 在 `message.py`。SQLModel 底层即 Pydantic，非表模型天然兼作 FastAPI 请求体/响应体校验，无需独立 `app/schemas/`。
- **`__init__.py`**：聚合 `APIRouter`，便于 `main.py` 统一挂载；后续多路由在此扩展。

## 8. Main 设计（`app/main.py`）

- **启动方式**：传统 FastAPI 应用，`lifespan` 启动钩子内完成"加载配置 +（启用时）`init_db()`"。
- **CORS**：从 `config.server.cors` 读取 origins / methods / headers 并注册（配置缺失时回退为 `*`，与旧行为兼容）。
- **路由挂载**：`include_router(api_router)` 挂载接口层（含 `/health`、`/v1/chat`、`/v1/analyze`）。
- 不引入额外启动复杂度（如异步任务队列），保持"传统后端"定位。

## 9. 实现要点与步骤（设计层，编码期落地）

1. **`app/db/models/`**：用 SQLModel 定义 `User` / `Conversation` / `Message` 表模型（各一文件），并以 `ConversationBase` / `MessageBase` 承载共享字段（表模型与 `Chat*/Analyze*` 契约均继承之）；`connection.py` 实现**异步**引擎/会话/`get_db`/`init_db` 与 `enabled` 门控（SQLite 启用外键 PRAGMA）。
2. **`app/db/schema.sql`**：落地**可执行建表 DDL**（三表 `CREATE TABLE` + 索引 + agent_traces 预留 + SQLite 适配），与 SQLModel 模型字段保持一致；保持为 `db/` 下独立文件，作为生产建表脚本。
3. **契约模型（非表 SQLModel，位于 `app/db/models/`）**：`conversation.py` 的 `ChatRequest` / `ChatResponse`、`message.py` 的 `AnalyzeRequest` / `AnalyzeResponse` 承载 §4.2 契约，无需独立 `app/schemas/`。
4. **`app/services/chat_service.py` + `analyze_service.py`**：`async` 实现，`await app/agent.run()`；`chat_service._persist` 在 `AsyncSession` 上 `await` 提交/刷新，实现 `User` upsert + 会话取得/创建 + 消息落库（含 `scene` 继承规则），`analyze_service` 返回结构化四字段（不落库）。
5. **`app/routes/chat.py` + `__init__.py`**：实现 `/health`、`/v1/chat`、`/v1/analyze`，均为 async，引用 `app/db/models` 契约，`db` 声明为 `AsyncSession | None`。
6. **`app/main.py`**：实现 `lifespan`（内 `await init_db()`）+ CORS（取自 `config.server.cors`）+ `include_router`。
7. **单测**（`tests/`）：`/health` 断言；`db.enabled=false` 且无模型 key 时通过注入 fake `run` 跳过真实调用验证 `/v1/chat`；DB 启用态单测（异步引擎 + `StaticPool`）验证新 `user_id` 首次请求能成功落库会话与消息。

## 11. 风险与待定

- **DB 建表双轨**：开发/测试期 ORM `create_all` 与生产 `schema.sql` 字段需保持一致（以 SQLModel 模型为单一事实来源）；生产部署以 `schema.sql` 为准，编码期保证二者字段一致。
- **`user_id` 来源**：03 不接鉴权，`user_id` 由请求体携带（临时方案）；接鉴权后改为从 token 解析。落库采用 upsert（未知 `user_id` 自动建 `User`），不强制调用方预先建用户。
- **`agent_trace` 落库**：`schema.sql` 已预留 `agent_traces` 表，但 02 当前 `AgentResult` 不含 trace，03 不写；待 02 扩展 trace 后再接。
- **异步驱动依赖**：SQLite 异步需 `aiosqlite`（已加入 `pyproject` 依赖）；PostgreSQL 异步需 `asyncpg`（`db.type=postgresql` 时启用，`connection.py` 自动规整 URL 为 `postgresql+asyncpg://`）。
- **数据库迁移（Alembic）**：当前建表走"SQLModel `create_all`（开发/测试）+ `schema.sql`（生产）"双轨，字段以 SQLModel 模型为单一事实来源。**迁移工具（Alembic）暂未接入**——研究/复现项目规模无需版本化迁移，待后续需要可控 schema 演进时再补（保留 `schema.sql` 作为生产建表脚本即可）。
- **SQLModel 选型**：SQLModel 同时提供 ORM 与 Pydantic 能力；接口层契约以**非表 SQLModel** 直接承载（底层即 Pydantic，可作 FastAPI 请求/响应校验），与表模型同文件、共享 `ConversationBase` / `MessageBase`，无需独立纯 Pydantic 校验层（见 §4.2）。
- **`model.mode=local` 依赖 vLLM**：同 01/02，开发期先 `api` 模式跑通。

## 12. 依赖变更（本期新增）

- `sqlmodel>=0.0.16`：ORM + Pydantic 统一（兼容 Pydantic v2，编码前以 `pip show sqlmodel pydantic` 核实版本匹配）。
- `sqlalchemy`：随 `sqlmodel` 间接引入；异步连接使用其 `sqlalchemy.ext.asyncio` 扩展。
- `aiosqlite>=0.19`：**异步 SQLite 驱动**（`sqlite+aiosqlite://`），开发/测试默认启用，已加入 `pyproject` 依赖。
- `asyncpg>=0.29`：**异步 PostgreSQL 驱动**（`postgresql+asyncpg://`，`db.type=postgresql` 时启用），已加入 `pyproject` 依赖；`connection.py` 自动规整 URL 驱动。
- 既有依赖（`fastapi` / `uvicorn` / `pydantic` / `pyyaml` / `httpx` / `openai` / `agentscope`）保持不变。
