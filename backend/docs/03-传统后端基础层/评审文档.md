## 2. 问题清单

### 问题1 〔门禁·中〕`schema.sql` 定位自相矛盾："不含可执行 DDL" vs "生产以落地版为准"
- **位置**：需求 §2 目标5 / §3 功能点（"**不含可执行 DDL**"）↔ 技术 §5.1（"**生产以 `schema.sql` 落地版为准**"）、§5.2（"**不含可执行 DDL**，具体建表语句在编码阶段生成"）。
- **现象**：同一份文件被同时描述为"纯设计文档、无 DDL"和"生产建表依据、落地版 SQL"。验收标准（需求 §4 / 技术 §10）要求 `schema.sql` "含三张核心表 + agent_traces 预留 + SQLite 适配说明"——若它不含可执行 DDL，"含三张核心表"究竟指"设计描述"还是"可执行的 `CREATE TABLE`"无法判定。
- **影响**：编码者不清楚该文件到底要不要写 `CREATE TABLE`；验收时"表结构是否齐备"无法闭环判定。
- **建议**：二选一并在两份文档同步——
  - **(a)** 定位为**设计文档**：明确写明"仅表结构与字段规划/SQLite 适配说明，不含可执行 DDL，生产建表由 ORM `create_all` 或迁移工具生成"，并把验收中"含三张核心表"改为"含三张表的字段规划描述"；
  - **(b)** 定位为**可执行 DDL**：写明 `schema.sql` 是生产用建表脚本（`CREATE TABLE` + 索引 + SQLite 适配），删除"不含可执行 DDL"的表述，明确它在生产环境如何被执行（手动执行 / 迁移工具）。

### 问题2 〔门禁·中〕双轨建表"或保持设计为 ORM 生成"留下未决选择，验收无法闭环
- **位置**：技术 §9 步骤2（"按设计文档落地最终建表语句（**或保持设计为 ORM 生成**）"）↔ 技术 §5.1/§11（"以 SQLModel 模型为单一事实来源，二者必须保持一致"）。
- **现象**：开发期用 ORM `create_all`、生产用 `schema.sql` 是两条建表路径；但文档又允许"或保持设计为 ORM 生成"，即 `schema.sql` 可能只是设计、生产也走 ORM。这是把"建表以谁为准"的拍板权推给实现者，而验收标准 §10 既要求 `schema.sql` 文件存在又要求 ORM 模型齐备，二者关系未锁死。
- **影响**：易产生字段漂移（手写 `schema.sql` 与 SQLModel 不同步）；且"双轨一致"在没有生成机制约束时只能靠人工核对。
- **建议**：明确二选一——
  - **(a)** `schema.sql` 为**唯一生产 DDL 来源**，编码期由 SQLModel 模型**反向生成**并人工校订（如 `sqlmodel.metadata.create_all` 导出 / Alembic），杜绝手写漂移；或
  - **(b)** 本期**生产也用 ORM `create_all`**，`schema.sql` 仅作设计留档、不进部署流程，验收相应弱化对其可执行性的要求。
  - 并在验收标准增加"SQLModel 模型字段与 `schema.sql` 经比对一致"的核查项。

### 问题3 〔门禁·中〕`analyze_service` "或并入 chat_service" 悬空决策
- **位置**：需求 §3 功能点（"`analyze_service.py`（**或并入 chat_service**）"）↔ 技术 §3/§6.2/§9 步骤4（明确两文件 `chat_service.py` + `analyze_service.py`）。
- **现象**：需求给实现者留了"可合并"的选项，技术文档已按"两个独立文件"落地设计。两份文档对结构口径不一致，若实现者按需求选了"并入"，则技术文档的目录结构、验收项全部失效。
- **影响**：模块结构未定，编码与验收无法对齐。
- **建议**：需求 §3 删除"或并入 chat_service"的开放性表述，直接采用技术文档的"两文件分离"方案（二者职责清晰、符合"一个服务一个文件"风格）；若确需合并，应在技术文档同步改为单文件并相应调整验收。

### 问题4 〔门禁·中〕上游 02 接口契约（`run` 签名 / `AgentResult` 字段）未锁定，03 编码存在阻塞依赖
- **位置**：技术 §6.1/§6.2（调用 `app.agent.run(message, scene, structured)`、读取 `reply`/`compliance_notes`/`risk_flags`/`intent`/`slots`/`tool_plan`/`expression`）↔ 技术 §11 风险（"最终以 02 编码后的实际签名/返回结构（`AgentResult`）为准；若 02 改签名，03 同步调整"）。
- **现象**：03 几乎所有的服务层与响应契约都建立在 02 的 `AgentResult` 上，但 02 自身仍在评审/编码中，签名与字段名尚未终审。技术文档既按预期字段写死（§4.2、`ChatResponse`/`AnalyzeResponse`），又自承"可能随 02 调整"，验收标准 §10 也要求"调用 02 `run()` 并落库"——契约未定时该验收项无法判定。
- **影响**：02 一旦改签名/字段，03 服务层与 4 个 Pydantic 响应模型需连带返工；当前直接按预期字段编码风险高。
- **建议**：评审结论要求二选一——
  - **(a)** 编码 03 前，由 02 文档回填**终审版** `run()` 签名与 `AgentResult` 字段清单到技术文档 §4.2/§6，删除"可能随 02 调整"的悬空表述；或
  - **(b)** 03 在 `services/` 内定义一层**适配/映射函数**，把 02 返回结构显式映射为 03 自己的 `ChatResponse`/`AnalyzeResponse`，将 02 的契约漂移隔离在适配层内，降低返工面。
  - 同时验收标准增加"03 仅依赖 02 文档化契约、不假设未声明字段"的核查。

### 问题5 〔门禁·中〕`chat` 落库时 `User` 实体的创建/查找语义未定义
- **位置**：技术 §6.1（"当数据库可用且提供了 `user_id` 时，取得或创建会话，写入用户消息与助手消息"）↔ 需求 §2（"用户表先留最小字段，不接登录"）/ §3（无创建用户的端点）。
- **现象**：落库前提是"提供了 `user_id`"，但全模块**没有任何创建 `User` 的接口**；当请求携带一个库里尚不存在的 `user_id` 时，行为完全未定义——是自动 upsert 创建 `User`、还是 400/忽略、`Conversation.user_id` 外键如何满足，均未说明。`User` 模型字段（§4.1）与"最小字段"的措辞也缺乏对"user_id 由谁产生"的解释。
- **影响**：这是 03 唯一的新实体写入路径盲区，编码时必然在此卡住或各写各的；外键约束（Conversation→User 级联删除）在无 User 行时会直接写库失败。
- **建议**：明确规则——
  - `user_id` 入参即视为"已存在或允许自动建"；服务层对未知 `user_id` 执行 upsert（不存在则创建 `User` 再建会话），或明确约定"调用方须先有 user_id，03 不负责建用户"并补充前置约束；
  - 在 技术 §6.1 补一句"未知 `user_id` 的处理（upsert / 报错）"；验收增加"首次携带新 `user_id` 能成功落库会话与消息"的用例。

### 问题6 〔中〕`scene` 在 `Conversation` 与 `Message` 双字段的归属/覆盖规则未定义
- **位置**：技术 §4.1（`Conversation.scene` 可空、`Message.scene` 可空）↔ 技术 §6.1（续聊时取/建会话）。
- **现象**：`scene`（领域场景）同时存在于会话级与消息级，但文档未说明二者的关系：新建会话时 `scene` 取自请求还是置空？续聊（`conversation_id` 提供）时新消息的 `scene` 是否覆盖会话级 `scene`？按会话过滤还是按消息过滤？这些都会影响后续按场景检索/统计的正确性。
- **影响**：数据语义歧义，续聊场景下场景归属易错乱。
- **建议**：在技术 §4.1 补充规则，如"会话级 `scene` 以首次请求为准、后续消息 `scene` 默认继承会话值、显式传参可覆盖消息级"；并明确查询维度以哪一级为准。

## 3. 非阻塞问题（建议一并修复）

### 问题7 〔低〕Services 是否 `async` 未明确
- **位置**：需求 §3（`async chat(...)` / `async analyze(...)`）↔ 技术 §6（未标注 `async`，也未出现 `await app.agent.run(...)`）。
- **现象**：路由均为 `async def + Depends(get_db)`，而 services 调用的 `run()` 是 `async`（需求 §1 明确 `async run`）。若 service 不标 `async` 且不 `await`，会漏掉协程或混入同步 DB 阻塞。技术文档应显式声明 `chat_service`/`analyze_service` 为 `async` 并 `await run()`。
- **建议**：技术 §6 标注 `async` 并在调用处写明 `await`；保持与需求一致。

### 问题8 〔低〕本期新增依赖与版本风险未声明
- **位置**：需求 §3 / 技术文档（均无"依赖变更"小节）。
- **现象**：本期引入 `sqlmodel`、`fastapi`/`uvicorn`、`pydantic` 等，但文档未列；尤其 **SQLModel 与 Pydantic v2 的兼容性**需核实（SQLModel 较新版本才完整支持 Pydantic v2），若项目基础环境是 Pydantic v1/v2 混用，ORM 与 `app/schemas/` 纯 Pydantic 会出现行为差异。
- **建议**：技术文档增加"依赖变更"小节，列出 `sqlmodel`/`fastapi`/`uvicorn` 及版本，并在编码前 `pip show sqlmodel pydantic` 核实兼容性（同 01 文档对 `agentscope` 的核实要求）。

### 问题9 〔低〕`enabled=false` 短路下路由 `db` 参数与测试 skip 真实调用的 seam 未说明
- **位置**：技术 §5.1（`get_db` 产出 `None`）↔ §9 步骤7 / 验收（"`db.enabled=false` 且无模型 key 时 `/api/v1/chat` 跳过真实调用"）。
- **现象**：路由用 `Depends(get_db)`，禁用时 `db=None`，但路由函数签名是否 `Optional[Session]`、service 如何判空短路需写明；另外"无 key 时跳过真实 agent 调用"需要测试 seam（如环境变量开关或 `monkeypatch`），文档未给出机制，单测难以稳定 skip。
- **建议**：技术 §7 明确路由 `db: Optional[Session] = Depends(get_db)` 及 service 的 `if db is None: 跳过落库`；§9/验收补充"测试通过注入 mock / 环境变量跳过 `run()`"的具体做法。

### 问题10 〔低〕`created_at` / `updated_at` 默认值策略未指定
- **位置**：技术 §4.1（`User`/`Conversation`/`Message` 均含 `created_at`/`updated_at`）。
- **现象**：未说明是 Python 侧 `default=datetime.utcnow` 还是数据库 `server_default`，`updated_at` 是否自动刷新也未约定；现已明确**仅 SQLite 后端**，统一在应用侧写入 UTC。
- **建议**：在技术 §4.1 补一句默认策略（推荐 `created_at` 默认当前时间、`updated_at` 在更新时刷新）。

### 问题11 〔低〕旧 `app/models/schemas.py` 的清理责任未说明
- **位置**：技术 §2（"旧 `app/models/schemas.py`……编码期由 `app/schemas/` 取代，不再使用"）↔ 需求 §3 目标3。
- **现象**：只说"不再使用"，未说是否删除、由谁删除、是否保留防误引用；脚手架遗留文件若残留，可能被新人不小心 import。
- **建议**：明确"编码阶段删除旧 `app/models/schemas.py`"或"保留但标记 deprecated 并确认无引用"。

## 5. 亮点（值得保留）

- **消费方定位清晰**：03 明确"只接 02、不重写智能体"，分层（DB / Services / Routers / Main）职责边界干净，符合"上层只依赖抽象"的解耦目标。
- **`db.enabled` 门控设计务实**：无数据库也能启动并响应 `/api/v1/chat`，利于本地联调与降级，是很好的工程化取舍。
- **SQLModel 持久化 + 纯 Pydantic 契约分离**：避免 ORM 模型直接泄漏到接口层，分工说明（§4.2/§11）到位。
- **风险章节诚实**：技术 §11 把 02 接口形态未定、`agent_trace` 预留、SQLModel 选型、`local` 依赖 vLLM 等不确定性都标了出来，没有掩盖。
- **需求与技术章节可对应**，便于追溯；不在本次范围（鉴权、RAG、trace 落库、SSE）也划得清楚，避免范围蔓延。
