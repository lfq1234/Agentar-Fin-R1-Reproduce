## 1. 背景与诉求

前序模块已就位（规划层面）：
- **01-模型接口**：API / 本地双模式统一入口 `get_model()`。
- **02-多智能体基础框架**：AgentScope 多智能体框架，主体位于 `app/agent/`，对外暴露 `async run(message, scene, structured) -> AgentResult`（含 `reply` / `compliance_notes` / `risk_flags` / 结构化四字段 `intent` / `slots` / `tool_plan` / `expression`）。**该契约已在 `app/agent/system.py` 终审落地**（评审问题4 已关闭），03 仅依赖此已文档化契约。

但当前后端只有骨架：`routes/chat.py`、`services/inference.py` 是 stub，且没有真正的数据库与启动装配。本需求搭建**传统后端基础层**——把 02 的框架通过标准 FastAPI + 数据层链路对外提供服务并持久化，是"把 AgentScope 框架接进工程化后端"的那一层。

> 注意：03 是**消费方**，不重新实现多智能体逻辑；它调用 02 的 `app/agent.run()`，只负责 HTTP 接入、业务编排与落库。

## 2. 目标与范围

- 目标 1（DB 层）：采用 **SQLModel** 统一管理 ORM 模型与数据库连接——`app/db/models/` 文件夹内同时放置表模型（`User` / `Conversation` / `Message`，各一文件）与连接模块（引擎/会话/`get_db`/`init_db`，`enabled` 门控）；建表 SQL 脚本 `app/db/schema.sql` 作为 `db/` 下的独立文件，不纳入 `models/` 文件夹。
- 目标 2（Services 层）：封装 `chat` / `analyze` 服务，调用 02 的 `app/agent.run()`，并把会话与消息落库。
- 目标 3（Routers 层）：传统 REST 接口 `/health`、`/v1/chat`、`/v1/analyze`；请求/响应校验模型（`ChatRequest` / `ChatResponse` / `AnalyzeRequest` / `AnalyzeResponse`）以**非表 SQLModel** 形式与表模型同处 `app/db/models/`，复用 SQLModel 的 Pydantic 校验能力，不再维护独立的 `app/schemas/`。
- 目标 4（Main）：传统 FastAPI 启动——`lifespan` 内加载配置 +（按需）初始化 DB、注册 CORS（取自 `config.server.cors`）、挂载路由。
- 目标 5（SQL 脚本）：`app/db/schema.sql` 作为**可执行的生产建表脚本**（含 `CREATE TABLE` + 索引 + SQLite 适配说明，覆盖 users / conversations / messages 三张核心表 + agent_traces 预留）；开发/测试期也可用 ORM `create_all` 建表，字段以 SQLModel 模型为单一事实来源。

**不在本次范围（后续独立需求）**：
- 鉴权 / 多租户（用户表先留最小字段，不接登录）。
- 真实 RAG 向量库（02 占位，检索后端后续）。
- `agent_trace` 轨迹采集与存储（表结构预留，03 不写）。
- SSE 流式响应（后续需求）。
- 02 框架本身的实现（属 02 编码阶段）。

## 3. 功能 / 非功能要求

- 功能点：
  - **DB 层**（`app/db/`，SQLModel，异步）：
    - `models/connection.py`：**异步**引擎/`async_session_maker`/`get_db` 依赖（`AsyncSession`）；`init_db()`（异步）在 `db.enabled` 时通过 SQLModel 建表；`enabled=false` 短路。
    - `models/user.py`、`models/conversation.py`、`models/message.py`：`User` / `Conversation` / `Message` SQLModel 表模型（各一文件）；`conversation.py` / `message.py` 额外以 `ConversationBase` / `MessageBase` 承载共享字段，表模型与 `Chat*` / `Analyze*` 契约均继承之。
    - `schema.sql`（`db/` 下独立文件）：**可执行建表 DDL**（users / conversations / messages 三表的 `CREATE TABLE` + 索引 + SQLite 适配说明 + agent_traces 预留）；开发/测试期也可由 ORM `create_all` 代建，二者字段以 SQLModel 模型为准保持一致。
  - **Services 层**（`app/services/`，异步）：
    - `chat_service.py`：`async chat(message, scene, user_id, conversation_id=None)` → **`await`** `app/agent.run()` 得 `AgentResult`，落库用户消息 + 助手消息，返回 `reply`（及建议式 `compliance_notes` / `risk_flags`）。落库语义：`user_id` 入参即视为合法，未知 `user_id` 自动 upsert 创建 `User` 后再建/取会话；`db` 不可用或 `user_id` 为空时跳过落库，仅返回 `reply`（`conversation_id` 为 `None`）。
    - `analyze_service.py`（**独立文件，不与 chat_service 合并**）：`async analyze(message, scene)` → **`await`** `run(structured=True)`，返回结构化四字段（`analyze` 不落库）。
  - **Routers 层**（`app/routes/`，契约模型同处 `app/db/models/`）：
    - 请求/响应契约（`ChatRequest` / `ChatResponse` / `AnalyzeRequest` / `AnalyzeResponse`）以**非表 SQLModel** 承载，位于 `app/db/models/`，不再维护独立 `app/schemas/`。
    - `chat.py`：`GET /health`、`POST /v1/chat`、`POST /v1/analyze`（均为传统 `async def` + `Depends(get_db)`，路由函数声明 `db: AsyncSession | None`，引用 `app/db/models` 契约）。
    - `__init__.py`：聚合 `APIRouter`。
  - **Main**（`app/main.py`）：`lifespan` 启动钩子、`FastAPI()` 实例、CORS（取自 `config.server.cors`）、`include_router`。
- 非功能：
  - 复用 01 / 02：模型切换（`model.mode`）、agent 框架对 03 透明；03 仅依赖 `app/agent.run()` 的已文档化 `AgentResult` 契约。
  - 异步一致：Services 层为 `async`，调用 02 的 `async run()` 时必须 `await`；Routers 为 `async def + Depends(get_db)`。
  - `scene` 归属规则：会话级 `scene` 以首次创建请求为准；消息级 `scene` 默认继承所属会话的 `scene`，仅当请求显式传 `scene` 时才覆盖该条消息。
  - `db.enabled=false` 时：DB 相关调用短路（内存态 / 不落库），服务仍可用。
  - 可测性：`/health` 断言；`/v1/chat` 在 `db.enabled=false` 或无模型 key 时可通过注入 fake `run` 跳过真实调用。

## 4. 验收标准

- [ ] `app/db/models/` 含 `connection.py`（引擎/会话/`get_db`/`init_db` + `enabled` 门控）+ `user.py` / `conversation.py` / `message.py`（SQLModel 表模型，各一文件）；`app/db/schema.sql` 为 `db/` 下独立文件且**含可执行 `CREATE TABLE` DDL**（三张核心表 + agent_traces 预留 + SQLite 适配说明），与 SQLModel 模型字段经比对一致。
- [ ] `app/services/` 含 `chat` / `analyze` 服务（`async`，`await run()`），调用 02 的 `app/agent.run()`；`chat` 在 `db` 可用且提供 `user_id` 时落库（未知 `user_id` 自动 upsert），`db` 不可用或 `user_id` 为空时跳过落库仍返回 `reply`。
- [ ] 契约模型：`ChatRequest` / `ChatResponse` / `AnalyzeRequest` / `AnalyzeResponse` 为**非表 SQLModel**（位于 `app/db/models/`，复用 `ConversationBase` / `MessageBase`）；`app/routes/chat.py` 提供 `/health`、`/v1/chat`、`/v1/analyze`，为传统 REST（async + `Depends(get_db)`，路由 `db` 声明为 `AsyncSession | None`，引用 `app/db/models` 契约）。
- [ ] `app/main.py` 为传统启动：`lifespan` 加载配置 +（启用时）初始化 DB、注册 CORS（取自 `config.server.cors`）、挂载路由。
- [ ] `config.db.enabled=false` 时整体不依赖数据库即可启动并响应 `/v1/chat`。
- [ ] `pytest`：无 `OPENAI_API_KEY`、无 vLLM、`db.enabled=false` 时 `/health` 与（注入 fake `run` 跳过真实调用）的 `/v1/chat` 仍能跑；且新 `user_id` 首次请求能成功落库会话与消息（DB 启用态单测覆盖）。
