## 5. 发现的问题与修复

### 🐛 Bug-1（阻断性）：`ReActAgent.finish` 缺 `response` 参数 → `KeyError: 'response'`
- **现象**：任何 `/api/v1/chat`、`/api/v1/analyze` 均 500。栈顶：
  `agentscope/agents/_react_agent.py` 第 216 行 `tool_call["input"]["response"]` → `KeyError: 'response'`。
- **根因**：AgentScope 0.1.6 的 `ReActAgent._acting` 对 `finish` 工具**硬读** `tool_call["input"]["response"]`。弱模型 qwen3-0.6b 的 ReAct 格式保真度不足，常以缺 `response` 字段的方式调用 `finish`，触发崩溃。这解释了 02 模块此前**从未真正端到端跑通**（技术文档亦自陈「未实际起服务联调」）。
- **修复**（`app/agent/agents.py`，`ReActAgentX`）：覆写 `_acting`，对 `finish` 分支做容错——缺 `response` 时从智能体记忆回退到最近一条非空消息作为答案，正常（强模型）路径不受影响。
- **连带修复**：覆写中引用了 `Msg`，但 `agents.py` 原先未导入 → 暴露 `NameError: name 'Msg' is not defined`。已补 `from agentscope.message import Msg`。

### 🛡️ 加固：限制 `ReActAgent.max_iters=5`
- **原因**：弱模型可能不调用 `finish` 而空转；AgentScope 默认 `max_iters=10`。联调中将上限收到 5，避免单轮对话无限循环拖垮延迟（同时是合理的生产护栏）。
- **位置**：`ReActAgentX.__init__` 透传 `max_iters=5`。

### ✅ 文档核对（澄清误报）
- 技术文档称路由为 `/api/health`、`/api/v1/chat`、`/api/v1/analyze`（统一 `/api` 前缀），**与实际代码 `app/main.py: include_router(prefix="/api")` 一致**。此前曾怀疑文档与代码前缀不符，经核对**文档无误**，无需改动。

### 🐛 Bug-2（接口健壮性）：`ModelInvokeError` 未转译为 HTTP 错误，直接外泄栈
- **现象**：自动化用例 `test_degradation_when_model_down`（模型死端点）预期返回 5xx，实际 `client.post` 直接抛出 `app.model.exceptions.ModelInvokeError`，测试被判失败。
- **根因**：`01` 统一异常 `ModelInvokeError` 在 `02`/`services` 层已按「评审 N2：上抛不静默」设计原样抛出，但 `app/routes/chat.py` 的端点未注册顶层异常处理器；FastAPI `TestClient` 默认 `raise_server_exceptions=True`，于是异常穿透为原始栈而非 HTTP 响应。这是**暴露给调用方的接口缺陷**（真实客户端也会拿到 500 跟踪而非干净错误体）。
- **修复**（`app/main.py`）：注册全局 `@app.exception_handler(ModelInvokeError)`，统一返回 `JSONResponse(500, {"error":"model_invoke_failed","detail": ...})`。修复后降级用例拿到干净的 5xx + 含 `vLLM`/`模型` 关键字的文案，符合断言。

### 🐛 Bug-3（阻断性，根因级）：`FastAPI(...)` 漏传 `lifespan=lifespan` → 启动钩子未执行 → `init_db()` 永不跑 → `no such table: users`
- **现象**：首轮自动化 2 个落库用例（`test_chat_returns_reply`、`test_continuation_and_persistence`）报 `sqlalchemy.exc.OperationalError: no such table: users`；即便**没有 live 后端在跑**，表也建不出来。
- **排查**：`tools/_dbdiag.py` 单独 `await init_db()` 能正常建出 `users`/`conversations`/`messages` 三表（28672 字节），说明 `init_db()` 本身正确。进一步用 `TestClient` 探针 + 文件标记验证：`lifespan` 内的 `init_db()` 调用**从未被执行**——`app.router.lifespan_context` 在修复前为 `None`。
- **真·根因**：`app/main.py` 的 `app = FastAPI(title=..., version=...)` **漏传了 `lifespan=lifespan` 关键字参数**，导致 FastAPI 启动时不会调用该生命周期钩子，`init_db()` 永远不跑，表从未创建。这才是 `no such table: users` 的真正来源（早先一度误判为"多进程并发写库竞态"，经探针证伪）。
- **修复**：`app/main.py` 改为 `app = FastAPI(title="Agentar-Fin-R1 Reproduce API", version="0.2.0", lifespan=lifespan)`，已验证 `app.router.lifespan_context is not None`。
- **测试侧处理（已移除原清库 fixture）**：联调早期曾加 `autouse` 会话级 fixture `_clean_db_before_suite` 在运行前 `os.remove` 删除 `agentar.db` 及其 `-wal/-shm/-journal` 附属文件——但该 fixture 源于"并发竞态"的**误判**，且 `os.remove` 被运行时（`sitecustomize.py`）的安全删除钩子拦截，沙箱内回收站不可用 → 直接抛 `OSError: [safe-delete][SAFE_DELETE_FAIL_CLOSED]` 使整个 suite 在 fixture 阶段崩溃。由于真因是 lifespan（Bug-3）而非竞态，且 5 个用例的落库断言均为**按 `conversation_id` 精确查询**（对历史脏数据免疫），该 fixture 已**移除**；`init_db()` 经修复后的 lifespan 在 `TestClient` 启动时正常建表即可。

### ⚠️ 客户端编码坑（非服务 Bug）
- 见 §3 踩坑提示：Git Bash 内联中文 → GBK → 模型服务 500。已用 UTF-8 文件规避。

## 6. 性能分析（延迟）

单轮对话 ~4.3min，瓶颈在 **4 个 ReAct 智能体串行的多轮模型调用**：

- 每个 ReAct 智能体最多 `max_iters=5` 次模型调用；每次调用经 OpenAI SDK → :9000 → transformers `generate`（GPU，`MAX_NEW_TOKENS=256`）。
- 实测单智能体 43~91s；单模型调用在隔离压测下约 4~9s，长尾来自：弱模型生成慢 + anaconda 运行时（含 tensorflow 启动告警）开销 + 多智能体串行累积。
- **非瓶颈项**：模型服务本身正常（19 次调用全 200）；SQLite 落库异步、开销可忽略；网络为本地回环。

**优化方向（供后续）**：
1. 减小 `max_iters`（如 2~3）或把 RAG/审核/风控中「无需工具」的角色改为 `DialogAgent` 单轮（RAG 当前即占位，可直出）。
2. 升级模型（qwen3-1.7b/更大）或换 vLLM/TGI 推理后端，单调用延迟可降数倍。
3. 并行化无依赖的智能体（审核/风控可并发），但需改造 `run()` 编排。
4. 降低 `MAX_NEW_TOKENS` 进一步压缩生成时间（权衡答案完整度）。
