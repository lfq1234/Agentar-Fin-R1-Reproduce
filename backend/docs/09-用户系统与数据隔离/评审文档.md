# 09 用户系统与数据隔离 — 评审文档（Review）

> 评审对象：`需求文档.md`(v0.1) / `技术文档.md`(v0.1)  
> 评审基准：仅基于本目录两份文档 + 既有跨模块事实（见 §待拍板项引用的前端 03 / 05 结论）  
> 评审结论：**有条件通过（Conditional Pass）** —— 鉴权地基设计扎实、对齐 `full-stack-fastapi-template` 范式，可先开工；但存在 **4 项重大（M1–M4）** 须在开工前澄清/修正。



---

## 1. 总体评价

**亮点**

- 设计原则清晰（"简单"——仅账号密码、无邮箱验证/找回/第三方/OAuth/角色），边界收敛，避免过度工程，符合本项目一贯的最小改动取向。
- 数据隔离**不新建第二套库**——明确复用 03/07/08 既有 `user_id` 列与索引，仅是切换 `user_id` 信任来源（请求体 → JWT），改动面小、风险可控（N4 原则落地）。
- 安全基线到位：Argon2 优先 + Bcrypt 兜底、HS256 + `exp`、`SECRET_KEY` 仅环境变量且缺失即失败、`sub` 为唯一归属、请求体/查询不再接受 `user_id`，从根上闭环越权。
- 测试沿用"无 torch 单测"范式，注册/登录/隔离均有断言，不依赖真实模型。

**核心风险**

- 模块间依赖（09 → 08）的**实现状态未确认**，需求多处假设 08 已落地，但据前端 03 技术文档，`backend/app/routes/chat.py` 仅有 chat/analyze/health，**后端 08 的文档/图谱接口实际尚未实现**——这直接动摇 FR5/FR6/FR7 的隔离标的（详见 M1）。

## 2. 重大级问题（Must-fix，开工前必修）

### M1 · 09 对 08 的实现依赖未确认，隔离验收可能无标的

- **现象**：需求 §1/FR6/FR7、技术 §1/§6.3/§10 均假设 08「个人文档与知识图谱后端」已存在带 `user_id` 列的 `personal_documents / personal_doc_chunks / personal_graph_nodes / personal_graph_edges` 及 DuckDB 向量表，且 `WHERE e.user_id = ?` 已按用户过滤。
- **矛盾**：据前端 `03-个人文档与知识图谱/技术文档.md` 的核查结论，「后端目前没有文档/图谱接口（`app/routes/chat.py` 只有 chat/analyze/health）」。即 **08 后端很可能仍处于文档阶段，代码未落地**。
- **影响**：若 08 未实现，FR5/FR6/FR7 的"隔离"对象是空表，验收 AC3（B 不召回 A 文档）/AC4（B 不可见 A 历史）无法成立；技术 §10 `test_isolation_documents` 也因无 08 设施而无法写。
- **建议**：开工前先确认 08 后端实现状态。若未实现，将 09 拆为两阶段——**阶段 A：用户系统 + 会话隔离（03/07，已具备 `user_id`）可独立交付**；**阶段 B：个人文档/图谱隔离（依赖 08，待 08 落地后补）**，避免 09 被 08 阻塞。

### M2 · `SECRET_KEY` 缺失校验非 fail-fast，与需求 S3 冲突

- **现象**：需求 S3 明写「`SECRET_KEY` 仅来自环境变量，**缺失则启动失败**（不提供默认值）」；技术 §4 `get_secret_key()` 仅在**首次调用**（签发 token）时 `raise RuntimeError`。
- **矛盾**：若 `lifespan`/模块加载期不调用 `get_secret_key()`，则缺密钥时服务照常启动，直到第一个人登录才报错——非需求要求的启动期 fail-fast。
- **建议**：在 `app.main` 的 `lifespan` 启动阶段、或 `security.py` 模块导入期 **eager** 调用一次 `get_secret_key()`，使缺密钥即启动失败，达成 S3。

### M3 · 「用户被禁用」状态码冲突（需求 401/403 vs 技术 400）

- **现象**：需求 FR4 将「用户被禁用」归入「无 token / token 失效 / 用户被禁用 → 401/403，不返回数据」；技术 §5 `get_current_user()` 对 `is_active=False` 返回 **400**（detail「账号已停用」）。
- **矛盾**：同一场景状态码不一致（需求 401/403 vs 技术 400）。
- **建议**：统一为 **403**（鉴权/授权失败语义更贴切）；并修正 `get_current_user` 的 `is_active` 分支状态码，与 FR4 对齐。

### M4 · 验收/测试中的「102 项」为模板占位数字，无出处

- **现象**：需求 §8 AC5「既有 **102** 项后端测试 + 新增…全部通过」；技术 §10「既有 **102** 项保持通过（`test_main`/`test_persistence` 的 `fake_run` 等已固化）」。
- **矛盾**：`102` 来自 `full-stack-fastapi-template` 实际测试数，本项目后端实际测试套件规模不同（据 05 联调报告：集成 5/5、单测 11 passed 等）。硬编码错误数字会误导排期与验收。
- **建议**：改为「**既有后端测试套件全量回归通过**」，删除具体数字；或先 `pytest --co -q` 统计真实用例数后填入。

## 3. 一般级问题（Should-fix）

### N1 · 需求背景「前端硬编码 user_id=1」与实际不符

- 需求 §1 称「`user_id` 由前端硬编码为 1」。实际前端 02 已改为**前端会话态生成会话级 id** 发后端（`useChat` 的 `genId`），并非硬编码 `1`。建议修正措辞为「前端在请求体/查询参数直接传入 `user_id`」，与 03 chat_service 的 upsert 行为一致。

### N2 · `EmailStr` 依赖遗漏，与自身表述矛盾

- 技术 §7.1 列新增依赖仅 `pwdlib[argon2,bcrypt]` + `PyJWT`，却注明「`email-validator` 若用 `EmailStr` 需补」；而 §3.2 模型已用 `EmailStr`。即**用了但没加依赖**，运行会 `ImportError`。
- 建议二选一：① pyproject 补 `"email-validator>=2.0"`；② 模型改 `email: Optional[str]`，由应用层做格式校验（更轻，契合"简单"原则）。

### N3 · 注册后是否自动登录未定义（UX 缺口）

- 需求 UX2/AC1 仅描述「注册页可含邮箱」「注册→登录→me 分两步」，未明确注册成功是否自动签发 token。
- 建议：为简化 UX，**注册成功即返回 `access_token`**（与 login 同构），省去用户再输一次密码；若坚持跳登录页，请在文档明示。

### N4 · `create_all` 新建列类型(BOOLEAN) vs ALTER 路径(INTEGER) 不一致

- 技术 §3.1 ALTER 用 `is_active INTEGER NOT NULL DEFAULT 1`；§3.2 模型经 `create_all` 生成的 `is_active` 为 `BOOLEAN`。SQLite 虽兼容（均存 0/1），但**同一列在不同初始化路径下类型声明不同**，易在调试/迁移时困惑。
- 建议：统一提供**单一迁移脚本**（`scripts/migrate_users.py` 执行 ALTER），开发期也走该脚本而非依赖 `create_all` 隐含类型。

### N5 · 「用户不存在」返回 404，需求未规定

- 技术 §5 `get_current_user()` 对 token `sub` 指向不存在的用户返回 404；需求 FR4/AC2 只覆盖 401/403。404 合理但属未约定行为。
- 建议：在需求 §5.1/§7 明示「token 合法但用户已删除 → 404（或统一 401）」，消除歧义。

### N6 · CORS preflight 对 OAuth2 表单需显式验证

- 技术 §7.3 称 `allow_headers=*` 已覆盖 `Authorization`，但登录端点跨域 POST `application/x-www-form-urlencoded` 会触发 preflight，`Access-Control-Request-Headers` 含 `Content-Type`。建议显式确认 `CORSMiddleware` 的 `allow_headers` 含 `Content-Type`（或保持 `*` 并在文档注明已验证），避免登录在浏览器端被 CORS 拦。

### N7 · 并发注册同名非原子

- 技术 §6.2 `register` 先 `get_by_username` 后 `create`，非原子。SQLite 单写者基本安全，但高并发（多 worker）可能双 409 或唯一约束抛错。
- 建议：依赖 `users.username` 已 `unique=True` 由 DB 兜底（捕获 `IntegrityError` → 409），不额外加锁。

### N8 · `rag/retrieve` 端点存在性需核对

- 需求 §5.2 与 技术 §6.3 都涉及 `POST /api/v1/rag/retrieve` 改造；需确认该端点真实存在（属 08 范围）。与 M1 同源——若 08 未实现，此端点亦缺失，改造无附着点。

## 4. 建议级（Nice-to-have）

- **S1 前端 401/403 统一跳登录**：需求 UX6 只说 401→跳登录；token 过期后端返回 403（M3 统一后），前端需对 401/403 一并处理，避免 403 时卡在界面。
- **S2 `SECRET_KEY` 强度**：建议文档补生成命令（如 `python -c "import secrets;print(secrets.token_urlsafe(48))"`），明确要求 ≥32 字节随机，禁用弱口令。
- **S3 禁用用户的管理面缺失**：当前无管理员/角色（Out of Scope），`is_active=False` 只能 DB 手动改。建议在文档注明「禁用仅 DB 操作，本期无 UI」，避免误解为可自助。
- **S4 密码策略**：仅长度 ≥8，未禁弱口令。简单原则下可接受，但可加一句「不建议使用常见弱密码」提示，或后续引入 zxcvbn。
- **S5 迁移脚本化**：技术 §9 仅在文档给 ALTER SQL；建议落地为 `scripts/migrate_users.py`，便于复现与 CI，而非依赖人工执行文档片段。
