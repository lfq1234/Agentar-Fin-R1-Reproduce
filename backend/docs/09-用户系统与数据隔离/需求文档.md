# 09 用户系统与数据隔离 — 需求文档（PRD）

> 版本：v0.1（草案，待评审）
> 关联模块：03 主库（users/conversations/messages）、07 会话历史、08 个人文档与知识图谱
> 参考实现：`full-stack-fastapi-template`（`backend/app/core/security.py`、`api/deps.py`、`api/routes/login.py`、`models.py`）

---

## 1. 背景与目标

当前 `users` 表仅有 `id/username/email/时间戳`，**无密码、无登录**。`user_id` 由前端硬编码为 `1`、或由请求体/查询参数直接传入（`chat_service` 甚至会对未知 `user_id` 自动 upsert 一个 `user_{id}` 假用户）。这带来两个问题：

1. **越权风险**：任何人都能在请求里填任意 `user_id` 读取他人对话/文档（08 的 RAG 作用域虽服务端强制，但 `user_id` 来源不可信）。
2. **体验断裂**：刷新即丢失会话、无「我的」概念、多用户共用同一份数据。

**目标**：引入最小可用的账号/密码登录，**为每个账号隔离其聊天记录与个人知识库**，并消除「请求体带 user_id」这一临时方案。

**设计原则（用户要求）**：简单——只填账号密码即可，不做邮箱验证、找回密码、第三方登录、角色权限（superuser 等）。

---

## 2. 范围

### 2.1 In Scope
- 用户表增加 `hashed_password` + `is_active`。
- 注册（`POST /auth/register`）、登录取 token（`POST /auth/login/access-token`）、当前用户（`GET /auth/me`）。
- 登录后返回 **JWT（Bearer）**，后续请求经 `Authorization` 头携带。
- 将所有「从请求取 user_id」的端点改为「从 token 解析当前用户」，实现**可信归属**。
- 前端增加登录/注册页、token 存储与注入、登录态门禁。
- **数据隔离**：每个账号只能看到自己的会话历史（03/07）与个人文档/知识图谱（08）。

### 2.2 Out of Scope（本期不做）
- 邮箱验证、密码找回/重置邮件。
- 角色/权限体系（superuser、管理员后台）。
- OAuth/SSO、第三方登录。
-  refresh token、踢下线、并发登录控制。
- 个人资料编辑、头像、昵称。

## 3. 功能需求（FR）

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| FR1 | 账号密码注册 | `username`（唯一）+ `password`（≥8 位），可选 `email`。注册即激活（`is_active=1`）。 |
| FR2 | 账号密码登录 | OAuth2 密码流（`username`/`password` 表单），成功返回 `access_token`（Bearer）。 |
| FR3 | 当前用户查询 | 携带合法 token 可获取自身 `id/username/email`。 |
| FR4 | 受保护端点 | 无 token / token 失效 / 用户被禁用 → `401/403`，不返回数据。 |
| FR5 | 会话隔离 | 账号 A 的会话历史（03 conversations/messages + 07 history）对账号 B 不可见。 |
| FR6 | 知识库隔离 | 账号 A 上传的个人文档、切片、图谱、向量，账号 B 不可见、不可检索。 |
| FR7 | RAG 作用域可信 | 08 `use_personal_docs` 召回的个人文档归属 = 当前登录用户，**模型侧无法篡改 user_id**。 |
| FR8 | 注册防重 | `username` 已存在返回 `409`；`email` 若提供则需唯一。 |
| FR9 | 密码安全 | 库内只存哈希（pwdlib/Argon2 或 Bcrypt），绝不存明文；登录失败统一返回「账号或密码错误」，不区分哪一项错（防枚举）。 |

## 4. 非功能需求

- **N1 无外部服务**：不引入邮件/短信网关；依赖仅 `pwdlib` + `PyJWT`（与模板一致）。
- **N2 配置外置**：`SECRET_KEY` 经环境变量注入（`config.yaml` 用 `${AUTH_SECRET_KEY}` 占位），**不得写入仓库**。token 有效期可配置（默认 60 分钟）。
- **N3 测试可达**：沿用无 torch 单测范式；注册/登录/隔离均有断言，不依赖真实模型。
- **N4 最小改动**：复用现有 `users` 表与既有 `user_id` 隔离列，**不新建第二套用户/会话库**。

## 5. API 契约（草案）

统一前缀沿用现有约定：`/api` 挂载、`/v1` 为业务版本，即完整路径 `/api/v1/...`。

### 5.1 新增鉴权端点
| 方法 | 路径 | 入参 | 出参 |
| --- | --- | --- | --- |
| POST | `/api/v1/auth/register` | JSON `{username, password, email?}` | `UserPublic{id,username,email}` |
| POST | `/api/v1/auth/login/access-token` | form `username`,`password`（OAuth2） | `{access_token, token_type:"bearer"}` |
| GET | `/api/v1/auth/me` | Header `Authorization: Bearer <token>` | `UserPublic` |

### 5.2 既有端点改造（user_id 来源切换）
| 端点 | 改造前 | 改造后 |
| --- | --- | --- |
| `POST /api/v1/chat` | `ChatRequest.user_id`（请求体） | 删除该字段；`user_id = current_user.id` |
| `GET/POST/DELETE /api/v1/documents[/...]` | `Query user_id=1` | `Depends(CurrentUser)` |
| `GET /api/v1/knowledge-graph` | `Query user_id=1` | `Depends(CurrentUser)` |
| `GET /api/v1/history/...` | `Query user_id`（str） | `Depends(CurrentUser)`，内部传 `str(current_user.id)` |
| `POST /api/v1/rag/retrieve` | `RagRetrieveRequest.user_id` | 改为 `current_user.id`（body 不再接受 user_id） |

> 说明：`health`(`/api/health`) 保持匿名，便于探活。

## 6. 前端 UX 需求

- **UX1 登录门禁**：无 token 时显示登录/注册页，登录成功后进入现有聊天界面。
- **UX2 表单**：仅「账号」「密码」两栏；注册页可含可选「邮箱」。提交走 OAuth2 表单（登录）或 JSON（注册）。
- **UX3 token 存储**：存 `localStorage`（key 如 `agentar_token`）；每次请求经 `client.ts` 注入 `Authorization` 头。
- **UX4 退出登录**：清除 token，回到登录页。
- **UX5 当前用户感知**：用真实 `current_user.id` 替换现有硬编码 `user_id=1`（chat/文档/图谱/历史均受益）。
- **UX6 错误提示**：401 → 提示「请重新登录」并跳登录页；注册 `409` → 「账号已存在」。

## 7. 安全与合规

- **S1 密码哈希**：pwdlib（Argon2 优先，Bcrypt 兜底），与模板 `core/security.py` 一致。
- **S2 token**：HS256 JWT，含 `sub=user.id` 与 `exp`；服务端不存 session。
- **S3 SECRET_KEY**：仅来自环境变量，缺失则启动失败（不提供默认值）。
- **S4 越权闭环**：鉴权后 `user_id` 唯一来源为 token，请求体/查询参数不再接受 `user_id`，彻底消除「填别人 id 读别人数据」。
- **S5 XSS 注意**：`localStorage` 存 token 有 XSS 风险；本期接受（与模板一致），后续可迁 httpOnly Cookie。CORS 需允许 `Authorization` 头。

---

## 8. 验收清单（AC）

- AC1：注册新账号 → 登录拿 token → `/auth/me` 返回该用户。
- AC2：错误密码登录 → `400`「账号或密码错误」；无 token 访问受保护端点 → `401/403`。
- AC3：用户 A 上传文档并开启 `use_personal_docs` 问答，用户 B 的会话**不**召回 A 的文档；B 的文档列表为空。
- AC4：用户 A 的会话历史对 B 不可见（03/07 均隔离）。
- AC5：既有 102 项后端测试 + 新增鉴权/隔离测试全部通过。
- AC6：`config.yaml` 不含明文 `SECRET_KEY`；缺失环境变量时启动报错。

---

## 9. 风险与权衡

- **R1 现有假用户数据**：`chat_service` 自动 upsert 的 `user_1` 等无密码，无法登录。开发期建议重置 `agentar.db` 并重新初始化（见技术文档 §迁移）；生产应走 Alembic。
- **R2 无邮件验证**：账号可被任意注册，属本期故意简化；若需防滥用后续再加。
- **R3 localStorage token**：XSS 风险（S5），接受为权衡。
- **R4 数据隔离已具备**：08 各表与向量索引均已带 `user_id` 列并建索引，本次主要是「把 user_id 的来源从请求改为 token」，而非新建隔离。
