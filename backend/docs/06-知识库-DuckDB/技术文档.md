## 1. 概述与架构定位

### 1.1 在本项目中的层位

本项目按职责分四层（04 §1），06 是 **04 的 RAG 存储后端的演进实现**，不新建框架层、不重复 04 的切分/混合检索算法，只把底层存储引擎从 SQLite（embedding 存 JSON、余弦在 Python 端算）升级为 **DuckDB**（向量列原生、余弦在 SQL 端算）。

```
01 模型接口 ── get_embedder() ──┐
                                 ├─► 06 知识库(DuckDB) ── ingest / 召回(向量+BM25) / 重排
04 RAG 算法(切分/BM25/重排) ─────┘        │  app/kb/  （对外暴露 retrieve() = 召回+重排）
                                         │
02 app.agent.run() 第 2 步 ── 调 agents["rag"] ──► RAG 智能体经 retrieve_documents 工具调
06 retrieve()(召回+重排) ──► 得 Passage ──► RAG 智能体按 rag.txt 总结 ──► 注入专家提示词
```

- **06 复用**：04 的 `_split_into_chunks`（切分）、`_BM25`（关键词召回）、融合重排逻辑、`Passage` 契约。
- **06 新增**：DuckDB 存储引擎（`app/kb/store.py` 的 `DuckDBKnowledgeStore`）、知识库生命周期管理、构建脚本、与 `run()` 的集成改造。
- **06 不重做**：提示词（04）、Agent 编排（02）、嵌入模型管理（01）。

### 1.2 为什么选 DuckDB（相对 04 §5.5 的选型）

| 方案 | 取舍 | 结论 |
|---|---|---|
| SQLite + sqlite-vec | 需额外扩展、向量运算不在 SQL 内 | 04 既有 `:memory:` 路径保留为 `sqlite` 后端 |
| Chroma / FAISS | 引入独立服务/进程外依赖，部署重 | 不符「嵌入式零服务」原则 |
| **DuckDB** | 进程内、原生 `FLOAT[]` 向量列、`list_cosine_distance` 精确最近邻、可 `vss` HNSW 加速、零额外服务；**向量表建在主库，ATTACH 主库检索，不另开文件** | **06 选定**，与 03/07 同主库 |

DuckDB 仍是进程内嵌入式引擎，迁移成本低；向量运算下沉到 SQL 执行引擎，避免 04 把全部 chunks 拉到 Python 端算余弦的内存/CPU 开销。

## 3. DuckDB Schema 与向量检索

### 3.1 表结构（DDL）

```sql
-- app/kb/schema.sql
CREATE TABLE IF NOT EXISTS chunks (
    id              BIGINT,           -- 自增主键（用 SEQUENCE 或 ROWID 派生）
    doc_id          VARCHAR,
    title           VARCHAR,
    doc_type        VARCHAR,          -- regulation | product | internal
    agency          VARCHAR,
    domain          VARCHAR,          -- 逗号分隔多标签（保留，便于人工查看/导出）
    domain_tags     VARCHAR[],        -- 规范化多标签数组 ['Banking','Securities',...]，过滤用此列（list_contains 精确命中）
    chapter         VARCHAR,
    effective_date  VARCHAR,          -- ISO 日期
    version         VARCHAR,
    source_path     VARCHAR,
    content         VARCHAR,
    embedding       FLOAT[],          -- 变长向量 list（同库内须等长）
    dim             INTEGER           -- 冗余维度，便于校验与过滤
);

-- domain_tags 为 LIST 列：btree 无法服务包含查询，用 min_max 索引记录 list 内 min/max，
-- 查询时跳过完全不相交的 row group；list_contains 主体仍为列扫描（万级可接受）。
CREATE INDEX IF NOT EXISTS idx_domain_tags ON chunks USING min_max (domain_tags);
CREATE INDEX IF NOT EXISTS idx_doc_id ON chunks (doc_id);
CREATE INDEX IF NOT EXISTS idx_eff    ON chunks (effective_date);
```

### 3.2 向量检索 SQL（精确最近邻）

DuckDB 1.1+ 提供 `list_cosine_distance(a, b)`（对 `FLOAT[]` 变长 list 有效），返回距离（0 最相似）。查询模式：

```sql
-- 元数据预过滤 + 向量余弦相似度排序取 top_k
SELECT
    id, doc_id, title, domain, chapter, content, effective_date,
    1 - list_cosine_distance(embedding, ?::FLOAT[]) AS similarity
FROM chunks
WHERE (? IS NULL OR list_contains(domain_tags, ?))        -- domain 精确多标签命中其一（无子串误命中）
  AND (? IS NULL OR effective_date >= ?)                  -- 生效日下界
ORDER BY similarity DESC
LIMIT ?;
```

- `?::FLOAT[]`：把查询向量（Python `list[float]` 经参数绑定）转为 DuckDB `FLOAT[]`。
- 元数据过滤在 `WHERE` 中**先于**向量计算执行，缩小候选集，提升精度与吞吐。
- 相似性 = `1 - 余弦距离`，满分 1.0。

### 3.3 可选 HNSW 加速（vss 扩展）

十万级 chunks 或低延迟场景可启用 `vss`：

```sql
INSTALL vss; LOAD vss;
-- vss 要求固定长度 ARRAY
ALTER TABLE chunks ALTER embedding SET DATA TYPE FLOAT[1536];   -- 依 embed_dim 固定
CREATE INDEX idx_hnsw ON chunks USING HNSW (embedding);
-- 查询改用 array_distance（近似最近邻）
SELECT *, array_distance(embedding, ?::FLOAT[1536]) AS dist
FROM chunks WHERE ... ORDER BY dist LIMIT ?;
```

> 默认 `kb.use_vss=false`：离线/内网环境 `INSTALL vss` 可能失败，精确扫描兜底；维度需固定（`kb.embed_dim` 非 0）才可用 HNSW。技术权衡见 §9。

### 3.4 维度自适应策略

- 同一库内 embedding 维度必须一致（余弦要求等长）。
- `ingest` 首个向量时记录 `dim` 并写入 `chunks.dim`；后续 `ingest` 若 `len(vec) != 库内 dim`，抛 `InconsistentDimensionError`（明确提示「切换 embedder 需 rebuild」）。
- `kb.embed_dim` 非 0 时强制校验该维度（配合 `vss`）。

### 3.5 与 FAISS 的对比（选型边界）

本节把 §1.2「FAISS 部署重」一句展开为可操作的选型判据。

| 维度 | 06 现状：DuckDB 暴力精确扫描 | FAISS |
|---|---|---|
| 检索算法 | 全表 `1 - list_cosine_distance` 排序取 Top-K（brute-force） | IVF / HNSW / PQ 等 ANN 索引，先建索引再跳查 |
| 精度 | 100% 精确，无近似误差 | 近似索引损失少量召回率（可调 90%+）；Flat 索引精确但无加速 |
| 复杂度 | O(N·d)，N=向量数、d=维度 | 查询近 O(log N) |
| 适用规模 | 千~万级 chunks 够用 | 百万~十亿级，毫秒级 |
| 结构化过滤 | 一条 SQL 顺带过滤 `domain`/`effective_date` | 本身不做字段过滤，需应用层先筛或额外 metadata 方案 |
| 存储形态 | 向量表在主库，DuckDB ATTACH 主库即查，零服务 | 独立索引文件，通常另配元数据存储 |
| 依赖/运维 | 仅 duckdb，零 torch 可跑单测，轻量 | 库较重，编译复杂，GPU 加速支持好 |

**结论与边界**：当前知识库规模为 11 块 / 2 文档（占位 embedder 阶段），DuckDB 精确扫描延迟可忽略，且免维护、可直接用 SQL 做业务字段过滤——契合「嵌入式零服务、最小改动」原则。FAISS 的价值在**规模**：当 chunks 涨到十万级、暴力扫描开始拖慢响应时，再引入 FAISS/ANN 加速才划算。其时可选平滑路径：保留 DuckDB 做 SQL 过滤+召回，仅把相似度计算一步替换为 FAISS 索引；或启用本文件 §3.3 的 `vss` HNSW 扩展（同为近似加速，但无需引入进程外依赖）。现阶段换 FAISS 属提前优化、增加运维负担，不采纳。

## 5. 召回与重排（检索核心链路）

06 知识库对外的**检索核心由「召回」与「重排」两段组成**——这正是 RAG 智能体获取本地依据的入口（调用关系见 §7）。算法沿用 04 `Retriever.search`，仅把"向量得分"来源从 Python 余弦换成 DuckDB `list_cosine_distance`。

### 5.1 召回（Recall）· 双路候选

- **向量召回**：DuckDB `1 - list_cosine_distance(embedding, ?::FLOAT[])` 计算查询与每块相似度，按 `top_k * β`（默认 `β=3`，扩召回）取候选，降低向量单路漏召。
- **关键词召回**：复用 04 `_BM25(contents)` 计算 BM25 分，捕获向量单路易漏的精确词面匹配（条款编号、专有名词、人名等）。
- 两路候选取**并集**作为重排候选集；两路均在「元数据预过滤后的全库」上独立召回（BM25 不在向量候选子集上算，否则退化为单路）。并集按 `id` 去重，单边命中的块在融合时该路得分记 0，不惩罚。

### 5.2 重排（Rerank）· 融合排序

- 向量得分 `nv = normalize(vec_scores)`、BM25 得分 `nb = normalize(bm25_scores)`（min-max 归一化）。
- 加权融合：`fused = vec_weight * nv + (1 - vec_weight) * nb`（默认 `vec_weight=0.7`，可调）。
- 按 `fused` 降序取 `top_k`，输出 `Passage(content, source, score, chapter, effective_date)`（**带出处与生效日**，供 RAG 智能体标注来源）。

### 5.3 可选 LLM / 交叉编码器重排（增强）

候选集较小时可对 `top_k * β` 候选做一轮轻量 **LLM 重排**或 **cross-encoder 二次精排**，提升长 query / 语义相近片段的相关性。

- 本地 0.6B 弱模型下**默认关闭**，以 §5.2 融合重排兜底（性能/稳定性权衡，避免小模型重排空转）；强模型或离线 cross-encoder 场景可开启。
- 实现上作为 `search()` 的可选后处理步骤（`rerank_top_n` 参数），不阻塞主链路。

### 5.4 代码骨架

```python
def search(self, query, top_k=5, domain=None, effective_after=None, vec_weight=0.7, rerank=False):
    beta = 3  # 扩召回倍数
    # —— 召回①：向量路，元数据预过滤后的全库取 top_k*beta 候选（见 §3.2 SQL）——
    vec_rows = self._duckdb_recall(query, top_k*beta, domain, effective_after)   # -> [(row, vec_sim, None)]
    # —— 召回②：关键词路，全库（元数据预过滤后）独立召回 top_k*beta 候选 ——
    #   BM25 是查询相关模型，对任意文本可打分，故能在全库独立补召回向量漏掉的块
    bm25_rows = self._bm25_recall(query, top_k*beta, domain, effective_after)    # -> [(row, None, bm25)]
    # —— 并集（按 id 去重；单边命中块其另一路得分记 0，不惩罚）——
    cand = self._union_recall(vec_rows, bm25_rows)   # -> [(row, vec_sim|None, bm25|None), ...]
    # —— 重排：缺失分填 0，min-max 归一化后加权融合 ——
    nv = _normalize([c[1] if c[1] is not None else 0.0 for c in cand])
    nb = _normalize([c[2] if c[2] is not None else 0.0 for c in cand])
    fused = [vec_weight*a + (1-vec_weight)*b for a, b in zip(nv, nb)]
    ranked_idx = sorted(range(len(fused)), key=lambda i: fused[i], reverse=True)
    if rerank and len(ranked_idx) > top_k:           # 可选 LLM/cross-encoder 二次精排
        ranked_idx = self._llm_rerank(query, [cand[i][0] for i in ranked_idx[:top_k*beta]], top_k)
    ranked_idx = ranked_idx[:top_k]
    return [ Passage(content=cand[i][0].content, source=cand[i][0].title or cand[i][0].doc_id,
                     score=round(fused[i],4), chapter=cand[i][0].chapter,
                     effective_date=cand[i][0].effective_date) for i in ranked_idx ]

# —— 召回辅助（统一返回 (row, vec_sim|None, bm25|None)）——

def _duckdb_recall(self, query, k, domain, effective_after):
    # 见 §3.2 SQL：向量余弦 top_k 候选；返回 [(row, vec_sim, None)]
    sql = "SELECT id, doc_id, title, chapter, content, effective_date, 1 - list_cosine_distance(embedding, ?::FLOAT[]) AS similarity FROM chunks WHERE (? IS NULL OR list_contains(domain_tags, ?)) AND (? IS NULL OR effective_date >= ?) ORDER BY similarity DESC LIMIT ?"
    rows = self._conn.execute(sql, [qvec, domain, domain, effective_after, k]).fetchall()
    return [(r, r.similarity, None) for r in rows]

def _bm25_recall(self, query, k, domain, effective_after):
    # 1) SQL 取元数据过滤后的全量 (id, content)；2) 04 _BM25 打分取 top_k
    rows = self._fetch_filtered(domain, effective_after)   # SELECT id, content, ... FROM chunks WHERE 元数据过滤
    if not rows:
        return []
    bm25 = _BM25([r.content for r in rows])                # 复用 04
    scores = bm25.scores(query)
    order = sorted(range(len(scores)), key=lambda i: scores[i], reverse=True)[:k]
    return [(rows[i], None, scores[i]) for i in order]

def _union_recall(self, vec_rows, bm25_rows):
    # vec_rows: [(row, vec_sim, None)]；bm25_rows: [(row, None, bm25)]
    by_id = {}
    for row, sim, _ in vec_rows:
        by_id[row.id] = [row, sim, None]
    for row, _, bm in bm25_rows:
        if row.id in by_id:
            by_id[row.id][2] = bm          # 双路命中：补上 bm25 分
        else:
            by_id[row.id] = [row, None, bm]
    return list(by_id.values())

def _normalize(xs):
    lo, hi = min(xs), max(xs)
    if hi - lo < 1e-9:
        return [1.0] * len(xs) if hi > 0 else [0.0] * len(xs)
    return [(x - lo) / (hi - lo) for x in xs]

> **修复（评审 B1）**：BM25 在**全库**独立召回后与向量路取并集，真正补回向量漏召的块；单边命中的块融合时该路记 0，不被惩罚——避免旧伪代码把 BM25 限制在向量候选子集上、退化为单路。
> 召回+重排的整体输出即 06 对外暴露的 `retrieve()`，被 RAG 智能体消费（§7）。
```

## 6. 知识库生命周期管理

| 操作 | 实现要点 |
|---|---|
| `stats()` | `SELECT count(*), count(DISTINCT doc_id), MAX(dim) FROM chunks` + 库文件大小（`os.path.getsize`）+ 最近构建时间（写 `kb_meta` 小表/文件）。 |
| `list_docs()` | `SELECT doc_id, title, doc_type, domain, version, count(*) FROM chunks GROUP BY doc_id`。 |
| `delete_doc(doc_id)` | `DELETE FROM chunks WHERE doc_id = ?` 返回 `changes()`。 |
| `rebuild()` | `DELETE FROM chunks`（或 `DROP + CREATE`）；若传 `kb/` 路径则重新扫描 `ingest` 全部文档。增量去重：同一 `doc_id` 重复 `ingest` 先 `delete_doc` 再写。 |

> 单写者：所有写操作（ingest/delete/rebuild）在进程内单连接串行执行，读操作（search/stats）并发无碍。

## 7. 与多智能体集成（RAG 智能体经召回重排做总结）

06 的 `retrieve()`（召回+重排，见 §5）**由 RAG 智能体调用**，而非在 `run()` 里直接调 store；"把检索片段总结成一段话依据"是 **RAG 智能体的 LLM 职责**（吃 `rag.txt` 的总结指令）。这样职责边界清晰：06 管检索，RAG 智能体管总结。

### 7.1 端到端调用链

```
02 run() 第 2 步:  agents["rag"](Msg("请检索与…相关的资料"))
        │
        ▼
RAG 智能体 (ReActAgentX, 提示词 rag.txt「聚合不罗列·标注来源·总结要点」)
        │  经其注册工具 retrieve_documents 调用
        ▼
app/agent/tools.py: retrieve_documents(query) → lookup_knowledge(query)
        │  后端切换为 06
        ▼
06 get_knowledge_store().retrieve(query)   ← 召回(向量+BM25, 扩召回) + 重排(融合)
        │  返回 Passage 列表（带出处/生效日）
        ▼
RAG 智能体 LLM 把 Passage 总结为 context（聚合不罗列）
        │
        ▼
注入领域专家提示词 → 专家作答并引用本地依据
```

### 7.2 改造点（`tools.py`，而非 `run()`）

`run()` 第 2 步**本就**调用 `agents["rag"]`（见 `app/agent/system.py:146-152`），无需改动主流程。只需把 RAG 智能体的检索工具后端从 04 空库 `Retriever` 切到 06：

```python
# app/agent/tools.py —— 把 retrieve/lookup_knowledge 后端切到 06（伪代码）
# from app.agent.retrieval import retrieve   # 旧：04 空库占位
from app.kb import get_knowledge_store        # 新：06 DuckDB/SQLite 后端

def lookup_knowledge(query: str) -> str:
    store = get_knowledge_store()             # 按 kb.engine 懒加载
    passages = store.retrieve(query, top_k=3) if store is not None else []
    if not passages:
        return "（暂无检索结果）"
    return "\n".join(f"- {p.content}（来源：{p.source}）" for p in passages)
```

- **06 的 `retrieve` 与 04 同名同签名**（`retrieve(query, top_k=3)`），`get_knowledge_store()` 按 `kb.engine` 分发 duckdb / sqlite，向后兼容。
- 检索到的 `Passage` 本身已带 `source`（出处）/`effective_date`（生效日），RAG 智能体在总结时会据此标注来源（满足 `rag.txt` 要求）。

### 7.3 降级与开关

- 开关：`kb.engine=duckdb` 或 `sqlite` 任一非空库即生效；`kb` 未配置或库为空时 `store.retrieve` 返回 `[]`，RAG 智能体如实声明「未检索到本地依据，不编造」——降级契约（04 §5.7 / `rag.txt`），不报错、不幻觉。
- 不破坏 05 已通过的联调：06 仅在「库非空」时有检索产出，空库行为等同原占位；`run()` 主流程零改动。

## 11. 风险与权衡

- **维度一致性**（§3.4）：跨 embedder 切换需 rebuild；文档须显式提示，否则 `list_cosine_distance` 因不等长报错。缓解：入库即校验 + `kb.embed_dim` 固定模式。
- **vss 离线风险**：`INSTALL vss` 依赖网络；默认 `use_vss=false`，精确扫描兜底（万级内性能可接受）。
- **DuckDB 并发**：单写者模型，进程内单连接；多进程（如多 worker uvicorn）共享同一主库文件时，写期与读期需协调——本期单进程后端，风险低；多 worker 场景建议「构建期写、运行期只读打开」或走主库既有连接池。
- **local 嵌入显存竞争**：嵌入模型与 LLM（qwen3-0.6b）同在 GTX 1650 4GB，需分时加载（先建库再起 LLM）或外部嵌入服务，沿用 05 环境限制结论。
- **二进制解析缺失**：PDF/DOCX/XLSX 本期不接，`ingest_document` 抛 `NotImplementedError`（扩展点），沿用 04 后续需求。
- **层位一致性**：总文档 §7 未含 06，待评审通过后回正（沿用 04 §11）。
