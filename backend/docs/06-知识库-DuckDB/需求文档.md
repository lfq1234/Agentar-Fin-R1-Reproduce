## 1. 背景与目标

后端前五个模块已落地，但 RAG 这一环存在三个未闭合的缺口（见 05 §7 已知问题）：

1. **知识库未建**：04 已实现 `ingest_*` 接入能力，但尚无 `kb/` 语料目录与默认知识库，`run()` 无库可检。
2. **RAG 占位未生效**：02 `system.py` 的 `run()` 中 RAG 仍是占位实现，注释明确「不调用 `get_embedder()`」，因此即使建了库，问答也吃不到检索增强（05 目标 5 无法断言）。
3. **存储选型待落地**：04 §5.5 把存储列为「SQLite + 向量扩展 / Chroma / FAISS 二选一」，尚未定稿实现。

**本模块（06 · 知识库-DuckDB）的目标**：以 **DuckDB** 作为嵌入式向量知识库存储与检索后端，把 04 的 RAG 管线从 SQLite 占位升级为真正可用的检索增强，并交付知识库全生命周期管理（建库 / 接入 / 重建 / 删除 / 统计），使 02 `run()` 能真正消费检索结果，闭环 05 目标 5。

设计原则：

- **统一主库、零服务**：知识库向量表（`chunks` / `kb_meta`）**直接建在 03 主库同一实例**，DuckDB 以 `ATTACH '<主库路径>'` 挂载主库做向量检索，进程内、不引入独立向量服务；与 03/07 同主库，部署形态一致。
- **演进而非重写**：复用 04 的切分 / 混合检索 / 重排算法与 `Passage` 契约，只替换底层存储引擎为 DuckDB，不破坏既有 `retrieval.py` 接口与测试。
- **双后端兼容**：保留 04 的 SQLite 后端作为可选实现，通过 `kb.engine` 切换，默认 `duckdb`。
- **向量检索下沉到 DuckDB**：用 `list_cosine_distance` 做精确最近邻 + 元数据预过滤；可选 `vss` 扩展做 HNSW 加速（默认关闭，规避离线扩展下载风险）。

## 2. 范围

### 2.1 包含（In Scope）

- **DuckDB 知识库存储引擎**：替代/并行 04 的 SQLite 存储（`chunks` 表 + 向量列 + 元数据列）。
- **知识库目录 `kb/` + 默认语料 + 一键构建脚本**：提供 `kb/sample_*.md` 等金融条款样本，及其 `ingest` 构建命令，闭环 05 目标 5 的"sample 知识库待建"问题。
- **文档接入**：`ingest_text` / `ingest_document`，当前支持 `txt` / `md` / `html`；二进制（PDF/DOCX/XLSX）解析沿用 04 后续需求（本期给 `NotImplementedError` 扩展点）。
- **文本切分**：复用 04 的 `_split_into_chunks`（标题/语义边界 + 父标题上下文 + 重叠），块大小与重叠可配。
- **向量化**：经 01 `get_embedder()`（api/local 双模式）；local 离线场景提供可选的**进程内嵌入直载**（借鉴 01 `LocalTransformerModel` 的惰性加载范式），避免强依赖外部嵌入服务。
- **召回与重排（检索核心链路）**：双路召回（向量召回 + BM25 关键词召回，扩召回融合）+ 融合重排，作为 RAG 智能体的本地依据来源，算法与 04 `Retriever.search` 一致（详见 FR6）。
- **RAG 智能体消费与总结**：06 的 `retrieve`（召回+重排）被 RAG 智能体（`agents["rag"]`）经其 `retrieve_documents` 工具调用，由该智能体把 `Passage` 列表**总结**为本地依据上下文后注入领域专家（详见 FR9）。
- **知识库生命周期**：`stats`（文档数/块数/维度）、`list_docs`、`delete_doc(doc_id)`（按 `doc_id` 删）、`rebuild`（清空重建）。
- **与多智能体集成**：02 `run()` 可切换至 DuckDB 后端，RAG 角色（信息查询智能体 + 各专家）真正消费检索到的 `Passage`，让 `reply` 命中检索内容。

### 2.2 排除（Out of Scope）

- 二进制格式深度解析（PDF 表格识别 / OCR / DOCX 字段抽取）——属 04 后续需求，06 仅接 `txt/md/html`。
- 联网新闻（`news_search`，属 04 §6）——06 不含。
- 多租户 / 多知识库隔离（多文件分库）——排期。
- 前端 / UI（与 05 一致，06 不含任何浏览器/页面代码）。
- 嵌入模型训练 / 领域微调（属 01/04 后续）。
- `agent_trace` 落库（检索命中痕迹审计）——属 03 后续，06 仅保证 `Passage` 带可追溯出处。

## 3. 功能需求

### FR1 · 建立知识库目录与默认语料
- 提供 `kb/` 目录与若干 sample 金融知识文档（如 `kb/sample_faq.md`、`kb/sample_regulations.md`），覆盖银行/证券/保险/信托/基金典型条款。
- 提供一键构建脚本（如 `python -m app.kb.build`，或 `make kb`），扫描 `kb/` 下文档并 `ingest` 到主库 `chunks` / `kb_meta` 表。

### FR2 · 文档接入（ingest）
- `ingest_text(text, *, doc_id, title, doc_type, agency, domain, effective_date, version, source_path, max_chars, overlap) -> int`：切分 + 向量化 + 写入，返回写入块数。
- `ingest_document(path, **meta) -> int`：按扩展名分发；`txt/md/html` 原生解析，`html` 去标签；二进制抛 `NotImplementedError`（扩展点）。
- 增量更新：同一 `doc_id` 重复 `ingest` 应视为新版本（先删旧 `doc_id` 再写），避免重复块。

### FR3 · 文本切分（可配）
- 复用 04 切分算法；块大小 `max_chars`（默认 600）、重叠 `overlap`（默认 80）可配（config `kb.chunk`）。
- 表格整块保留、长块带父标题上下文，与 04 §5.3 一致。

### FR4 · DuckDB 存储
- 复用 03 主库（同一 DB 实例），`chunks` / `kb_meta` 表随主库 `init_db()` 一并建；不再有独立知识库文件。
- 表 `chunks`：元数据列（`doc_id` / `title` / `doc_type` / `agency` / `domain` / `chapter` / `effective_date` / `version` / `source_path`）+ `content` + `embedding`（`FLOAT[]`，变长 list）。
- 维度自适应：首个 `ingest` 决定本库 `dim`；后续 `ingest` 维度不一致应明确报错（DuckDB `list_cosine_distance` 要求等长）。

### FR5 · 向量检索
- `vector_search(query_vec, top_k, domain, effective_after) -> list[Passage]`：DuckDB `list_cosine_distance(embedding, query_vec)` 计算相似度，按元数据预过滤后取 `top_k`。
- 默认精确最近邻；可选 `vss` HNSW 索引加速（`kb.use_vss=false` 默认关闭）。

### FR6 · 召回与重排（检索核心链路）
知识库对外的**检索核心链路**，由「召回」与「重排」两段组成，是 RAG 智能体获取本地依据的来源（与 RAG 智能体协作见 FR9）：

- **召回（Recall）· 双路候选**：
  - 向量召回：DuckDB `list_cosine_distance` 计算查询与各块相似度，按 `top_k * β`（默认 `β=3`，扩召回）取候选，降低向量单路漏召；
  - 关键词召回：复用 04 `_BM25(contents)` 计算 BM25 分，捕获向量单路易漏的精确词面匹配（条款编号、专有名词等）。
  - 两路候选取**并集**作为重排候选集；两路均在「元数据预过滤后的全库」上独立召回（BM25 不在向量候选子集上算，否则退化为单路）。并集按 `id` 去重，单边命中的块融合时该路得分记 0，不惩罚。
- **重排（Rerank）· 融合排序**：
  - 对向量得分与 BM25 得分分别 min-max 归一化，加权融合 `fused = vec_weight * nv + (1 - vec_weight) * nb`（默认 `vec_weight=0.7`，可调）；
  - 按 `fused` 降序取 `top_k`，输出 `Passage(content, source, score, chapter, effective_date)`（**带出处与生效日**，供 RAG 智能体标注来源）。
- **可选 LLM / 交叉编码器重排（增强）**：候选集较小时可对 `top_k * β` 候选做一轮轻量 LLM 或 cross-encoder 二次精排，提升长 query 相关性；本地 0.6B 弱模型下默认关闭，以融合重排兜底（性能/稳定性权衡，见技术文档 §5.3）。
- 接口：`search(query, top_k, domain, effective_after, vec_weight) -> list[Passage]`（融合重排主入口）；`retrieve(query, top_k) -> list[Passage]`（02 既有契约，默认 `top_k=3`，内部复用 `search`）。

### FR7 · 元数据过滤
- `domain`：多标签逗号分隔；存储时规范化为 `domain_tags VARCHAR[]`（`string_split(trim(domain), ',')`），过滤用 `list_contains(domain_tags, ?)` **精确**命中其一（无子串误命中，替代 `LIKE '%tag%'`）。
- `effective_after`：生效日下界（ISO），优先现行有效（`effective_date >= 下界`）。
- 过滤在向量检索**之前**做（缩小候选集），提升精度与性能。

### FR8 · 知识库生命周期管理
- `stats() -> dict`：返回文档数、块数、embedding 维度、库文件大小、最近构建时间。
- `list_docs() -> list[dict]`：列出已入库文档（`doc_id` / `title` / `doc_type` / `domain` / `version` / 块数）。
- `delete_doc(doc_id) -> int`：按 `doc_id` 删除其全部块，返回删除块数。
- `rebuild(*, rescan: bool = False) -> int`：默认仅清空 `chunks` 表（DELETE FROM chunks）并返回删除块数；`rescan=True` 时清空后重新扫描 `kb/` 全部文档 `ingest`。重新构建的责任由 `build.py` 承担，语义单一、可预测（评审 I2）。

### FR9 · RAG 智能体消费与总结（检索 → 依据）
06 的 `retrieve`（召回+重排）**被 RAG 智能体（信息查询角色，`app/agent/agents.py` 的 `agents["rag"]`，即提示词 `rag.txt`）调用**，由该智能体负责把检索结果**总结**为本地依据，再交给领域专家：

- **调用链（端到端）**：02 `run()` 第 2 步调 `agents["rag"]` → RAG 智能体经其工具 `retrieve_documents`（`app/agent/tools.py`）调用 06 `get_knowledge_store().retrieve()`（即 FR6 的**召回+重排**）→ 得到 `Passage` 列表 → RAG 智能体按 `rag.txt` 的「总结要求」（聚合不罗列、标注来源与生效日、无结果如实声明）产出检索上下文 `context` → 注入领域专家提示词 → 专家作答并引用本地依据。
- **06 与 RAG 智能体的职责边界**：06 只负责「召回+重排」输出带出处/生效日的 `Passage` 列表；"把片段总结成一段话依据"是 RAG 智能体的 LLM 职责（吃 `rag.txt` 的总结指令），二者分工明确，互不越界。
- **降级契约**：库为空或检索为空时 `retrieve` 返回 `[]`，RAG 智能体如实声明「未检索到本地依据」，提示词强制「不编造」，与 `rag.txt` 及 04 §5.7 一致（降级而非幻觉）。
- **最小改造点**：将 `app/agent/tools.py` 的 `retrieve()` / `lookup_knowledge()` 后端由 04 空库 `Retriever` 切换为 06 的 `get_knowledge_store()` 即可生效，**不改 `run()` 主流程**（RAG 智能体本就由 `run()` 第 2 步调用）。

### FR10 · 双后端兼容
- `kb.engine ∈ {duckdb, sqlite}`：默认 `duckdb`（ATTACH 主库做余弦）；`sqlite` 回落到纯 Python 余弦（仍读主库 `chunks` 表），保证既有测试与 `:memory:` 轻量路径不变。两者均读写主库，不另开文件。
- 统一接口：`get_knowledge_store()` 工厂按 `kb.engine` 返回对应实现，对外暴露一致契约（FR2/FR5/FR6/FR8）。

## 4. 非功能需求

- **依赖**：仅新增 `duckdb`（纯 Python 包，无系统级依赖、无独立服务），不污染现有 venv；与 SQLite 后端并存，可独立测试。
- **性能**：精确最近邻在万级 chunks 内毫秒级（DuckDB 列式 + 向量化执行）；`vss` HNSW 适用于十万级以上或低延迟场景（可选）。
- **可测试**：单测可在**无 torch** 环境运行——通过注入 mock embedder（返回固定维度向量）验证 DuckDB 存储/检索/生命周期，不触发真实模型。
- **兼容性**：同一知识库内 embedding 维度须一致；支持维度自适应（首个 ingest 决定）或 `kb.embed_dim` 显式固定（配合 `vss`）。
- **并发安全**：DuckDB 单写者模型，后端进程内单连接读写，避免并发写竞争；读多写少（构建期写、查询期读）天然契合。
- **可移植**：主库文件随仓库分发或本地构建，不依赖网络（构建脚本幂等，可重跑）。

## 5. 数据模型（DuckDB schema）

```sql
-- 06 知识库核心表（DuckDB）
CREATE TABLE IF NOT EXISTS chunks (
    id              BIGINT,                      -- 自增主键
    doc_id          VARCHAR,                     -- 文档标识（增量/删除键）
    title           VARCHAR,                     -- 文档标题
    doc_type        VARCHAR,                     -- 来源分类：regulation | product | internal
    agency          VARCHAR,                     -- 发文/来源机构（央行/证监会/...）
    domain          VARCHAR,                     -- 领域多标签逗号分隔（保留，便于人工查看/导出）
    domain_tags     VARCHAR[],                    -- 规范化多标签数组 ['Banking','Securities',...]，过滤用此列（list_contains 精确命中）
    chapter         VARCHAR,                     -- 父标题/章节上下文
    effective_date  VARCHAR,                     -- 生效日（ISO，优先现行有效）
    version         VARCHAR,                     -- 文档版本（增量去重）
    source_path     VARCHAR,                     -- 来源文件路径
    content         VARCHAR,                     -- 切分后的文本块
    embedding       FLOAT[],                     -- 向量（变长 list，同库内等长）
    dim             INTEGER                      -- 向量维度（冗余列，便于校验/过滤）
);

-- 元数据过滤索引（DuckDB 自动维护列存索引；精确过滤友好）
-- domain_tags 为 LIST 列：btree 无法服务包含查询，用 min_max 索引记录 list 内 min/max，
-- 查询时跳过完全不相交的 row group；list_contains 主体仍为列扫描（万级可接受）。
CREATE INDEX IF NOT EXISTS idx_chunks_domain_tags ON chunks USING min_max (domain_tags);
CREATE INDEX IF NOT EXISTS idx_chunks_doc_id ON chunks (doc_id);
CREATE INDEX IF NOT EXISTS idx_chunks_eff   ON chunks (effective_date);
```

> 说明：`embedding` 用 `FLOAT[]` 变长 list（适配不同 embedder 维度）；`vss` 模式下需改为固定长度 `FLOAT[dim]` 并建 HNSW 索引。详见技术文档 §3。

## 6. 接口 / API 契约

### 6.1 存储后端接口（`app/kb/store.py`）
统一契约（DuckDB 与 SQLite 双实现共用）：

```python
class KnowledgeStore(Protocol):
    def ingest_text(self, text: str, *, doc_id: str,   # 必填：无默认值，避免重复 ingest 互相覆盖（评审 I1）
                    title: str = "", doc_type: str = "internal",
                    agency: str = "", domain: str = "",
                    effective_date: str = "", version: str = "1",
                    source_path: str = "", max_chars: int = 600,
                    overlap: int = 80) -> int: ...
    def ingest_document(self, path: str, **meta) -> int: ...
    def search(self, query: str, top_k: int = 5,
               domain: str | None = None,
               effective_after: str | None = None,
               vec_weight: float = 0.7) -> list[Passage]: ...
    def retrieve(self, query: str, top_k: int = 3) -> list[Passage]: ...
    def stats(self) -> dict: ...
    def list_docs(self) -> list[dict]: ...
    def delete_doc(self, doc_id: str) -> int: ...
    def rebuild(self, *, rescan: bool = False) -> int: ...   # 默认仅清空；rescan=True 清空后重扫 kb/ 入库（评审 I2）
```

### 6.2 模块级工厂与便捷函数（`app/kb/__init__.py`）
```python
def get_knowledge_store() -> KnowledgeStore:
    """按 config.kb.engine 返回 DuckDB 或 SQLite 实现（懒加载）。"""

# 便捷函数（02 run() 经此取片段，向后兼容 04）
def retrieve(query: str, top_k: int = 3) -> list[Passage]: ...
def ingest_text(text: str, **meta) -> int: ...
def ingest_document(path: str, **meta) -> int: ...
```

### 6.3 构建脚本（`app/kb/build.py`）
- `python -m app.kb.build`：扫描 `kb/` 目录文档 → `ingest` → 写主库 `chunks` / `kb_meta` 表 → 打印 `stats()`。
- 可作为 CI / 部署前步骤，也可在 `lifespan` 阶段按需触发（首次启动自动构建，可选）。

### 6.4 可选 REST（排期，非本期）
后续可在 03 层暴露 `POST /api/v1/kb/ingest`、`GET /api/v1/kb/stats`、`DELETE /api/v1/kb/doc/{doc_id}`，供运维管理知识库；本期以模块级接口 + 构建脚本为主，不新增路由。

## 7. 配置（config.yaml 新增 `kb` 段）

```yaml
# —— 06-知识库（DuckDB）：存储后端与构建配置 ——
kb:
  engine: duckdb              # duckdb（默认）| sqlite（回落 04 既有）
  # 06 不单独配 path：chunks/kb_meta 表建在 03 主库同一实例，随 init_db() 建表
  embed_dim: 0                # 0=自适应（取首个 embedding 维度）；非 0 固定（配合 vss HNSW）
  use_vss: false              # 是否启用 vss HNSW 索引（默认关闭，离线环境避免扩展下载）
  build_on_startup: false     # lifespan 阶段是否自动构建 kb/（默认手动 build 脚本）
  chunk:
    max_chars: 600
    overlap: 80
  # 向量化依赖 01 的 get_embedder()；local 离线嵌入见技术文档 §4
  local_embed:
    enabled: false            # true 时启用进程内嵌入直载（不依赖外部嵌入服务）
    model_path: ${LOCAL_EMBED_MODEL_PATH}   # 本地嵌入模型目录，由环境变量/本地 secret 注入，不入库（评审 I5）
```

> 与既有 `emb` 段关系：`kb` 的向量化统一走 01 `get_embedder()`（`emb.mode`）；`kb.local_embed` 仅为「local 模式离线向量化」的可选补充，启用时复用 app/model/local 的惰性加载范式，**不影响** `emb` 配置契约。

## 9. 已知问题 / 待办

1. **local 模式嵌入可用性**：`run()` 要真正向量化需 `get_embedder()` 可用；api 模式需 `OPENAI_API_KEY`，local 模式需本地嵌入服务或启用 `kb.local_embed` 进程内直载——06 须明确 local 离线嵌入路径（技术文档 §4 给出方案）。
2. **维度一致性**：同一 DuckDB 库内 embedding 维度必须一致；跨 embedder 切换（如 bge 512 ↔ text-embedding-3-small 1536）需重建库，文档须提示。
3. **总文档 §7 拓扑仍待校正**：`00-总文档` 未含 06 知识库层，待 02/04/06 评审通过后统一回正（不属 06 改动，沿用 04 §11 约定）。
4. **`vss` 扩展离线风险**：HNSW 加速依赖 `INSTALL vss`，内网/离线环境可能失败，故默认 `use_vss=false`，精确扫描兜底。
5. **二进制解析**：PDF/DOCX/XLSX 本期不接，沿用 04 后续需求；`ingest_document` 对二进制抛清晰 `NotImplementedError`。
