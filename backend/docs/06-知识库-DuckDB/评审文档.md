## 1. 总体评价

两份文档质量较高：职责边界清晰、DuckDB 选型论证充分、双后端兼容与降级契约成熟、无 torch 单测对 CI 友好。整体符合「演进而非重写」原则，复用 04 的切分/BM25/重排而非另起炉灶，工程决策稳健。

主要风险集中在三处：
- **(a) 双路召回实现与描述自相矛盾**——BM25 在向量候选子集上算，等于退化为单路；
- **(b) domain 多标签过滤用 `LIKE` 模糊匹配**——既不精确又使索引失效；
- **(c) 接口契约若干默认值**存在覆盖/语义含糊风险。

以上需在编码前修订。

## 2. 亮点

- 嵌入式零服务范式与现有 SQLite 部署一致，迁移成本低。
- 双后端（duckdb 默认 / sqlite 回落 04 既有）保证 `:memory:` 测试不回归，稳妥。
- 降级契约明确：空库/空检索返回 `[]`，RAG 智能体据 `rag.txt` 如实声明「不编造」，与 04 §5.7 一致。
- 维度一致性在入库即校验 + `kb.embed_dim` 固定模式双重保障。
- vss 默认关闭规避离线 `INSTALL` 风险，精确扫描兜底。
- 无 torch 单测（mock embedder 注入）使 CI 不依赖 GPU/模型。
- 实现步骤（技术 §9）与验收标准（需求 §8）一一对应，可落地性强。

## 3. 需修订的问题

### 3.1 阻塞级（编码前必须修订）

**B1 ·【已修订】双路召回退化为单路（技术 §5.4 伪代码 vs §5.1 文字矛盾）**
- 问题：§5.1 文字要求「向量召回、BM25 关键词召回两路候选取并集」；但 §5.4 伪代码中 BM25 是在向量召回返回的 `top_k*β` 子集 `contents` 上计算的（`_BM25(contents)`），并未在全库独立召回。这导致 BM25 只能给向量已召回的块打分，无法补召回向量漏掉的块——双路并集退化成向量单路 + 线性加权。
- 影响：直接违背 FR6「降低向量单路漏召」的设计目标，关键词召回形同虚设。
- 修订：BM25 应在元数据过滤后的**全库**上独立计算 `top_k*β` 候选，再与向量召回候选取并集后融合重排。修正伪代码：
  ```python
  vec_rows  = self._duckdb_recall(query, top_k*β, domain, effective_after)  # 全库向量召回
  bm25_rows = self._bm25_recall(query, top_k*β, domain, effective_after)     # 全库关键词召回
  candidates = _union_by_id(vec_rows, bm25_rows)                            # 按 id 去重并集
  # 再对 candidates 做归一化 + 加权融合
  ```
  同时让 §5.1 文字与 §5.4 代码一致。
- ✅ 已修订：技术 §5.4 重写为双路独立召回（`_duckdb_recall` / `_bm25_recall` 在元数据过滤后的**全库**独立召回）+ `_union_recall` 按 id 去重并集 + 加权融合；§5.1 文字同步。

**B2 ·【已修订】domain 多标签过滤用 LIKE 模糊匹配（需求 §5/§7、技术 §3.2）**
- 问题：`WHERE domain LIKE '%' || ? || '%'` 对逗号分隔字符串做子串匹配，两个问题：
  1. **误匹配**：domain 含 `Securities` 时查询 `security` 会命中；含 `Banking` 时查询 `bank` 命中——无法精确表达「包含某标签」。
  2. **索引失效**：前导通配符 `%tag%` 使 `idx_domain` 完全失效，万级 chunks 退化为全表扫描，违背「元数据过滤缩小候选集」的性能初衷。
- 修订：schema 增加数组列 `domain_tags VARCHAR[]`，ingest 时 `string_split(domain, ',')` 写入；过滤改用 `list_contains(domain_tags, ?)`。DuckDB 对 LIST 列有 min/max 索引，包含过滤比 LIKE 前模糊更有效。若坚持 VARCHAR 方案，至少改用 `',' || domain || ',' LIKE '%,' || ? || ',%'` 边界匹配消除跨词误命中（仍不解决索引失效）。

### 3.2 重要（建议编码前修订）

**I1 ·【已修订】`doc_id` 默认值 `"doc"` 有覆盖风险（需求 §6.1 接口契约）**
- 问题：`ingest_text(..., doc_id: str = "doc")` 默认同 doc_id。多次无参 `ingest_text` 会被 FR2「同 doc_id 视为新版本先删后写」逻辑互相覆盖，静默丢失数据。
- 修订：`doc_id` 改为必填（去掉默认值）或由函数自动生成 UUID；默认值改为 `""` 并在 ingest 时拒绝/自动分配。

**I2 ·【已修订】`rebuild()` 语义含糊（需求 §8/FR8 vs 技术 §6）**
- 问题：需求 §8 写「清空 chunks 表并重新 ingest kb/ 全部文档（或仅清空供外部重建）」，括号给出两种语义；技术 §6 表又写「若传 kb/ 路径则重新扫描」。两文不一致，调用方无法预判行为。
- 修订：明确二选一——`rebuild()` 仅清空（DELETE FROM chunks，返回删除块数）；重新扫描构建由 `build.py` 负责。若需合并，给 `rebuild(rescan: bool = False)` 显式参数。

**I3 · 增量 ingest「先删后写」非原子（需求 §2.1/FR2）**
- 问题：同 doc_id 重复 ingest = 先 `delete_doc` 再写多块，非事务包裹。中途失败会留下该 doc 部分块（或零块），状态不一致。
- 修订：单 doc 的 delete + 多 INSERT 包在同一事务（单写者串行本就满足，加 `BEGIN/COMMIT` 即可）。

**I4 ·【已修订】duckdb 版本下界未声明（需求 §4）**
- 问题：向量检索依赖 `list_cosine_distance`，该函数在 DuckDB 1.1+ 提供；但需求 §4 仅写「仅新增 duckdb（纯 Python 包）」，未标注版本约束。
- 修订：依赖处显式 `duckdb>=1.1.0`；技术文档 §3.2 已注「1.1+」，应与依赖声明对齐。

**I5 ·【已修订】`config.yaml` 硬编码本地绝对路径（需求 §7）**
- 问题：`kb.local_embed.model_path: D:/models/bge-small-zh` 是 Windows 绝对路径，跨平台不可用且不应用于仓库配置。
- 修订：`config.example.yaml` 用相对路径或 `${LOCAL_EMBED_MODEL_PATH}` 占位；真实路径由本地 env/secret 注入，不入库。

### 3.3 建议（可选优化）

- **S1 · `dim` 冗余列可瘦身**：`chunks.dim` 每行存同一维度是冗余；改为 `kb_meta` 小表存全局 dim，ingest 首条时写入并校验。
- **S2 · `Passage` 显式复用 04 数据类**：技术 §1.1 称「复用 Passage 契约」，建议 `app/kb` 直接 `from app.agent.retrieval import Passage`，避免 06 重新定义导致字段漂移。
- **S3 · `00-总文档 §7` 拓扑回正**：已知问题已承认；建议 06 评审通过后与 04 §11 一起回正，避免文档拓扑长期失配。
- **S4 · vss 定长 ARRAY 转换实测**：技术 §3.3 `ALTER TABLE ... ALTER embedding SET DATA TYPE FLOAT[1536]` 在 DuckDB 对 LIST→定长 ARRAY 的支持需编码阶段实测；可选路径，默认关闭，风险可控。
- **S5 · 多 worker 只读打开**：技术 §11 已注多进程共享同一 duckdb 文件需协调；建议运行期以只读模式 `duckdb(path, read_only=True)` 打开，避免构建期外意外写。
